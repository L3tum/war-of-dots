# Deep Plan: Test WebGPU Rendering and the Frontend

## Overview
The game's graphics code currently has no real tests: the "renderer tests" run against hand-copied math inside the test file that has drifted from the actual renderer, and the network layer's main class is never constructed. This plan adds cheap-to-run test layers so rendering and frontend bugs are caught locally in minutes instead of through human back-and-forth: (1) headless unit tests that run the *real* `Renderer` against a fake GPU and the *real* `Connection` against a fake WebSocket, (2) a cross-language contract test that locks the Rust↔TypeScript wire format, and (3) an optional real-browser smoke test that plays a recorded game and checks for render errors.

## Problem Statement
`renderer.test.ts` re-implements geometry locally (its own `detectBorderEdges`, `generateBorderVertices`, `worldToScreen`, `generateCityDotVertices`) and has drifted: the real renderer emits border positions in **world space** and does the camera transform in **WGSL** (renderer.ts:347-348), so the test's local screen-space `worldToScreen` corresponds to no real renderer function, and the real border detection operates on `fillTerritory(...)` output (renderer.ts:1250) rather than the raw grid the test's copy sees. There is also no browser/CI layer to catch frontend regressions before they reach the server.

## Design
Layer the work so each layer pays for itself before the next starts. Verified: `Renderer`'s constructor is `constructor(canvas: HTMLCanvasElement, device: GPUDevice)` (renderer.ts:157) — the device is already a constructor param, so a fake `GPUDevice` needs no renderer refactor. `textureFormat` comes from `navigator.gpu!.getPreferredCanvasFormat()` (renderer.ts:162), the symbol atlas uses `new OffscreenCanvas(...)` (renderer.ts:172), and `canvas.getContext('webgpu')` (renderer.ts:159); all three must be stubbed under happy-dom. Renderer already exposes test state: `camera`, `fogDirty`, `borderDirty`, `lastRenderError`, the `*VertexCount` fields, and public `renderFrame()`/`startRenderLoop()`.

- **Layer 1 — headless unit tests (fake GPU + real `Renderer`/`Connection`), no new infrastructure.** Runs in existing `make test` → `frontend-test` (vitest 4.1.10 + happy-dom). This directly kills the drift: the real code is what's tested.
- **Geometry strategy — assert on recorded `writeBuffer` payloads, skip broad extraction.** The transform lives in WGSL, so there is no TS `worldToScreen` to extract and testing one would relocate the drift, not delete it. The fake GPU records the *real* emitted positions (world space), stride, and counts, which is the authoritative geometry output. Extract **only** the single drift-affected pure block, `detectBorderEdges`, out of the `render(gameState)` data-update pass (renderer.ts:1247-1280, currently an inlined loop — note: this is `render()`, the update pass, *not* `renderFrame()`, the draw pass) so the player-vs-player / NONE(255)-excluded edge cases run against real logic fed with `fillTerritory` output. (`fillTerritory` in territory.ts:27 is already a pure exported function, testable today.)
- **Layer 1b — CBOR golden-fixture contract test.** Rust has `to_cbor_bytes` (src/server/protocol.rs:764, `ciborium`) plus ~15 round-trip tests; the client pins lockstep constants ("MUST stay in lockstep with `src/server/protocol.rs`", connection.ts:104-107: `UNIT_POSITION_STEPS = 65_536`, I3/I4 packing). One committed golden **byte** file serialized by **`ciborium`** in Rust and decoded by **`cbor-x`** in vitest locks schema + packing drift without a browser. No JSON companion — canonical input values live inline in the tests.
- **Layer 2 — no-server real-browser E2E, CPU software rendering (Playwright, gated/skippable).** Runs the *real* GPU stack on CPU: `xvfb-run` + `headless: false` + Chromium's Dawn/SwiftShader software adapter (`--enable-unsafe-swiftshader --use-angle=swiftshader` — re-verify exact flags against current Chromium before freezing; Playwright's default headless shell has no `navigator.gpu`, hence the xvfb route). No GPU hardware needed. The no-server path (`?replay=file.jsonl`) runs the full in-page replay pipeline with **no game server and no WebSocket**: `ReplayPlayer.loadReplay` fetches `` `replays/${file}` `` (replay_player.ts:40), so a static file server over `frontend/dist` + a `replays/` dir supplies the page and fixture. Gated behind a new make target and skipped gracefully when xvfb/Chrome are absent.
- **Package research (checked Sept 2026, npm registry + GitHub) — there is no ready-made mock/fake `GPUDevice` package.** Candidates examined: `vitest-webgl-canvas-mock`/`jest-webgl-canvas-mock` (mock the *WebGL* canvas 2d/webgl context — different API surface, no `GPUDevice`); `chaunceyjiang/fake-gpu` (spoofs GPU *info* strings, not the API); `vgpu` (Vercel Labs shader-abstraction framework with its own `effect`/`frame` API, not a drop-in `navigator.gpu`); `webgpu`/`@kmamal/gpu`/`bun-webgpu` (real Dawn-backed GPUs, not mocks — see software-rendering bullet). None of them record `writeBuffer` payloads or draw-call sequences, which is the whole point of Layer 1's assertions. Hence the small hand-rolled recording fake is justified: it doubles only the ~20 methods the renderer actually calls (~200 lines), and its surface is pinned by this codebase rather than a generic API.
- **CPU software rendering — already covered by Layer 2, with an optional Node path documented.** Layer 2 *is* CPU software rendering: headless Chromium under `xvfb-run` uses the Dawn/SwiftShader software GPU, so the real WGSL shaders are compiled (naga/tint) and rasterized **on CPU — no GPU hardware required** (this machine has no GPU; `xvfb-run` is installed). Separately, the Dawn-backed `webgpu` npm package (`dawn-gpu/node-webgpu`, v0.6.0, actively maintained by toji/greggman, 450k+ monthly downloads, prebuilt linux binaries) exposes the standard WebGPU API in Node and can render to textures + read back pixels on a software backend (e.g. lavapipe). Its own README explicitly recommends Playwright/Puppeteer over it for testing web pages (→ Layer 2) and notes it provides no canvas/web-platform integration. **Optional Layer 1.5** (only if WGSL-only regressions recur or browser E2E proves too slow): run the real `Renderer` under vitest against dawn.node's software device — requires a shim translating the renderer's `canvas.getContext('webgpu')`/`getCurrentTexture()`/`OffscreenCanvas.transferToImageBitmap` calls to render-to-texture + `readBuffer` (the package supplies no DOM surface), so it carries shim-maintenance cost; not in the critical path.
- **Rejected:** pixel/screenshot baselines — flake factory; "no render errors" is fully served by `lastRenderError === null` + no error overlay. **The server-boot E2E case** (`cargo run` + `/ws/replay?game_id=` + `/debug/stats` stats-panel assertion) is **deferred** — it re-runs the same client pipeline the no-server case covers, and `/debug/stats` is cfg-gated (game_server.rs:92-95) so it needs a debug build. Add later if the no-server spec proves out.
- Alternatives considered: testing only via Playwright (rejected — CI-hostile and slow for pure-math bugs); extending happy-dom instead of a fake device (rejected — happy-dom won't provide `GPUDevice`); ready-made GPU mock package (rejected — none exists, see research bullet).

## Risks & Mitigations
- **happy-dom lacks `OffscreenCanvas` / `getContext('webgpu')` / `navigator.gpu`** — stubbed by `setupFakeGpu()` in the vitest setup file; verified needed at renderer.ts:159/162/172.
- **Geometry test could relocate the drift** — resolved by asserting on recorded `writeBuffer` payloads (the real world-space output) rather than a TS transform, and extracting only the one drift-affected function (`detectBorderEdges`); `detectBorderEdges` tests must use `fillTerritory` output, not the raw grid.
- **happy-dom canvas is 0×0** — set `canvas.width`/`height` explicitly before asserting on geometry-dependent outputs.
- **Mock GPU can't catch WGSL shader bugs** — accepted at Layer 1; Layer 2 compiles real shaders; if WGSL-only regressions recur, add a naga/WGSL syntax check or the Dawn-backed Node option.
- **E2E is flaky/expensive on GPU-less Linux** — strictly gated behind `make frontend-e2e`, skipped gracefully without xvfb/Chrome, never in the default `make all` path.
- **Golden-fixture regeneration friction + `to_cbor_bytes` is `#[cfg(test)]`** — document the concrete `cargo test`-dump / dev-bin regeneration path in the fixture's README comment; the Rust test re-decodes the same bytes so a corrupt/wrongly-regenerated fixture fails fast.
- **`float_deser` encode asymmetry** — pinned explicitly in the contract test (JS→Rust of whole-number floats); the Rust→both-decode direction sidesteps it.
- **No CI exists today (no `.github/workflows`)** — Layer 1 needs none; add a minimal workflow running `make all` + `make frontend-e2e` (skippable) as a follow-up only after Layer 1/2 land cleanly.
