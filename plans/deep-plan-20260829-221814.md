## Problem Statement

The game server sends per-player CBOR delta frames over raw TCP / WebSocket with no interest management, fat string-based entity payloads, whole-grid resends on any grid change, and an unbounded per-client `Vec<u8>` egress channel. The goal is a sustained reduction in **CPU (network phase)**, **heap allocations**, and **wire bandwidth** — validated package-by-package with the existing A/B benchmark harness, per the codebase convention that any algorithm change must be benchmarked before landing (`src/server/delta.rs` header).

## Scope Decisions

**In scope:**
- Server-side network phase, egress transport (TCP + WS bridge), wire format evolution (negotiated), benchmark harness extensions, and the TS client changes each wire change requires (`frontend/src/net/connection.ts`, `frontend/src/game/*`, regenerated `frontend/src/generated/protocol.ts`).
- Interest management (#1), entity compression (#2), grid RLE (#3), transport coalescing/backpressure (#4), scratch encode buffers + codec evaluation (#5), wire-rate decoupling (#6, server-side emit gating), lobby/reason-log traffic (#7), TCP_NODELAY + length-prefixed framing (#8).

**Explicitly deferred / skipped (and why):**
- **UDP transport** (#9): ≤ 16 players/room, commands must be reliable, grid frames are 40 KB–1 MB — a large rewrite buying latency only. Revisit only if post-WP measurements show TCP is still the bottleneck.
- **LZ compression** (#10): not worth it below ~256 B and marginal elsewhere; revisit only if a dense grid-dirty regime persists after WP4, measured via `net_wire_bytes`.
- **Replay recording** (JSONL `serde_json` per `MoveEvent`): disk-only, not on the wire; untouched. Replay compatibility is preserved structurally — replays record game logic (`MoveEvent`s), not wire frames.
- **Rayon parallelization of the delta phase**: a previous attempt was reverted; the `delta.rs` header requires A/B before parallelizing. Not part of this plan.
- **WebSocket protocol changes**: framing/NODELAY (WP3) apply to the raw TCP transport only; WS already frames messages. WS benefits from Bytes/coalescing/backpressure via the shared bridge channel (WP1).
- **Storage/config serde_json usage**: not network traffic.

### Protocol compatibility strategy (applies to all WPs)

1. **Handshake** (introduced in WP3): add `ClientMessage::Hello { client_version: u32, features: u32 }` (client sends it as the very first message on a new TCP/WS game connection) and `ServerMessage::Negotiated { server_version: u32, features: u32 }` (server replies once, before any other message). Feature bits (u32 bitmask): `F_FRAME_LEN=1`, `F_GRID_RLE=2`, `F_COMPACT_ENTITIES=4`, `F_AOI=8`, `F_POSTCARD=16` (reserved).
2. **Legacy path is frozen**: if the first inbound message is **not** `Hello` (or arrives after a grace timeout with no `Hello`), the server treats the connection as legacy: `features = 0`. Legacy clients get byte-identical frames to today — CBOR, string IDs, full-grid diffs, no length prefix, no new `ServerMessage` variants ever sent to them. New enum variants are only ever emitted to connections whose negotiated `features` include the matching bit. This is safe because ciborium/serde tag external enum variants; an unknown variant would break an old decoder, so gating is mandatory, not optional.
3. **Struct field additions** (e.g. new grid-diff field on `GameDeltaMessage`) use `Option` + `#[serde(skip_serializing_if = "Option::is_none", default)]` so old clients (serde ignores unknown fields) and new clients both tolerate the other's frames.
4. **Resync is the safety net for every risky change**: `FullState` already exists and is already sent at game start and on spectator attach. Any dropped frame, resync marker, or client-side decode error triggers a client `ClientMessage` (reuse: no new message needed — server sends `FullState` unconditionally on its own resync trigger; the client can force resync by re-sending `GetLeaderboard`? **No** — add `ClientMessage::RequestResync` in WP3, one new variant, server answers with `FullState`).
5. **Replays** (`/ws/replay`, `handle_ws_replay`-style 60 Hz `FullState`/`DeltaState` loop, game_server.rs lines 1321–1425) are unaffected: they serve stored `MoveEvent`s over the legacy format.

## Ordered Work Packages

Ordering rationale: WP1/WP2/WP3 are low-risk, mostly server-local, and land the transport substrate (Bytes, bounded egress, handshake) that every later wire change builds on. WP3 is a *protocol* prerequisite for WP4–WP6 (feature negotiation). WP4/WP5 are the bandwidth killers with contained blast radius (grid bytes, entity bytes). WP6 is the restructure that breaks W9 splicing and needs the negotiated client first. WP7 then cuts the encode cost the remaining volume, and WP8 cuts the emit frequency.

### WP1 — Egress transport: `Bytes`, per-tick frame coalescing, `TCP_NODELAY`, bounded game channel with resync

**Goal.** Kill per-frame allocations and syscalls on egress; add backpressure with authoritative resync; make shared frames (lobby, `GameOver`, `LlmReasonLog`) cheap refcount bumps.

**Current behavior.** `PlayerSender::Tcp(mpsc::UnboundedSender<Vec<u8>>)` (room.rs:68) — unbounded, one `Vec<u8>` per message, sender task `write_all`s each frame (game_server.rs:1446–1460). `net_send_ms` is "Always 0 in the headless benchmark … models no outbox" (benchmark.rs `TickData`). Lobby broadcasts clone per player (lobby.rs:161–172). No `TCP_NODELAY`.

**Changes.**
1. Add `bytes = "1"` to `Cargo.toml`.
2. `room.rs`: `PlayerSender::Tcp(mpsc::UnboundedSender<Bytes>)` (control class) plus `PlayerSender::send_bytes(&self, Bytes)`. Add a bounded **game-delta** channel per connection: `mpsc::channel::<Bytes>(64)`; extend `PlayerConnection` with `delta_tx: mpsc::Sender<Bytes>` (or a small `Egress { control: UnboundedSender<Bytes>, game: Sender<Bytes> }` struct owned by `PlayerConnection`). `Command::AddSpectator(PlayerSender)` signature follows suit (room.rs:33) — update both match arms handling `Command::AddSpectator` (game_server.rs:539 in the tick `select!`, and :877 in the idle branch) plus the spectator bridge construction site (~1200).
3. Coalesce: in the tick send loop (game_server.rs ~740–785), each player's per-tick `DeltaState` is exactly one frame today; keep it one, but change the unit of work from `Vec<u8>` to `Bytes` — outbox becomes `Vec<(String, Bytes)>`, `NetworkPhaseResult.encoded` (delta.rs:547) becomes `Vec<(String, Bytes)>` (wrap the `Vec<u8>` from `encode_message*` with `Bytes::from` — zero copy). For multi-message ticks (e.g. `LlmReasonLog` + `DeltaState`), the tick's game-class frames for one player are concatenated into a single `Bytes` before enqueue. **Client impact (new work, not verification):** the browser client (`frontend/src/net/connection.ts`, **WebSocket-only**) currently decodes each WS binary message as a single CBOR message (`onmessage` → `CBOR.decode`), so multi-document payloads need new client support: loop-decode consecutive CBOR documents in one WS message (new code + new vitest in `connection.test.ts`). The raw-TCP client is `src/bin/console_client.rs`, whose read loop (`from_reader` + `buf.clear()`) drops trailing concatenated frames and must be updated in the same PR.
4. Backpressure: `game` channel is bounded (64). `PlayerSender::send_game(&self, Bytes) -> Result<(), ()>`: `try_send`; on `Err(TrySendError::Full(_))`: send one `ResyncRequested`-style control marker (a `Bytes` tag, or simpler: enqueue a `ServerMessage::FullState` produced by the room loop via a `tokio::sync::oneshot` ping) — **spec**: enqueue a `Resync` control item and drop the delta frame. Sender task drains control + game in priority: game frames first each wake, control never drops. First-full-per-connection triggers exactly one FullState per 256-tick cooldown (anti-flap).
5. `handle_tcp_client` (game_server.rs:1440): set `stream.set_nodelay(true)` before `split`. WS path: `ws_sink.lock().await` per frame stays (axum constraint) but frames arrive pre-coalesced.
6. Benchmark: model the outbox in `benchmark.rs` — in the network phase, after `run_network_phase`, count egress messages per player (1 coalesced frame vs N) and add `net_egress_msgs: u32` and `net_resyncs: u64` to `TickData`; keep `net_send_ms` = 0 but report coalesced-vs-uncoalesced frame counts in the HTML (the A/B for WP1 is `allocs`/`bytes` + frame count, since real syscall time needs a live client).

**Protocol changes & compat.** None on the wire format. One mpsc item = one WS binary message (game_server.rs WS bridge), so coalesced game frames reach the browser as multi-document WS payloads — the client changes in item 3 are a **hard dependency** of this package, not a verification task. Legacy `console_client` receives concatenated TCP frames and loses trailing documents until updated in the same PR; ship client+server together.

**Metrics & verification.** `./run-stresstest.sh wp1` then `cargo run --profile release --features debug-overlay,microbenchmarks,bench-alloc -- --benchmark --bench-seed 42 --bench-html ./reports/wp1.html --bench-prev ./reports/stress_base.html` (200×200 profile: `./run-benchmark.sh wp1`). Expect: per-tick `allocs` down (no per-player `Vec` clones in lobby/spectator paths), `max_alloc` unchanged, `net_egress_msgs` ≤ players/tick.

**Risks & rollback.** Drop-newest-delta semantics could briefly desync a slow client — mitigated by guaranteed FullState resync; the existing "send error drops the player" path (game_server.rs ~760) is retained as a last resort. WS backpressure (slow consumer) now surfaces as channel-full instead of unbounded memory growth — intended. Rollback: single PR, revert restores `Vec<u8>`/unbounded path.

**Est. effort.** 2–3 days server + 1 day client (connection reassembly tests) + 0.5 day harness.

**Definition of done.** Stress A/B vs baseline: per-tick `allocs` ≥ 20% lower with `net_wire_bytes` unchanged (bytes-neutral transport win); unit test: a 64-frame backlog on the game channel produces exactly one resync and no delta loss beyond the dropped frames; new vitest in `connection.test.ts` for 3-document single-WS-message decode green (no such test exists today).

### WP2 — Lobby & LLM-reason traffic reduction (no protocol change)

**Goal.** Remove per-player clone + per-player `tokio::spawn` in lobby broadcasts; bound `LlmReasonLog` fan-out cost.

**Current behavior.** `broadcast_lobby_update` (lobby.rs:161–172): `encode_message(msg)` once, then `encoded.clone()` + `tokio::spawn(async move { sender.send(encoded_clone) })` per player. `LlmReasonLog` (game_server.rs:500–511): encode once, `encoded.clone()` per player, sent to **all** players (all human players and spectators; LLM-only players are not in the tick-loop `players` list — the `None` no-op case applies to the lobby broadcast path instead) on every arrival, potentially multiple per tick.

**Changes.**
1. `lobby.rs`: change `broadcast_lobby_update(&self, code, msg)` to take/produce a `Bytes` and send via the existing per-client `PlayerSender` (from WP1: `Bytes` clone = refcount bump). Drop the `tokio::spawn` per player — the control channel's sender task already provides async send; do `for player in &lobby.players { let _ = player.connection.send_bytes(frame.clone()) }` from the caller's task (control send is `try_send`-capable; if the channel API is async-only, use one `tokio::spawn` **per broadcast** iterating players, not per player).
2. `LlmReasonLog`: per-tick coalescing — buffer `(name, action, reason)` triples already drained in the tick loop; send at most one `LlmReasonLog`-bearing frame per tick per player (concatenate actions for multi-entry ticks by joining `action` strings, keeping the first/last reason — trivial since it's a log UI). Add `net_misc_frames: u32` to `TickData` (reason-log + advice + lobby frames per tick in the benchmark; the benchmark currently models none of this — add a synthetic N LLM players option? **No**: keep the benchmark honest; measure via `allocs`/`bytes` delta of the coalescing change and a targeted unit test counting sends with a fake `PlayerSender`).

**Protocol changes & compat.** None. (A `LlmReasonLogBatch` message variant is deliberately *not* added — routing "to acting player + spectators only" changes who sees logs, a product decision; deferred, see Open questions.)

**Metrics & verification.** `./run-benchmark.sh wp2` + `--bench-prev` against `wp1` report: per-tick `allocs`/`bytes` down on ticks where lobby/reason traffic fires (benchmark adds a synthetic lobby update every 100 ticks? **Yes —** add `--bench-lobby-traffic` flag to `benchmark.rs` that injects a `LobbyUpdate` encode+broadcast every 100 ticks across `BENCH_PLAYERS` players so the effect is measurable). Unit test: 8 players, `broadcast_lobby_update` → exactly 8 channel sends, 0 `Vec<u8>` clones of the payload (asserted via bench-alloc counter or a counting `PlayerSender::Websocket` closure).

**Risks & rollback.** Low. Rollback: revert.

**Est. effort.** 0.5–1 day.

**Definition of done.** `--bench-lobby-traffic` A/B: per-tick allocs on lobby-traffic ticks ≥ 50% lower; stress A/B neutral on `net_wire_bytes`/`net_ms`.

### WP3 — Handshake, feature negotiation, length-prefixed TCP framing

**Goal.** Introduce the negotiation foundation used by WP4–WP6; make TCP ingress O(1) framing instead of re-parsing a growing buffer; set `TCP_NODELAY` (done in WP1 for egress symmetry).

**Current behavior.** No handshake: first client message is `ClientMessage::LobbyMessage(...)` (protocol.rs `ClientMessage`). TCP read loop re-parses CBOR from the whole buffer on every `read` (game_server.rs:1467–1500), clears on success, keeps partial bytes on failure (1 MB cap) — O(n²) over a fragmented multi-message buffer.

**Changes.**
1. `protocol.rs`: add `ClientMessage::Hello { client_version: u32, features: u32 }` and `ClientMessage::RequestResync`; add `ServerMessage::Negotiated { server_version: u32, features: u32 }`. Add `const PROTOCOL_VERSION: u32 = 2` and feature-bit constants (`F_FRAME_LEN=1`, `F_GRID_RLE=2`, `F_COMPACT_ENTITIES=4`, `F_AOI=8`) in `protocol.rs`.
2. `room.rs` / `game_server.rs`: per-connection `Negotiation { features: u32, done: bool }` (starts `features = 0` = legacy). In `handle_client_message` (game_server.rs:1587): if msg is `Hello` and `!done` → intersect with server-supported features, send `Negotiated`, mark done, and continue normal lobby handling. First non-Hello message → mark `done`, features stay 0 (legacy). `RequestResync` → room sends `FullState` on that connection (reuse `Command::AddSpectator`'s `full_state_with_vision` construction, game_server.rs ~882).
3. **Framing (only when `F_FRAME_LEN` negotiated)**: server writes `u32` BE length prefix + frame on the TCP path; read loop becomes: fill buffer → loop { if len ≥ 4: read prefix, wait for full frame, `decode_client_message`, advance }. Old legacy connections keep today's decode-retry loop verbatim. WS path unchanged (WS frames it).
4. Client (`frontend/src/net/connection.ts`): the browser client is WS-only (no TCP): send `Hello { client_version: 2, features: 0b1111 }` as the first WS binary message; on `Negotiated`, apply bits to decoder behavior (WP4–WP6 hooks); WS messages remain single-frame — no length-prefix code in the browser; on decode error send `RequestResync` (rate-limited 1/s). Regenerate `frontend/src/generated/protocol.ts` (schemars). **`src/bin/console_client.rs` task** (the only real TCP client): send `Hello` on TCP connect and implement the 4-byte-prefix framing loop there when `F_FRAME_LEN` is negotiated.
5. `decode_client_message` unchanged (CBOR); framing is transport-level only, so `RequestResync`/`Hello` work even on legacy-framed connections (a new client talking to an old server gets "no Negotiated reply" → proceeds as legacy after a 100 ms grace; a new server seeing an old client's first `LobbyMessage` proceeds legacy — no cross-version lockout either way).

**Protocol changes & compat.** New variants only ever sent to clients that sent `Hello` (server) or after receiving `Negotiated` (client). Legacy frozen per the compat strategy. Replay path never negotiates.

**Metrics & verification.** Harness: add a `--bench-frame-len` flag (forwarded in `main.rs` like `--bench-splice`) that adds 4 bytes per encoded frame to `wire_bytes` so the prefix overhead is visible in `net_wire_bytes` (the harness otherwise models no transport — see `net_send_ms` doc). `./run-stresstest.sh wp3` A/B (`--bench-frame-len` on): `net_wire_bytes` up by exactly 4×(frames/tick) bytes (prefix overhead — must be visible and justified), `allocs` down on the read-path (no growing-buffer reparse; measure via a new microbenchmark in `src/microbenchmarks` — add "tcp_frame_reassembly: 64 KB message split over 16 reads" case comparing old vs new parser). E2E: new client ↔ new server, new client ↔ legacy server (feature-masked), legacy client (old `connection.ts` build) ↔ new server must all pass a 5-minute smoke game (`cargo run --profile release -- --serve`, two browser tabs + a scripted legacy WS client test in vitest).

**Risks & rollback.** Protocol surface risk is the highest of the three "quick wins" — mitigated by the frozen legacy path and the 3-scenario e2e matrix above. Rollback: revert; old clients remain supported by construction.

**Definition of done.** All three compat scenarios green in CI (add a `--compat-smoke` e2e script or vitest suite); framing microbenchmark shows ≥ 2× fewer parser passes on fragmented input; stress A/B: `net_wire_bytes` delta equals exactly the prefix overhead (no accidental re-encoding), `allocs` non-increasing.

### WP4 — Per-cell grid diffs (RLE borders, vision bit-delta)

**Goal.** Grid-dirty ticks currently resend the entire flat grid — 40 KB at 200×200, ~1 MB at 1000×1000. Send only changed cells.

**Current behavior.** `compute_shared_deltas` (delta.rs:213) detects border change via `Arc::ptr_eq`/slice compare vs `baselines.prev_border` and sets `border_grid_diff: Option<Arc<Vec<u8>>>` to the **whole** grid. Per-player vision change → whole `vision_grid_diff` (delta.rs `build_delta_inner`, line 443). `estimate_delta_size` charges `v.len() + 16` for the full grid (protocol.rs:412–424). `SpliceShared::build` splices `border_grid_diff` as the first shared entry (protocol.rs `SpliceShared` docs).

**Changes.**
1. `protocol.rs`: add `GridDiff` wire enum (negotiated `F_GRID_RLE`):
   ```rust
   #[serde(tag = "kind", content = "cells")]
   pub enum GridDiff { Full(Vec<u8>), Cells { cells: Vec<[u8; 2]>, values: Vec<u8> } }
   ```
   Border: `Cells` = changed-cell (x,y) u8 pairs + u8 values (player idx 0..N or 255). When the run of changed cells in row-major order is long, RLE-encode `(row, start_col, len, value)` quadruples instead — pick RLE when `cells.len() > values.len()/1`? **Spec**: choose the smaller of sparse-pairs vs RLE at encode time (both ≤ ~2·changed_cells bytes; implement a `GridDiffCodec` in `src/server/grid_diff.rs` with a `best(&[u8] prev, &[u8] curr) -> GridDiff` function and full-grid fallback when `changed > total/2` or when `Full` byte-size ≤ `Cells` byte-size). Vision (0/1): bit-pack changed cells into a bitset + `Option` value per cell, or sparse pairs — sparse pairs suffice; 0/1 values go into a parallel `Vec<bool>`.
2. `GameDeltaMessage`: add `border_grid_diff_v2: Option<GridDiff>` and `vision_grid_diff_v2: Option<GridDiff>` (skip-if-none, default). Old field stays `None` for v2 peers; v2 peers keep old field `None` and set v2. `grid_width` semantics unchanged (sent when either diff present).
3. `delta.rs`: in `compute_shared_deltas`, compute the border `GridDiff` once per tick (shared); in `build_delta_inner`, compute vision `GridDiff` per player (vision is per-player already). Store `prev_border: Arc<Vec<u8>>` and `prev_vision` unchanged as the diff baseline (they already are). Update `estimate_delta_size`: `v2 present → changed_cells * 6 + 32` bound.
4. **Splicing**: `SpliceShared::build` gains the border `GridDiff` bytes as the shared entry (border diff is still player-independent → W9 splicing survives intact for borders; vision stays per-player encoded as today).
5. Client (`frontend/src/game/territory.ts`, `game_state.ts`): when `F_GRID_RLE` negotiated, apply `Cells` to a local grid copy instead of replacing; on `RequestResync`/`FullState` rebuild from full grids. Vitest: `apply_grid_diff_cells` round-trip equals full-grid replace for random changes; stress case >50% change → server sends `Full` variant, client handles both.
6. Benchmark: `run_network_phase` must produce the v2 diff when `--bench-grid-rle` is set (new flag on `BenchmarkConfig`, forwarded in `main.rs` arg parsing next to `--bench-splice`); `net_wire_bytes` then reflects real bytes. Add `net_grid_bytes: u64` (grid-diff share of `net_wire_bytes`, per-tick) to `TickData` so grid vs entity share is visible in the HTML.

**Protocol changes & compat.** Additive field + feature bit; legacy peers keep whole-grid `border_grid_diff`/`vision_grid_diff` exactly as today (the legacy `SharedDeltas` path stays alive only while ≥1 legacy peer exists — server keeps computing both variants when a mixed lobby exists, which costs the diff computation once, not per player).

**Metrics & verification.** `./run-stresstest.sh wp4-rle --bench-grid-rle` vs `./run-stresstest.sh wp4-base` (no flag) A/B via `--bench-prev`: expect grid-dirty tick bytes −50…95%; overall `net_wire_bytes` ≥ 40% lower (grids dominate at 1000×1000 per baseline). `max_alloc` on grid-dirty ticks drops from ~1 MB. `net_ms`/`net_delta_ms` neutral-or-better (diff scan is O(cells) = O(40 KB–1 MB) memcmp — measure! If the O(n) scan dominates, that's the finding for WP7/WP8).

**Risks & rollback.** Diff-scan CPU (1 MB memcmp per player on vision at 1000×1000 — vision scan is per-player!) → mitigate: only scan when the grid `Arc` changed since the player's baseline (existing `Arc::ptr_eq` guard), and cap: if scan shows >50% change, fall back to `Full` (already spec'd). Client desync → `RequestResync` safety net + full-grid fallback. Rollback: `--bench-grid-rle` off + feature bit off = today's behavior byte-identical (the legacy path is left in place, not deleted — delete only after one release of A/B data).

**Est. effort.** 3 days server (codec + delta integration + tests), 2 days client + vitest.

**Definition of done.** Stress A/B: `net_wire_bytes` ≥ 40% lower, `net_grid_bytes` on grid-dirty ticks ≥ 90% lower vs `Full` variant, zero desync in a 30-min e2e game with forced vision churn (new `--bench-vision-churn` benchmark flag forcing vision-grid changes every tick), `alloc_invariants` (dhat) suite green.

### WP5 — Entity ID & enum compression (v2 entity wire format)

**Goal.** `UnitState`/`UnitUpdate`/`CityUpdate` carry `String` ids, `String` owner, `String` unit_type, `String` symbol, `f32` positions, `Vec<(f32,f32)>` paths (protocol.rs). Replace with indices + fixed points for 3–6× smaller entity payloads.

**Current behavior.** Estimator assumes ~400 B/added unit, ~200 B/update, ~80 B/city (protocol.rs:412–424) — strings dominate. Baseline commit rebuilds `HashMap<String, UnitState>` per tick (the live per-tick commit is in `run_network_phase`, delta.rs:750-759; the replay path has an analogous commit at game_server.rs:1402-1410).

**Changes.**
1. `protocol.rs` (negotiated `F_COMPACT_ENTITIES`):
   - `UnitStateV2 { unit_idx: u32, owner_idx: u8, type_idx: u8, pos: [u16; 2] (fixed-point, 1/64 tile), men: u16, max_men: u16, organisation: u8, equipment: Vec<(u8, u16)>, max_equipment: Vec<(u8, u16)>, path: Vec<[u16; 2]>, flags: u16 (healing/resupply/encircled/attacking/on_water/embarking/disembarking), supply_percent: u8, boat_supply_percent: u8 }` — drop `symbol` (derive from type_idx client-side; `LobbySettings::custom_unit_types` + `unit_types` config already give the symbol table), drop `id`/`owner` strings (indices).
   - `UnitUpdateV2 { unit_idx: u32, position: Option<[u16; 2]>, men: Option<u16>, organisation: Option<u8>, …flags diff as two-bitmask u16 (set, clear) }` — bitmask diff replaces 11 `Option<bool>` fields.
   - `CityStateV2 { city_idx: u32, pos: [u16; 2], owner_idx: Option<u8>, manpower: u32, level: u32 }`, `CityUpdateV2` analogous.
   - `FullStateV2` / `DeltaStateV2` variants: `FullStateV2(GameStateMessageV2)` adds the **registry** to full state: `units: Vec<UnitStateV2>`, `unit_names: Vec<String>` (idx→name, so the UI can still label units; sent once, not per frame), `cities: Vec<CityStateV2>`, `city_names: Vec<String>`, `players: Vec<String>` (owner table, ≤16), `unit_types: Vec<u8 symbol idx>` — terrain stays `Vec<Vec<String>>` (static per game; compressing terrain is a separate small win, do it: `terrain: Vec<u8>` + `terrain_types: Vec<String>` registry — same pattern, ~10 lines).
2. **Index allocation with generation**: `GameRoom`/`NetworkBaselines` gains `unit_index_map: HashMap<String, u32>` where `u32 = (generation << 24) | slot` (16 M units > any game; slot reused on death, generation incremented → no reuse ambiguity, per research #2). Owner idx = stable per-game player order (lobby join order, ≤16 → u8). Type idx = order of `unit_types` in settings.
3. `delta.rs`: `SharedDeltas` gains v2 parallel fields built alongside v1 when `features` includes the bit (single conversion pass over the existing `UnitState` snapshot — conversion is `O(updates)` integer work, no new game-state reads). `NetworkBaselines::prev_units` stays `HashMap<String, UnitState>` (digest/quantization logic at delta.rs:30–100 untouched — compression is purely at the encode boundary; this keeps the quantization A/B history comparable).
4. `estimate_delta_size`: v2 → `units_added*48 + updates*24 + cities*12` (measure-tune post-landing).
5. Splicing: v2 shared segments (`units_added..city_updates` v2) splice exactly like today (`SpliceShared::build` gains a v2 branch) — byte splicing is format-agnostic, W9 survives.
6. Client: `frontend/src/game/units.ts` + `game_state.ts` maintain idx→name registry from `FullStateV2`; decode v2; vitest round-trips against v1 decode (property test: same game, v1 and v2 paths produce identical rendered state).

**Protocol changes & compat.** New `ServerMessage::FullStateV2/DeltaStateV2` variants sent only to `F_COMPACT_ENTITIES` peers. Mixed lobbies: server emits v1 to legacy peers and v2 to new peers — two shared-segment pre-encodes per tick (the v1 `SharedDeltas` already exists; v2 adds one more `SpliceShared` build — cost measured in `net_encode_ms`).

**Metrics & verification.** `./run-stresstest.sh wp5 --bench-compact-entities` vs `wp5-base` A/B: expect entity share of `net_wire_bytes` (new `net_entity_bytes` metric — add alongside `net_grid_bytes`) 3–6× lower; `net_encode_ms` lower (fewer bytes, same encoder); `net_delta_ms` slightly up (conversion pass) — net `net_ms` must be non-increasing.

**Risks & rollback.** Fixed-point position rounding (1/64 tile) visible in fast movement — mitigate: path is sent as the same fixed-point sequence, client lerps; A/B a 1/256 resolution if the jitter is reported. Registry desync (server/client index mismatch after a missed frame) → `RequestResync` rebuilds the registry wholesale (that's the design's safety net; document it in the client). Rollback: feature bit off.

**Est. effort.** 4 days server, 2.5 days client.

**Definition of done.** Stress A/B: `net_entity_bytes` ≥ 3× lower, `net_wire_bytes` ≥ 25% lower, `net_encode_ms` ≤ baseline, property test (v1≡v2 state equivalence) green across 1000 seeded ticks, e2e 30-min game with zero desyncs.

### WP6 — Interest management: per-player entity filtering (AoI-lite)

**Goal.** Every player currently receives identical shared `units_added/unit_updates/city_updates` (delta.rs `SharedDeltas`; research #1: "vision only gates grids"). Deliver each player only the entities in their vision, with enter/leave events.

**Current behavior.** `run_network_phase` builds one shared entity delta per tick (`compute_shared_deltas`, delta.rs:213) and hands the same `Arc<Vec<UnitUpdate>>` to every `build_delta_inner` call (line 443). Per-player vision grid is available at that point (`game.vision_grid_flat(pid)`, delta.rs:678) but used only for the vision diff.

**Changes.**
1. `delta.rs`: new `compute_entity_visibility(current_units, vision_grids_per_player, prev_visible: HashMap<pid, HashSet<u32 unit_idx>>, grid_width) -> per-player: { visible_updates, visible_added, visible_removed(leave) }`. A unit is visible to pid when its (x,y) cell is 1 in pid's vision grid (O(units × 1) with flat grid indexing). Maintain per-player `prev_visible` in `NetworkBaselines` (new field, keyed by the WP5 `unit_idx` — **WP6 hard-depends on WP5**; filtering by String ids would re-introduce the per-tick allocation this plan is removing).
2. Wire (negotiated `F_AOI`, implies `F_COMPACT_ENTITIES`): `DeltaStateV2` entity fields become per-player: `units_added: Vec<UnitStateV2>`, `units_removed: Vec<u32>` (leaves the player's interest set — not necessarily dead), `unit_updates: Vec<UnitUpdateV2>`, plus `unit_leaves: Vec<u32>` (left vision but alive) so the client can hide, not delete. `CityUpdateV2` filtered by city cell visibility the same way.
3. **W9 splice breaks** (per-player content diverges): redesign to *shared prefix + per-player suffix* — splice layout becomes `[map header] [vision?] [border?] [width?] [player]` shared/partial + per-player entity segment encoded per player (the byte-pinning test in `protocol.rs` gets a v2 counterpart pinning the new layout; keep the v1 splice path byte-identical for legacy peers). Expected: encode cost returns toward per-player serialization of the entity segment — measured by `net_encode_ms` in A/B; if the loss is > the bandwidth gain in the 4-player benchmark, ship AoI anyway (bandwidth is the primary axis) but record the tradeoff in the report.
4. Client: `units.ts` maintains `known_units` — `unit_leaves` hides the unit (fades out), re-entering (same `unit_idx`, seen in `unit_updates`) re-shows it; `RequestResync` resets the interest set.
5. Spectators: `spectator_vision` union grid already gives one vision grid (game_server.rs W5 path) — AoI applies to them with the union set.

**Protocol changes & compat.** `F_AOI` negotiated via WP3; legacy peers keep the shared-everything path (left in place). Mixed lobby costs: shared v1 delta + per-player v2 AoI deltas coexist.

**Metrics & verification.** `./run-stresstest.sh wp6 --bench-aoi` (new flag: benchmark gives each of the `BENCH_PLAYERS` real vision grids from the game and enables per-player filtering) vs `wp6-base`: `net_entity_bytes` should drop by roughly (1 − mean_vision_fraction) — expect 50–90% on the 1000×1000 front-line layout where most units are outside a given player's vision. `net_delta_ms` up (per-player filtering O(P×units)) — **must** stay within budget: if `net_delta_ms` increases > 2×, implement the fast path: units whose (x,y) didn't move this tick and were visible last tick stay visible without rescan (track moved-set from `unit_updates`), re-scan only moved units + border changes.

**Risks & rollback.** Highest-risk package: subtle desyncs (unit visible in updates but missed `added`), CPU blowup at 10k units × 4+ players, splice test churn. Mitigations: `RequestResync` net, the moved-set fast path, A/B before enabling by default (flag `aoi_default: false` in server config, flip after a release of data — matches the delta.rs A/B convention). Rollback: feature bit off → shared-everything path.

**Est. effort.** 4–5 days server (incl. fast path), 1.5 days client.

**Definition of done.** Stress A/B: `net_entity_bytes` ≥ 50% lower, `net_delta_ms` ≤ 2× baseline, `net_wire_bytes` total ≥ 50% lower vs pre-WP6, 30-min e2e with two players: no ghost units, no missing visible units (add a dev-mode client consistency assert behind a query param).

### WP7 — Reusable encode buffers (+ postcard evaluation for v2)

**Goal.** Cut `net_encode_ms` and encode allocs: per-player CBOR encode serializes into a fresh `Vec<u8>` every frame (protocol.rs:389–410), and ciborium's writer allocates internally.

**Current behavior.** `encode_message_with_hint` pre-sizes a `Vec` (N5) but still allocates per call; W9 splicing already avoids P× re-serialization of shared segments, so the remaining per-player encode is: map header + vision entry + `grid_width` + player + (v2: entity segment) — still a fresh allocation per player per tick. `SpliceShared::build`/`encode_entry` allocate fresh `Vec`s for shared segments each tick (protocol.rs W9 section) — these are size-stable per game, so they are prime reuse candidates.

**Changes.**
1. Scratch buffers: `NetworkBaselines` (or a new `EncodeScratch` owned by the room loop) holds `BytesMut` per player and for the shared segments, grown-not-shrunk, fed via a `&mut impl io::Write` ciborium writer (`ciborium::into_writer` accepts any `Write` — point it at the scratch slice). `encode_delta_spliced` / v2 equivalents append into scratch, hand out `Bytes` (`freeze`/`copy_to_bytes` — copy is 1×, allocation is 0). Guard: buffer is per-player-task local, no sharing (the tick loop is single-task — safe).
2. **Codec evaluation** (bounded, decided by data): add a postcard-encoding path for `DeltaStateV2` behind `F_POSTCARD` + `--bench-postcard` flag; A/B vs ciborium on the v2 structs (postcard: fixed-size, no tag overhead, no dynamic allocations in the writer). Land postcard **only** if the A/B shows ≥ 30% encode-time or ≥ 25% byte win on the stress profile; otherwise record the negative result in `reports/` (the delta.rs convention asks for the evidence either way). No flatbuffers/sonic (complexity not justified at ≤16 peers, per research #5).
3. Remove now-duplicate full `Vec<u8>` paths: after WP1, everything flows as `Bytes`; `encode_message` stays for legacy/lobby/error frames.

**Protocol changes & compat.** Postcard, if landed, is feature-negotiated (`F_POSTCARD`); CBOR remains the default and the legacy format. Otherwise no protocol change at all.

**Metrics & verification.** `./run-stresstest.sh wp7` A/B: `net_encode_ms` ≥ 30% lower (scratch reuse alone expected ~10–20% on the v1 path, more on v2 entity segments); per-tick `allocs` down by roughly (players + 2 shared) allocations per tick; postcard A/B decision documented with numbers.

**Risks & rollback.** Low: buffers are task-local and only change allocation timing, not bytes (v1 output must remain byte-identical — the W9 byte-pin test stays green; add an explicit "scratch reuse does not change bytes" test). Postcard risk isolated behind its own bit. Rollback: per-item revert.

**Est. effort.** 2 days (buffers + tests), 1 day (postcard A/B, decision either way).

**Definition of done.** Stress A/B: `net_encode_ms` ≥ 30% lower, byte-pin + byte-identity tests green, postcard decision memo in `reports/wp7_codec_decision.md`.

### WP8 — Wire-tick decoupling (server-side emit gating)

**Goal.** The network phase runs every sim tick even when quantization has already reduced deltas to trivial (delta.rs quantization exists, but a tick with one quantized `men` bump still emits a frame to affected players). Gate emission and let clients interpolate.

**Current behavior.** Idle-skip exists (no message on fully idle ticks), but any sub-threshold-tripped field emits immediately; `game_speed` up to 10 Hz (validation at game_server.rs:2718) means up to 10 network phases/sec/tick.

**Changes.**
1. `delta.rs`: extend idle-skip into **per-field emit deferral**: `NetworkBaselines` gains `pending: per-player, per-unit small diff accumulator` — when a field change is below an "urgent" threshold (new: urgent = encircled/attacking/removed/position-jump > 1 tile; non-urgent = men/org/supply micro-bumps) and a frame was emitted to that player < `emit_gap` ticks ago (default `emit_gap = ceil(10 / max(game_speed, 10)) * …` → **concretely**: non-urgent changes are deferred until the next tick that is ≥ 10 ticks of wall-clock 100 ms old… simpler fixed rule: non-urgent deferral window = 10 sim ticks), they accumulate and ride the next urgent frame. Forced flush: every 100 ms wall-clock (tracked via `tokio::time::Instant` in the room loop) or on any urgent change or vision/border grid change (grids stay immediate — they're already RLE-cheap after WP4).
2. `FullState`/delta carry `tick: u32` (add `#[serde(skip_serializing_if)]`-free plain field in v2 only; legacy untouched) so the client can measure staleness; client (`game_state.ts`): lerp unit positions between the last two received `UnitUpdateV2`/`FullStateV2` snapshots using tick numbers, clamped to 200 ms extrapolation; grid renders last-received (fine — grid changes are infrequent and cheap).
3. Benchmark: `--bench-defer` flag; `TickData.net_frames_sent` (existing `deltas_sent` in `NetworkPhaseResult` suffices) + new `net_deferred_ticks: u64`.

**Protocol changes & compat.** v2-only, feature bit `F_DEFER` (bit 32? no — extend `F_POSTCARD=16`, add `F_DEFER=32`). Legacy peers keep immediate emission (the deferral is applied per-peer: a player with any legacy peer is the only constraint — deferral is per-player state, so mixed lobbies are fine: legacy peer gets immediate frames, v2 peer gets deferred frames; baselines diverge per peer, which `NetworkBaselines` already supports via per-pid keys).

**Metrics & verification.** `./run-stresstest.sh wp8 --bench-defer` A/B: network phase cost per *emitted* frame unchanged, but emitted frames/tick drops (target: `deltas_sent`/tick ≥ 40% lower on the 10 Hz config); CPU: total `net_ms`/sec ≥ 40% lower (add `net_ms_per_sec` to the HTML summary since per-tick metrics undercount this win when frames are skipped). Client lag test: vitest with simulated 100 ms-stale frames → interpolated position error < 1 tile.

**Risks & rollback.** Latency to urgent events (must stay 1 tick — the urgent set is spec'd explicitly); baseline drift bugs (deferral accumulator desyncs from quantization) — mitigate with a unit test that replays a seeded field-value sequence and asserts deferred output ≡ immediate output modulo timing. Rollback: `--bench-defer` off / bit off.

**Est. effort.** 2.5 days server, 1.5 days client.

**Definition of done.** Stress A/B at 10 Hz config: `net_ms_per_sec` ≥ 40% lower, urgent-event delivery latency = 1 tick (unit test), 30-min e2e: no visible rubber-banding at 10 Hz game speed.

## Sequencing & Dependencies

```
WP1 (transport) ─┐
WP2 (lobby/log) ─┼─ independent, parallel, all before/at WP3
WP3 (handshake) ─┴─ gates WP4, WP5, WP6, WP8 (feature bits)
WP4 (grid RLE) ── depends: WP3. Independent of WP5.
WP5 (compact entities) ─ depends: WP3. GATES WP6 (unit_idx).
WP6 (AoI) ─ depends: WP3 + WP5.
WP7 (encode buffers/postcard) ─ depends: WP1 (Bytes); best after WP5/WP6 (buffers the final frame shapes).
WP8 (defer) ─ depends: WP3 + WP5 (tick field, per-player baselines); pairs with WP4 (grids stay immediate).
```

Critical path: **WP3 → WP5 → WP6 → WP7 → WP8**. WP1/WP2 can land (and be benchmarked) in parallel with WP3's development. WP4 slots in right after WP3, in parallel with WP5 (different files: `grid_diff.rs`/territory client vs protocol entity structs/units client — one shared file `protocol.rs`, merge-sequential to avoid churn).

Cumulative expectation (stress profile, 10k units / 1000×1000, `--bench-splice`): after WP1+WP2 ≈ allocs −20%; after WP3 ≈ wire-neutral; after WP4 ≈ wire −40%; after WP5 ≈ wire −65%, encode ↓; after WP6 ≈ wire −80%, `net_delta_ms` +fast-path-bounded; after WP7 ≈ encode −30%; after WP8 ≈ network CPU/sec −40%.
