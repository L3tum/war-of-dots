# Deep Plan: Persist TickContext Over Multiple Ticks

## Problem Statement

`TickContext::build()` is called every tick in `Game::tick_game()`, performing a full ECS query over all living units and rebuilding two HashMaps (`units_by_player` and `owner_id_by_entity`) plus cloning small data (cities ~20 entries, funds ~12 entries). This work is repeated even when nothing changed, and critically, the context is built **before** movement runs, meaning consuming systems receive stale position data.

At game scale (500+ units), the per-tick ECS archetype traversal `world.query::<(Entity, &UnitOwner, &UnitPosition)>().iter()` dominates `build()`'s cost. Persisting TickContext and only updating fields that changed would eliminate redundant work on ticks where no structural changes occurred.

## Context

### Current Architecture

**File:** `src/game/game.rs`

**TickContext struct** (line ~162):
```rust
pub struct TickContext {

    pub cities: Vec<City>,
    pub funds: HashMap<String, u32>,
```

**`TickContext::build()`** (line ~180): single-pass construction
1. Scoped Arc extraction: clones `cities` and `funds`, reads `width`/`height`
2. `world.query::<(Entity, &UnitOwner, &UnitPosition)>().iter()` — iterates ALL units
3. Builds `units_by_player` (grouped by player ID string) and `owner_id_by_entity` (Entity→u8) simultaneously

**`tick_game()` execution order** (line ~392):
```
1. ctx = TickContext::build()       ← BEFORE everything
2. economy (every ECONOMY_TICK_INTERVAL ticks; currently = 1, so every tick)
3. water
4. movement                         ← positions change here
5. nearby_enemies (uses ctx.owner_id_by_entity, NOT ctx.units_by_player)
6. combat (uses ctx.owner_id_by_entity, NOT ctx.units_by_player)
7. supply (MODIFIES funds and manpower!)
8. city_capture (MODIFIES city ownership!)
9. influence (every 3rd tick, uses ctx.units_by_player and ctx.cities)
10. encirclement (every 30th tick, uses ctx.units_by_player and ctx.cities)
11. surrender (every 30 ticks)
12. death_cleanup
```

### Field Change Frequencies

| Field | Changes | When | Changed by |
|---|---|---|---|
| `world_entity` | Never | Set at `Game::new` | — |
| `width` | Never | Derived from map | — |
| `height` | Never | Derived from map | — |
| `cities` | Rarely | Only during `city_capture` (ownership changes) | `city_capture::run` |
| `funds` | **Every tick** (economy) + **every tick** (supply) | `economy::run` adds; `supply::run` subtracts | economy + supply |
| `units_by_player` | **Every tick** | Movement changes positions; spawns/deaths add/remove entities | movement, recruit, death_cleanup |
| `owner_id_by_entity` | Sporadically | Only when entities spawn or die | `recruit_unit` (between ticks), `death_cleanup` |

### Consuming Systems and Their Actual Usage

**`nearby_enemies::run`** (every tick):
- Uses `ctx.owner_id_by_entity.get(&e)` for O(1) owner filtering
- **Does NOT use** `ctx.units_by_player` — queries positions fresh from ECS

**`combat::run`** (every tick):
- Uses `ctx.owner_id_by_entity.get(&e)` for candidate filtering and same-owner checks
- **Does NOT use** `ctx.units_by_player` — queries positions fresh from ECS

**`influence::run`** (every 3rd tick):
- Uses `ctx.units_by_player` to iterate positions per player for grid computation
- Uses `ctx.cities` for city influence projection (filters by `c.owner`)
- **Does NOT use** `owner_id_by_entity`

**`encirclement::run`** (every 30th tick):
- Uses `ctx.units_by_player` for position-based encirclement flagging
- Uses `ctx.cities` for safe-anchor seeding (filters by `c.owner`)
- **Does NOT use** `owner_id_by_entity`

### Current Bugs Identified

1. **Stale Positions in influence/encirclement:** `ctx` is built before movement, so `units_by_player` contains stale positions when influence (step 9) and encirclement (step 10) consume it. Both systems use these stale positions to compute grid influence and encirclement flags.

2. **Non-deterministic Player Indices:** `owner_id_by_entity` assigns u8 indices in ECS iteration order (`player_id_to_index` HashMap insertion order), which is non-deterministic across ticks. If the map is persisted, player index 0 on tick N might become index 2 on tick N+1, causing silent correctness bugs in owner comparisons.

3. **`ctx.funds` is Stale for Its Only Consumer:** The only consumer of `ctx.funds` is the economy block in `tick_game()`, which reads it before supply runs. This means `ctx.funds` already contains pre-economy funds — it's inherently stale.

## Design

### Recommended Approach: Incremental TickContext with Split Update Points

Three lightweight update points instead of one monolithic `update()`:

1. **Start of tick:** Update `owner_id_by_entity` if entities changed (recruit/death between ticks)
2. **After movement:** Rebuild `units_by_player` (positions changed — always needed every tick)
3. **Before influence/encirclement:** Clone `cities` if ownership changed (lazy, rare)

### Key Design Decisions

1. **Remove `funds` from TickContext:** No consuming system needs it. The economy block can read directly from the world. This simplifies dirty tracking.

2. **`TickContext` stored directly on Game (not `Option`):** `build_initial()` is infallible in practice (world_entity is always valid). Avoids `unwrap()` in hot paths.

3. **Deterministic player index assignment:** Sort player IDs before assigning u8 indices. O(p log p) where p ≤ 8 players — negligible cost, only runs when entities change.

4. **Always rebuild `units_by_player` every tick:** Positions change every tick, and influence/encirclement depend on fresh positions. The optimization is NOT about skipping this — it's about skipping `owner_id_by_entity` on most ticks.

### Deterministic Player Index Assignment

```rust
fn rebuild_owner_id_by_entity(world: &World, map: &mut HashMap<Entity, u8>) {
    map.clear(); // Preserve capacity
    let mut player_id_to_index: HashMap<String, u8> = HashMap::new();
    
    // First pass: collect all player IDs, sort them for deterministic index assignment
    let mut player_ids: Vec<String> = world
        .query::<&UnitOwner>()
        .iter()
        .map(|owner| owner.player_id.clone())
        .collect();
    player_ids.sort();
    player_ids.dedup();
    
    for (idx, pid) in player_ids.iter().enumerate() {
        player_id_to_index.insert(pid.clone(), idx as u8);
    }
    
    // Second pass: assign owner IDs based on sorted indices
    for (entity, owner) in world.query::<(Entity, &UnitOwner)>().iter() {
        let id = *player_id_to_index.get(&owner.player_id).unwrap();
        map.insert(entity, id);
    }
}
```

### Tick Loop Changes

```rust
pub fn tick_game(&mut self) {
    if !self.running { return; }
    self.tick += 1;
    
    // 1. Start of tick: update owner map if entities changed
    if self.ctx_dirty.entities_changed {
        self.ctx.update_owner_map(&self.world);
    }
    self.ctx_dirty = TickContextDirty::default();
    
    // 2. economy (reads funds directly from world)
    if self.tick.is_multiple_of(ECONOMY_TICK_INTERVAL) {
        // ... economy run ...
        // ... read funds from world directly for player update ...
    }
    
    // 3. water
    // 4. movement
    let mover_count = systems::movement::run(...);
    
    // ── AFTER movement: always rebuild units_by_player ──
    self.ctx.update_units_by_player(&self.world);
    
    // 5. nearby_enemies (uses ctx.owner_id_by_entity)
    // 6. combat (uses ctx.owner_id_by_entity)
    // 7. supply
    // 8. city_capture
    let changed_cities = systems::city_capture::run(...);
    if !changed_cities.is_empty() {
        self.ctx_dirty.cities_changed = true;
    }
    
    // 9. influence (every 3rd tick)
    if self.tick.is_multiple_of(INFLUENCE_TICK_INTERVAL) {
        if self.ctx_dirty.cities_changed {
            self.ctx.update_cities(&self.world, self.world_entity);
            self.ctx_dirty.cities_changed = false;
        }
        systems::influence::run(&mut self.world, &self.ctx, self.tick);
    }
    
    // 10. encirclement (every 30th tick)
    if self.tick.is_multiple_of(CITY_CAPTURE_TICK_INTERVAL) {
        if self.ctx_dirty.cities_changed {
            self.ctx.update_cities(&self.world, self.world_entity);
            self.ctx_dirty.cities_changed = false;
        }
        systems::encirclement::run(&mut self.world, &self.ctx, self.tick);
    }
    
    // 11. surrender
    // 12. death_cleanup
    let death_count = systems::death_cleanup::run(...);
    if death_count > 0 {
        self.ctx_dirty.entities_changed = true;
    }
}
```

### Entity Change Detection

- **`recruit_unit()`:** Called from command channel between ticks. Sets `self.ctx_dirty.entities_changed = true` so the next tick's start-of-tick update rebuilds `owner_id_by_entity`.
- **`death_cleanup::run()`:** Returns the count of dead entities cleaned up. `tick_game()` sets `entities_changed = true` if count > 0.

### city_capture Changes

`city_capture::run()` currently returns `()`. Change to return `Vec<String>` of city IDs whose ownership changed. The `BTreeMap<String, String>` of `city_ids_changed` already exists in the implementation — extract it into a return value.

## Risk Assessment

### Risk 1: Deterministic player index assignment adds overhead
**Impact:** Low. Only runs when entities change (recruit/death), not every tick. O(p log p) for p ≤ 8 players is negligible.

### Risk 2: city_capture doesn't currently track which cities changed
**Impact:** Low. The `BTreeMap<String, String>` of `city_ids_changed` already exists in `city_capture::run()`. Extract into a return value.

### Risk 3: Tests build TickContext at the wrong time
**Impact:** Medium. ~20 test sites need updating. Use `build_initial()` + `update_units_by_player()` after spawning units.

### Risk 4: Modest performance gain — `units_by_player` still rebuilt every tick
**Impact:** Low. Correct assessment. The main optimization is `owner_id_by_entity` persistence. Real wins are: (a) skipping owner map rebuild on most ticks, (b) removing funds clone, (c) fixing stale position correctness bug.

### Risk 5: Lazy city update could miss if influence/encirclement skip this tick
**Impact:** Low. `cities_changed` dirty flag persists across ticks. If influence/encirclement skip tick N but run on tick N+3, cities are updated right before that tick's influence/encirclement.

### Risk 6: Borrow checker complications with `self.ctx`
**Impact:** Low. Access `self.ctx` via local reference pattern: `let ctx = &self.ctx;` which borrows `self.ctx` (immutable) while `self.world` is mutable — they're disjoint fields of `self`, so Rust allows this.

## Performance Assessment

The actual savings are modest but measurable:

| Savings | Amount |
|---|---|
| `owner_id_by_entity` not rebuilt on ticks with no entity changes | ~2-3 µs/tick (O(n) ECS query + HashMap rebuild) |
| `funds` removed from TickContext | ~0.3 µs/tick (HashMap clone of ~12 entries) |
| `cities` only cloned when changed | ~0.5 µs on non-city-capture ticks (rarely matters) |
| **Total per typical tick** | **~2-3 µs** |

The more important fix is **correctness**: stale positions in influence/encirclement and non-deterministic player indices. These bugs exist today and this plan fixes them as a natural consequence of the persistence architecture.
