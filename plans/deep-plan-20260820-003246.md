# Deep Plan: Unit occupancy — at most one unit per cell

*Follow-on to plans/deep-plan-20260819-000146.md (the reverse-lookup death_cleanup plan — shipped,
and now **kept as-is** per user: the upcoming conditional `nearby_enemies` rebuild makes the purge
load-bearing). User-locked decisions: occupancy **yes** (cell 1.0); recruiting only on a **free
city dot** — the previous unit must move away before the next recruit; benchmarks/premade
scenarios **bypass** occupancy and spawn at set positions; death_cleanup **unchanged**; large-list
microbench coverage **kept**.*

## Context — what the measurement actually showed

The stress_6 run kept `death_cleanup` at **21 010 ms / 12.359 ms avg** (vs 10 905 ms pre-change)
even after the reverse-lookup rewrite. So the rewrite made things **worse, not better**, and a
second "fix" (single-query pass) did not move it. Rather than keep guessing, I built a faithful
phase-level micro-harness (`cargo test --release --features microbenchmarks dc_phase_measurement`):
10 000-unit world, a 3 000-unit dense cluster with **~1 000-entry enemy lists** (matching the
benchmark's real `total_nearby_entries / with-enemies ≈ 588 146 / 577 ≈ 1 019`), and it times each
phase of `death_cleanup` separately against the **original flat retain**:

```
dead     flat_retain(old)   reverse_lookup   query+retain   new(reverse+retain)
100            22 µs              4.6 µs          26.1 µs           31 µs  (1.4x)
1000           44 µs              9.0 µs          51.6 µs           61 µs  (1.4x)
2000           84 µs             18.2 µs         102.5 µs          120 µs  (1.4x)
```

**Finding 1 — the reverse lookup is ~1.4× *slower* than the flat retain in dense spikes.** The
"targeted" idea assumed the dead units' neighborhoods are small. In a dense symmetric cluster they
are *huge* (each dead unit lists ~1 000 enemies), so step 2 reads ~`dead × 1000` entries, and step 3
still scans every candidate's list (a second full pass over the dense cluster). It only wins when
dead units sit in sparse terrain — which are the cheap ticks anyway. The spikes that dominate the
total are exactly the case where it loses.

**Finding 2 — the real cost driver is list *density*, not the cleanup algorithm.** The benchmark
converges units to one point (moves 30 % of units to the map centre every 20 ticks) and
`recruit_unit` spawns every unit at the *same* `city_pos`. That builds a cluster where 577 units
hold ~1 019-entry lists. **Both** top systems are O(total entries):
- `nearby_enemies` full rebuild: writes all ~588k entries/tick → **4.3 ms/tick (7 751 ms total)**.
- `death_cleanup` purge: scans all ~588k entries on death ticks → **12.3 ms/tick (21 010 ms total)**.

Optimizing the cleanup algorithm is the wrong level. Bounding units-per-cell at the source bounds
every list, which fixes both systems at once. That is Rework 1.

**Finding 3 — the `NearbyEnemies` purge is redundant.** `nearby_enemies` does an **unconditional
full rebuild every tick** (only an empty-world early return) and runs *before* `combat`, building
every list from the grid of **currently living** units. So any reference to a unit that died is
overwritten by the next tick's rebuild. The only readers of `NearbyEnemies` are:
- `combat` (runs *after* the rebuild → always sees fresh lists; and it tolerates a stale ref
  anyway — `world.get::<&UnitPosition>(entity2)` → `Err` → `continue`, combat.rs:274-297), and
- `combat_health()` (diagnostic; only counts `nearby.entities.len()`, never derefs entities).

So *under the current per-tick full rebuild* the purge has zero gameplay effect. **User decision
(locked): keep the purge as-is.** The next `nearby_enemies` rework switches to a **conditional
rebuild** — after which a dead unit's stale references are *not* wiped by any rebuild, so the
death_cleanup purge becomes load-bearing, and its fresh-lists invariant (documented in the module
doc) is precisely the contract that rebuild must uphold. The 1.4× dense-spike overhead measured
above is moot once occupancy bounds lists (death spikes become µs-scale). `death_cleanup` is
therefore **out of scope for this plan**.

## The rework — unit occupancy: at most one unit per cell

### Goal
Bound units per cell so every `NearbyEnemies` list is O(constant) instead of O(cluster size).
Kills the O(588k) cost in `nearby_enemies` and `death_cleanup` simultaneously.

### Verified structural facts (from code audit)
- `UnitPosition` is written by exactly **one** code path outside spawn: the movement apply phase
  (movement.rs:130). `water.rs` only toggles `on_water`/timers. → One enforcement point in
  movement covers every position change.
- City dots are plain `Economy.cities` data with coordinates — **not ECS units** — so a city never
  occupies a cell. "One unit per city cell" means: a *previous recruit still sitting on the city*
  is the only thing that blocks the next one.
- `WorldExt::spawn_unit(unit_type, owner, city_pos)` already spawns at an explicit position — no
  world_ext change needed for a bypass path.
- No existing test recruits >1 unit per city in one game (audited: game.rs tests, 
  tests/integration_game.rs) — the new recruit gate breaks none of them. The **benchmark** is the
  only consumer that stacks (10 000 units via `recruit_unit`), so it moves to the bypass path.

### 1. Constant — `src/game/constants.rs`
```rust
/// Cell side for the one-unit-per-cell occupancy rule. MUST stay < COMBAT_RANGE (2.0): at 2.0,
/// edge-adjacent units are 2.0 apart and the strict `dist² < COMBAT_RANGE_SQ` check excludes
/// them, silently breaking combat. 1.0 keeps edge-adjacent units 1.0 apart (in range) and
/// bounds a unit's 3×3 occupancy neighbourhood to 9 cells → ~9–13-entry enemy lists.
pub const OCCUPATION_CELL_SIZE: f32 = 1.0;
```
Guarded by a const-safety unit test (`OCCUPATION_CELL_SIZE < COMBAT_RANGE_SQ.sqrt()`), not a
per-tick assert.

### 2. Occupancy core — new `src/game/occupancy.rs`
```rust
pub fn cell_of(pos: UnitPosition) -> (i32, i32)          // (floor(x/S), floor(y/S))
pub fn cell_key(cx: i32, cy: i32) -> u64                 // packed key, no alloc
pub fn build_counts(world: &World) -> HashMap<u64, u32>  // per-cell resident count, all units
pub fn cell_occupied(counts: &HashMap<u64, u32>, pos: UnitPosition) -> bool
```
- Pure, unit-testable. `build_counts` queries `(Entity, &UnitPosition)` — O(n) hash inserts
  (µs-scale for 10k units). Rebuilt fresh per movement tick (no persistent state, no
  death-coupling, deterministic) — far cheaper than the O(588k) work it prevents.
- **Counts, not a resident-entity map:** the benchmark's initial bypass placement legally stacks
  many units per cell; a count lets each unit move *out* (decrement) while still blocking
  move-into (count > 0). A `bool`/`cell→entity` map would be ambiguous under overlap.

### 3. Move enforcement — `src/game/systems/movement.rs` apply phase (~:119-159)
Before the apply loop: `scratch.occupancy = build_counts(world)` (new `MovementScratch` field,
grow-only, `clear()`'d per tick — standard scratch pattern). For each `change.moved` unit, in
`scratch.changes` order (ECS query order = deterministic total order):
1. `target = cell_of(clamped new_pos)`, `from = cell_of(old_pos)`.
2. **Self-exclusion:** a unit moving *within its own cell* (0.1 steps inside a 1.0 cell) is always
   allowed — block only when `count[target] > (1 if target == from else 0)`.
3. **Blocked** → skip the move entirely: no `UnitPosition` write, **no `pop_head`** (the waypoint
   is not consumed — the unit didn't reach it), no `movers` push, no `moved` flag. The unit stays
   at `old_pos` and retries next tick (movement recomputes from the path every tick).
4. **Allowed** → apply as today; then `count[from] -= 1` (drop if 0), `count[target] += 1`.
   Same-tick swaps (A out of X, B into X) resolve first-come in apply order — deterministic
   either way; document it.
- **Documented equilibrium:** units converging on a contested point form a 1-unit-per-cell shell
  and wait at their path head until a cell frees (death/move). Stable, no list growth.

### 4. Recruit gate — `src/game/game.rs`
- `recruit_unit(city_id, unit_type, owner)`: in **Phase 1 validation** (before any funds/manpower
  deduction — an occupied city must not spend resources), add
  `if cell_occupied(&build_counts(&self.world), city_pos) { return None; }`. On-demand O(n) build
  is fine: recruits are event-rate in real play, and the benchmark path bypasses this entirely.
- New **premade/benchmark path** `pub fn recruit_unit_at(&mut self, unit_type: &UnitType, owner:
  &str, pos: UnitPosition) -> Option<String>`: identical funds/manpower checks + deduction and
  identical post-spawn bookkeeping (registry, `entity_reverse`, owner map, stats, staleness
  flags), but **no occupancy check** and an explicit position. Factor the shared tail of
  `recruit_unit` into a private helper both call. Future "premade scenario" loaders (none exist
  in the codebase yet) use this too.

### 5. Benchmark switch — `src/benchmark.rs`
The benchmark **is** a premade scenario: replace its `recruit_unit` calls — initial round-robin
population (:364-395) **and** recruit events every 100 ticks (:170-191) — with
`recruit_unit_at(..., city.position)`. Same funds/manpower semantics (the benchmark seeds both
for this), same layout as today (city-position stacks), occupancy-bypassed, so the 10 000-unit
stress population still fields. Movement events (30 % → centre every 20 ticks, :153-166) are
**unchanged** — they now form a bounded shell instead of a 1000-stack, the new realistic
behavior the stress test exercises. Initial city stacks legally over-occupy cells from tick 1
(bypass) and drain as units get paths and move out — expected warm-up, not a violation.

### Expected impact (the payoff)
- `total_nearby_entries`: 588 146 → **bounded** — engaged units × ~6–12 (lists ≤ ~12 in a 3×3,
  minus same-owner), after the initial-stack warm-up drains. ~20–100× drop.
- `nearby_enemies`: 4.3 ms/tick → scales with entry count (target ≲ 0.2 ms/tick).
- `death_cleanup`: 12.4 ms/tick → scales with entry count (death spikes become µs-scale).
- `combat`: fewer candidate pairs → slightly cheaper.
- **Gameplay changes (by design):** no stacking; convergence forms shells around contested
  points. `units_remaining`, `total_nearby_entries`, `combats/tick`, `movers/tick` all shift vs
  stress_6 — **do not diff gameplay rows against the pre-change report**; stress_8 is the new
  baseline.

## death_cleanup — unchanged (user decision)
Keep the shipped reverse-lookup purge (`dead_set` + `seen` + `candidates`) exactly as-is. Rationale

fresh-lists invariant is the contract that rebuild must uphold. `dc_phase_measurement` is **kept**

independent of the game's occupancy rules.

## Steps
1. **Occupancy core** — `src/game/occupancy.rs` per §2 + unit tests: `cell_of` at cell boundaries
   (including negative coords); `cell_key` round-trip; `build_counts` on a hand-built world
   (2 units same cell → count 2; unit in adjacent cell → count 1); `cell_occupied` true/false;
   const-safety: `OCCUPATION_CELL_SIZE < COMBAT_RANGE_SQ.sqrt()`.
2. **Movement enforcement** — §3 in `movement.rs` + unit tests (the module's existing test helper
   already builds worlds): move into empty cell succeeds (pos written, mover recorded); blocked
   when target cell holds another unit (pos unchanged, **path head NOT popped**, not in
   `movers`, `moved` false); same-cell motion allowed (self-exclusion); same-tick swap A-out/
   B-into resolves deterministically in apply order; blocked unit moves once the occupant
   despawns/moves.
3. **Recruit gate + premade path** — §4 in `game.rs` + tests: first recruit at a city succeeds;
   second (previous unit unmoved) returns `None` **and deducts nothing** (funds + manpower
   unchanged); after the previous unit moves away, the next recruit succeeds; `recruit_unit_at`
   places two units at the same position (bypass), deducts resources, registers id/owner
   identically to `recruit_unit`.
4. **Benchmark switch** — §5; smoke-run a short benchmark to confirm ~10 000 units still field
   ("Recruited N units" log).
5. **Build + full test pass** (see Verification).
6. **Stress benchmark** — fresh occupancy baseline (see Verification).

## Risks & mitigations
- **R1 — gameplay shift (expected, by design).** No stacking; convergence forms shells;
  `units_remaining` etc. change vs stress_6. Mitigation: stress_8 is the *new* baseline; repeat
  run confirms determinism (same seed → identical rows).
- **R2 — blocked-unit stall at path head (expected equilibrium).** A unit waits for its target
  cell to free; deaths/moves free cells. Worst case: 1/tick crawl around a full shell.
  Documented in movement's module doc; stress_8 shows the steady state. Pathological jam →
  small detour logic (out-of-scope follow-up).
- **R3 — same-cell self-exclusion edge (low).** A mover whose `new_pos` stays in its own cell
  must not be blocked by itself (the count map includes the mover until applied). Handled in §3
  step 2; pinned by a dedicated test.
- **R4 — recruit-on-demand O(n) count (negligible).** `build_counts` per `recruit_unit` call is
  O(units) hash inserts; recruits are event-rate (real play) and bypassed (benchmark). No
  per-tick cost on this path.
- **R5 — initial benchmark over-occupied stacks (expected warm-up).** Bypass placement stacks
  ~10 000 units at city positions; tick-1 lists are ~city-stack-size, draining as units get
  paths. Not a violation — premade scenarios are exempt by design.
- **R6 — combat-range vs cell-size coupling (guarded).** Raising `OCCUPATION_CELL_SIZE` ≥ 2.0
  would push edge-adjacent units outside `COMBAT_RANGE_SQ` and silently break combat. Mitigated
  by the const-safety unit test + the documented invariant on the constant.
- **R7 — determinism (low).** All new logic is fixed-order: counts built from ECS query order;
  first-come resolution in `scratch.changes` order; no RNG, no wall-clock. Stress repeat-run
  check in Verification.
- **R8 — out of scope, unchanged:** death_cleanup structure (`seen`/reverse-lookup — kept per
  user decision for the conditional-rebuild contract); the `nearby_enemies` conditional rebuild
  itself (next plan — its TODO already documents that the death_cleanup purge depends on list
  freshness); `owner_id_by_entity`/`entity_registry` unbounded growth; `tick_durations_ms`
  ring.
