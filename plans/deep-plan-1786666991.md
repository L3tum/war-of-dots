# Shared Owner Lookup in TickContext

## Context

Multiple game systems independently perform owner lookups every tick, each with redundant ECS queries, String clones, and per-system deduplication — creating unnecessary CPU and allocation overhead on the hot tick path.

| System | ECS Query for Owner | String Clones | Per-Pair Lookup |
|---|---|---|---|
| `TickContext::build` | `(Entity, &UnitOwner, &UnitPosition)` | 1 × `owner.player_id.clone()` per unit | — |
| `nearby_enemies::run` | `(Entity, &UnitPosition, &UnitOwner, &UnitFlags)` | 1 × clone + builds `HashMap<&str, usize>` + `Vec<usize>` | — |
| `combat::run` | `(Entity, &UnitPosition, &UnitOwner, &UnitFlags, &UnitStats, &NearbyEnemies)` | 1 × clone in candidates | `world.get::<&UnitOwner>(entity2)` + String `==` per pair |
| `city_capture::run` | `(Entity, &UnitOwner, &UnitPosition)` | — | — |

At 500 units across 4 players:
- **4+ separate ECS queries** touch `UnitOwner` (should be 1)
- **~1500 String clones** per tick (should be ~500)
- **Potentially thousands of per-pair `world.get::<&UnitOwner>()` + String comparisons** in dense melees

The `nearby_enemies` system (added in the last commit replacing `spatialty`) maintains its own `owner_ids: Vec<usize>` lookup built from a HashMap dedup each tick. This is redundant with the single-pass `units_by_player` build already done by `TickContext::build()`.

## Approach

Add a `HashMap<Entity, u8>` compact owner lookup table to `TickContext`, built in the **same single-pass ECS query** that already builds `units_by_player`. Downstream systems (`nearby_enemies`, `combat`) read from the shared lookup instead of doing their own `&UnitOwner` query.

### Why `u8`?

- Max players = 255. Game realistically uses ≤ 8 players.
- `u8` comparison is a single-byte integer equality — no pointer chasing, no String hashing.
- `HashMap<Entity, u8>` is compact: ~12 KB at 500 units, dropped after each tick.

### Why remove `&UnitOwner` from ECS queries?

Fewer component tables traversed per iteration in hecs. Combat drops from 6 to 5 components, nearby_enemies from 4 to 3. This reduces per-entity borrow overhead.

## Data Structures

### `TickContext` — new field

**File:** `src/game/game.rs`, struct at line ~161


**Note:** The `player_ids: Vec<String>` reverse lookup was proposed but has no consumer in the current implementation. Systems only do equality comparison (`u8 == u8`), never need to resolve back to a String. Omitted to save memory.

### `CellEntry` — `owner_idx` type change

**File:** `src/game/systems/nearby_enemies.rs`

```rust
#[derive(Clone, Copy)]
struct CellEntry {
    entity: Entity,
    pos: UnitPosition,
    owner_idx: u8, // was: usize
}
```

**Note on struct size:** Rust default layout means `CellEntry` with `(Entity(16), UnitPosition(8), u8)` still pads to 32 bytes (alignment to 8). The benefit is not a size reduction but semantic correctness — `owner_idx` is a compact owner ID, not an array index.

2. Update `TickContext::build()` — the existing single-pass query now also builds the owner map:

```rust
// Single pass: group entities+positions by player AND build owner_id lookup
let mut units_by_player: HashMap<String, Vec<UnitHandle>> = HashMap::new();
let mut owner_id_by_entity: HashMap<Entity, u8> = HashMap::with_capacity(512);
let mut player_id_to_index: HashMap<&str, u8> = HashMap::with_capacity(16);
let mut next_id: u8 = 0;

for (entity, owner, pos) in world.query::<(Entity, &UnitOwner, &UnitPosition)>().iter() {
    let pid = &owner.player_id;
    let id = *player_id_to_index.entry(pid.as_str()).or_insert_with(|| {
        let id = next_id;
        next_id += 1;
        id
    });
    owner_id_by_entity.insert(entity, id);
    units_by_player
        .entry(pid.clone())
        .or_default()
        .push(UnitHandle {
            entity,
            pos: (*pos).as_tuple(),
        });
}

debug_assert!(next_id < 255, "TickContext: too many players (max 255 for u8 owner IDs)");
```

3. Update the `Self { ... }` construction:

```rust

    cities,
    funds,
    width,
    height,
    units_by_player,
    owner_id_by_entity,
})
```

## Performance Analysis

### Per-tick work comparison (500 units, 4 players)

| Metric | Before | After | Delta |
|---|---|---|---|
| ECS queries touching `&UnitOwner` | 4+ (build, nearby, combat, city_capture) | 1 (build only, for nearby+combat) | -75% for migrated systems |
| String clones per unit (nearby+combat) | ~2 per unit | ~1 per unit (build only) | -50% |
| Owner dedup allocation (nearby) | `HashMap<&str,usize>` + `Vec<usize>` per tick | 0 | -2 allocations/tick |
| Per-pair combat check | `world.get::<&UnitOwner>()` + String `==` | `HashMap<Entity,u8>::get()` + u8 `==` | estimated significant improvement |
| Candidate Vec tuple size (combat) | includes `String` (24+ bytes) | `u8` (1 byte) | -24 bytes/unit in candidates |

### The combat benefit is the primary win

Currently, for every pair scanned, combat does:
1. `world.get::<&UnitOwner>(entity2)` — archetype table lookup + borrow guard
2. String comparison (`o.player_id == *owner1`) — heap pointer chase + byte-by-byte

Replacing with:
1. `ctx.owner_id_by_entity.get(&entity2)` — one HashMap lookup
2. `u8` equality — single byte compare

The actual speedup is unmeasured and depends on cache behavior, but the ECS borrow guard + String comparison path is demonstrably more expensive than a HashMap + integer compare.

## Risks and Mitigations

### Risk 1: `ctx` is `None`
**Mitigation:** Guard with `if let Some(ref ctx) = ctx` (same pattern as influence/encirclement). If `None`, the game is in a broken state anyway.

### Risk 2: Entity reuse after death
**Mitigation:** `hecs::Entity` includes a generation counter. Reused entity IDs get a different generation. Dead HashMap entries are GC'd when `ctx` is dropped at end of tick.

### Risk 3: `u8` overflow with 256+ players
**Mitigation:** `debug_assert!(next_id < 255, "Too many players (max 255 for u8 owner IDs)")`. In practice, ≤ 8 players.

### Risk 4: Test fixtures build ctx at wrong time
**Mitigation:** Each test must build `ctx` AFTER spawning units. Pattern: spawn units → `TickContext::build()` → `run()`.

### Risk 5: `filter_map` in ECS query skips unknown entities
**Mitigation:** Safe — `filter_map` with `ctx.owner_id_by_entity.get(e).copied()` skips entities not in the map. Should never happen for valid units (all units with `UnitPosition` have `UnitOwner`). If it does, it's a game logic bug, not a panic.

### Risk 6: No units added/removed between build and use
**Mitigation:** `ctx` is built at tick start. No unit spawning happens between `ctx.build()` and nearby_enemies/combat. Death cleanup runs at tick end, after both systems.

### Risk 7: `supply.rs` not migrated
**Mitigation:** Intentional. Supply runs after combat, needs fresher data. Its own query is needed for stats/equipment/flags/water_transition regardless of owner.
