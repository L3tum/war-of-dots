#### T-3 / X-1 — `owner_id_by_entity`: `HashMap<Entity,u8>` → dense `Vec<u8>` (memory-traffic)

**Files / functions:**
- `src/game/game.rs` — `TickContext` struct (`owner_id_by_entity` field), `TickContext::build_initial`, `rebuild_both` (test/bench), `recruit_unit` (`insert(entity, player_idx)`).
- `src/game/systems/movement.rs` — `populate_grid_units` (`.get(&entity)`).
- `src/game/systems/supply.rs` — per-unit owner lookup (`.get(&entity)`).
- `src/game/systems/combat.rs` — target-acquisition owner check + same-owner check.
- `src/game/systems/encirclement.rs` — (Phase 2 E-3) owner lookup in the flag sweep.

**Why it's a win (evidence):** `owner_id_by_entity` is a `HashMap<Entity, u8>` with ~9 800 entries. Every consumer does `.get(&entity)` — a SipHash hash + probe (~10–20 ns). Across a tick that is ~9 800 (movement) + ~9 800 (supply) + ~2 630 (combat movers) ≈ **~22 000 lookups/tick ≈ ~286 µs**. A dense `Vec<u8>` indexed by entity id is one array load + one sentinel check (~1–2 ns).

**Mechanism — REUSE the existing `gate_cooldown` dense-Vec-by-entity-id pattern `[VERIFY]`.**
`movement.rs` already has `gate_cooldown_active/set/clear` operating on a `Vec<u64>` indexed by the low 32 bits of `Entity::to_bits()`, with a generation in the high bits and a `GATE_BACKOFF_MAX_ID = 1 << 20` cap so a pathological id (`Entity::DANGLING` = `u32::MAX`) cannot resize the Vec to GBs. Mirror that shape.

**Before (conceptual):**
```rust
// game.rs
pub struct TickContext {
    pub owner_id_by_entity: HashMap<hecs::Entity, u8>,
    // ...
}
// consumers:
let owner_idx = ctx.owner_id_by_entity.get(&entity).copied(); // Option<u8>
```

**After (concrete shape) — generation-guarded, mirrors `gate_cooldown`'s index+cap idiom but uses the hecs *entity generation* as the guard (REVIEW-PLAN correction):**
```rust
// game.rs
pub const OWNER_NONE: u8 = 255;
const OWNER_MAX_ID: u32 = 1 << 20;   // mirrors GATE_BACKOFF_MAX_ID

pub struct TickContext {
    // owner_id_by_entity: HashMap<hecs::Entity, u8>  // REMOVED
    /// owner_at[id] = owner index, or OWNER_NONE (255) if never set.
    pub owner_at: Vec<u8>,
    /// The hecs entity generation that set owner_at[id]. A lookup is valid only
    /// if owner_gen[id] == entity.generation() — this is what makes id-reuse safe
    /// (a dead unit's id reused by a new unit has a different generation).
    pub owner_gen: Vec<u32>,
    // ...
}

impl TickContext {
    #[inline]
    pub fn owner_index(&self, e: hecs::Entity) -> u8 {
        let id = e.index();                       // hecs id (low 32 bits of to_bits)
        if id >= OWNER_MAX_ID { return OWNER_NONE; }  // guards Entity::DANGLING (id u32::MAX)
        let i = id as usize;
        if self.owner_gen.get(i).copied().unwrap_or(0) != e.generation() { return OWNER_NONE; }
        self.owner_at.get(i).copied().unwrap_or(OWNER_NONE)
    }
    #[inline]
    pub fn owner_set(&mut self, e: hecs::Entity, oi: u8) {
        let id = e.index();
        if id >= OWNER_MAX_ID { return; }
        let i = id as usize;
        self.ensure_owner_cap(i + 1);             // grow owner_at/owner_gen together
        self.owner_at[i] = oi;
        self.owner_gen[i] = e.generation();
    }
}
```
(`ensure_owner_cap` resizes both Vecs to the given length, init `owner_at` with `OWNER_NONE` and `owner_gen` with `0` — a `resize` no-op at steady state. Verify `hecs::Entity` exposes `.index()` and `.generation()` in this hecs version — the `gate_cooldown` code uses `to_bits()` + `>> 32`; adapt to whichever accessors the pinned hecs provides.)

**Two correctness sub-decisions (resolve BEFORE coding — these are the risk):**

1. **Id-reuse / stale-owner hazard — RESOLVED by REVIEW-PLAN.** A dead unit's entity id can be reused by a later-spawned unit of a *different* player. **Finding (REVIEW-PLAN, verified in source):** `death_cleanup::run` (`death_cleanup.rs:30`) does **not** take `TickContext` and never touches `owner_id_by_entity` — it only does `entity_reverse.remove` + `world.despawn`. So the current HashMap is *not* cleared on death; it is safe only because (a) `recruit_unit` sets the owner at spawn (`game.rs:1071`) before the entity is queryable, and (b) a despawned entity never appears in any ECS query. The dense Vec must preserve that safety **without** relying on death_cleanup. **Decision (locked by review): use the hecs entity-generation guard** (`owner_gen[id] == e.generation()`, shown in the concrete shape above). This needs **no `death_cleanup` change at all** (the earlier "1 line in death_cleanup" estimate was wrong — death_cleanup has no TickContext access) and is robust to id-reuse because hecs increments generation on every id reuse, so `(id, generation)` uniquely identifies an entity lifetime. (A clear-on-death approach was considered and rejected as more invasive: it requires threading `TickContext` into `death_cleanup::run`.)

2. **DANGLING / sentinel guard.** `Entity::DANGLING` (id `u32::MAX`) and any id ≥ `OWNER_MAX_ID` must return `OWNER_NONE` and must **not** trigger a resize. The `owner_index` above already guards `id >= OWNER_MAX_ID` before any indexing (and the generation check then returns `OWNER_NONE` for any unset/stale slot).

**Rewrite at call sites** — replace
`ctx.owner_id_by_entity.get(&entity).copied().map(|i| i as usize).filter(|&i| i < len)`
with
`let oi = ctx.owner_index(entity);` then `if oi != OWNER_NONE && (oi as usize) < len { … }`. The set path is `ctx.owner_set(entity, player_idx)` in `recruit_unit` (replacing the `insert`), and `build_initial`/`rebuild_both` call `owner_set` for each unit. Movement/supply/combat keep the identical `None`/out-of-range fallback semantics (draw no supply / treat as no-owner), so behavior is bit-identical for live units. **Note for Phase 2 E-3:** `owner_index` is *not* the right source for the encirclement flag sweep's player index (see the E-3 correction — the territory grid uses sorted-player order, `owner_index` uses first-seen order).

**Determinism argument:** the mapping entity→owner is *identical* to the HashMap for every live entity (same value written at the same time by `recruit_unit`), and the dense Vec is strictly more deterministic than a `HashMap` (no iteration-order dependence — but these are point lookups, so no order was ever observable). The clear-on-death makes the alive-set exactly match the HashMap. Any consumer that currently gets `None` (absent/out-of-range) gets `OWNER_NONE` → the same code path.

**Risk:** LOW-MED. The only real risk is the id-reuse window (handled by clear-on-death + the `OWNER_MAX_ID`/DANGLING guard). Effort: small — type change + 4 call sites + `build_initial` / `rebuild_both` / `recruit_unit` / `death_cleanup`.

**Verification:**
- Microbench: `systems/movement_500`/`movement_2000` (populate_grid_units path), `systems/supply_500`.
- Unit/integration: full `make test` (combat targeting + territory determinism are the sensitive ones; also any test that spawns/despawns and re-reads owner).
- Add a focused test: spawn unit A (owner P1) → despawn → spawn a new unit → assert its `owner_index` reflects its real owner, never a stale value.
- `make check` + `make clippy -D warnings`.

#### E-1 — encirclement `Arc::ptr_eq` before the 1 MB byte-compare — **⛔ DROP (REVIEW-PLAN: UNSAFE as specified)**

**Why the original idea is UNSAFE (REVIEW-PLAN, verified in source):** the rationale "Arc is immutable → same allocation = same bytes" is **false** for this code. influence publishes from a **double-buffer and mutates the slot in place**:
- `influence.rs:359` `let terr = Arc::make_mut(&mut scratch.territory_pool[terr_gen]);`
- `influence.rs:436` `wb.territory.grid = Arc::clone(&scratch.territory_pool[terr_gen]);` — then flips `terr_gen`.

The buffer alternates `pool[0]`/`pool[1]` each dirty tick. By the time a slot is `make_mut`ed again its refcount is 1, so `Arc::make_mut` **reuses the same allocation and overwrites it in place**. The *same Arc pointer* therefore wraps *different bytes* on different ticks → `Arc::ptr_eq(stored, current) == true` does **not** imply byte-equality → short-circuiting the byte-compare on pointer equality would skip the flood when territory actually changed → stale `safe` grid → wrong `encircled` flags. This is a **determinism/correctness bug**. The codebase already documents this hazard — `encirclement.rs`: *"Copying (not borrowing) the territory keeps the fill immune to the influence double-buffer rotation between ticks."*

**Decision: DROP E-1.** The existing full byte-compare in `inputs_unchanged` (`self.fill_territory[..] == territory[..]`) is the correct, safe check. The ~1 MB compare is ~100 µs, amortized over a 30-tick cadence (~3 µs/tick) — not worth the risk. **If** the compare ever measures hot, the safe fix is for influence to emit a content-based dirty signal (per-tick revision counter or cheap content hash on the published territory) that encirclement compares instead of the byte slice — never an Arc pointer compare. Keep E-1 out of scope.
