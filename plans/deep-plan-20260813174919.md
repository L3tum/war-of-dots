# Deep Plan: SpatialHash Crate Evaluation

## Context

This analysis was prompted by the question of whether the game's internal `SpatialHash` data structure and the `SpatialtySystem` that uses it should be replaced with an external crate such as `spatial_hash_3d` (https://github.com/alexpyattaev/spatialhash). The current system is purpose-built for the game's 2D turn-based strategy simulation and powers combat adjacency lookups without O(n²) pairwise checks.

**What the systems do:**

- **`SpatialHash`** (`src/game/systems/spatial_hash.rs`) — A sparse hash grid mapping `(cell_x, cell_y)` → `Vec<hecs::Entity>`. Cell size is 2.0 world units (matching combat range), so entities within combat distance are guaranteed to be in the same or adjacent cells. Provides `insert(entity, x, y)`, `remove(entity, x, y)`, `query_nearby_into(x, y, &mut out)`, and `clear()`. Note: `query_nearby()` (the non-allocating variant) and `clear()` are both annotated `#[allow(dead_code)]` — they are used only in tests and the optional `perfect-movement` feature, not in the main game tick. The production hot path exclusively uses `query_nearby_into()`.

- **`SpatialtySystem`** (`src/game/systems/spatialty.rs`) — A 3-pass incremental system that maintains `NearbyEnemies` components on all units by processing only movers and fresh spawns each tick. Costs scale with mover count, not total unit count. Used by `CombatSystem` to find candidates without scanning all pairs.

- **Consumers:** `Game` struct stores a `SpatialHash` instance (`src/game/game.rs:108`). It is passed through to `spatialty::run()` and `death_cleanup::run()`. When the `perfect-movement` feature is enabled, `movement.rs` creates its own ephemeral `SpatialHash` for segment-circle interception checks.

- **Test coverage:** 10 unit tests in `spatial_hash.rs` + 10 integration tests in `spatialty.rs` + 3 tests in `death_cleanup.rs` = **23 tests total**. There are 8 dedicated SpatialHash microbenchmarks plus 3 spatialty system microbenchmarks = **11 benchmarks total**.

## Decision

**Do NOT switch to any external crate.** The current implementation is purpose-built, well-tested, memory-efficient, and correctly matched to the game's 2D sparse-map use case. No available crate offers a net benefit — they either have license incompatibilities, wrong dimensional assumptions, higher memory usage, or APIs that would require substantial wrapper code.

## Analysis

### 1. License Incompatibility (Hard Blocker)

The project is licensed under **MIT** (`Cargo.toml:license = "MIT"`). The leading candidate crate, `spatial_hash_3d`, is licensed under **GPL-3.0** (with an internal inconsistency — `Cargo.toml` says `GPL-2.0-or-later` while `LICENSE.txt` says `GPL-3.0`).

**Consequences:**
- GPL is a copyleft license. Adding it as a dependency would legally require the entire project to be relicensed under GPL.
- Keeping the project MIT while depending on GPL code would constitute copyright infringement.
- There is no way around this. This is a hard blocker.

### 2. Technical Mismatch

#### Dimensions

- **Crate:** Fixed-volume 3D grid (`[T; WIDTH * HEIGHT * DEPTH]`). Designed for volumetric spatial partitioning.
- **Game:** 2D sparse map (200×200 tiles, entities only at a few hundred positions). No Z-axis concept exists in the game model.

Forcing a 3D data structure onto a 2D problem is a category error. The game would either need to fix `z = 0` for every operation (wasteful) or build a 2D wrapper (defeating the purpose of using the crate).

#### Memory Usage

With `cell_size = 2.0` on a 200×200 map, the grid has **100×100 = 10,000 cells** (not 200×200 — each cell covers 2.0×2.0 world units).

| Scenario | Current (sparse HashMap) | `spatial_hash_3d` (dense array) |
|---|---|---|
| 200 units on 200×200 map | ~13 KB | ~360 KB (10,000 cells × ~36 bytes for `Option<Vec<Entity>>` baseline) |
| 500 units on 200×200 map | ~36 KB | ~360 KB (baseline is fixed regardless of occupancy) |
| 5,000 units on 200×200 map | ~360 KB | ~360 KB + entity storage |

**Key points:**
- **Current:** O(entities) — `HashMap<(i32,i32), Vec<Entity>>` only stores cells that have entities.
- **Crate:** O(width × height) — pre-allocates the entire grid regardless of occupancy. Even if you could store a bare `Entity` (6 bytes) per cell, the baseline for 10,000 cells is 60 KB. To match the game's multi-entity-per-cell semantics, you need `Option<Vec<Entity>>` per cell, which has a ~36-byte minimum footprint (two pointers + allocation header) even when empty, bringing the baseline to ~360 KB.
- The crate never becomes more memory-efficient at game-relevant densities. The benchmark runs with 60 units per city across 12 cities (720 units peak), and typical games have 200–500 units. Current system uses **10× less memory** at game-relevant densities.

#### API Incompatibility

| Operation | Current API | Crate API | Gap |
|---|---|---|---|
| Insert entity at position | `insert(entity, x, y)` | `sh[Vector3] = value` | Requires wrapper |
| Remove entity at position | `remove(entity, x, y)` | None (overwrite `sh[Vector3] = default`) | Missing — must implement |
| Query nearby entities | `query_nearby_into(x, y, &mut out)` | `iter_cubes(min, max)` | Different semantics |
| Clear all | `clear()` — O(1) | `iter_mut()` then set default — O(W×H×D) | Wrong complexity |
| Cell capacity | `Vec<Entity>` per cell (multiple entities) | Single `T` per cell | Must store wrapper type |
| Auto-evict empty cells | Yes (on `remove`) | N/A (dense array) | Wasteful at sparse density |

The crate's indexing-based API (`sh[Vector3] = value`) is fundamentally incompatible with the insert/remove/query pattern used throughout the game. A wrapper would need approximately **60–70 lines of indirection code** to bridge the gap — effectively re-implementing the current system on top of the crate.

#### `clear()` is dead code in production

The `clear()` method is annotated `#[allow(dead_code)]` and is only called in one unit test (`clear_removes_all`) and one benchmark (`spatial_hash/clear`). It is **not** called in the main game tick or in the `perfect-movement` feature path. The `perfect-movement` feature creates a fresh `SpatialHash::new()` each tick rather than reusing/clearing an existing one. Any crate comparison involving `clear()` complexity is therefore not relevant to production behavior.

### 3. Ecosystem Risk

- **Stars:** 2 on GitHub
- **Forks:** 1
- **Commits:** 51 (suggests single-developer project, not a team)
- **Maintenance signal:** None visible — no recent activity, no issue tracker activity, no version releases
- **Tests:** 1 criterion benchmark test (no unit tests for correctness)

The crate has minimal community adoption and no active maintenance signal. Depending on an unmaintained crate introduces long-term risk: if the crate's dependencies break, if security issues are found, or if the author abandons it, there's no community to take over.

### 4. Current System Strengths

The existing implementation has significant advantages that would be lost or degraded by switching:

1. **Incremental design.** `SpatialtySystem` only processes movers and fresh spawns each tick. Per-tick cost scales with `mover_count`, NOT total unit count. A crate-based approach would likely require rebuilding or differencing the entire grid.

2. **Buffer reuse.** `query_nearby_into(x, y, &mut out)` reuses the caller's `Vec` to avoid per-call allocations. This is critical for the hot path where hundreds of queries happen per tick. The non-buffer-reuse variant (`query_nearby()`) is not called in production.

3. **Auto-eviction.** `remove()` automatically evicts empty cells from the `HashMap`, keeping the sparse representation compact. No periodic cleanup pass needed.

4. **Per-phase timing instrumentation.** Three phases (`p1_collect`, `p2_process`, `p3_finalize`) are individually timed and exposed via `--bench-detailed spatialty` for profiling. This would need to be rebuilt.

5. **Zero external dependencies.** The `SpatialHash` struct uses only `std::collections::HashMap` and `hecs::Entity`. No crate to update, no breakage from upstream changes, no license audits.

6. **23 tests and 11 benchmarks.** Comprehensive coverage:
   - `spatial_hash.rs`: 10 unit tests (empty query, insert/query, adjacent cells, diagonal, two-cells-away exclusion, multi-entity, clear, negative coordinates, 9-cell coverage, far-away empty query)
   - `spatialty.rs`: 10 integration tests (fresh spawn initialization, same-owner exclusion, mover attacking flag, mover retreat, two nearby movers, stationary defender, far-away skip, three owners, empty world, dense cluster filtering)
   - `death_cleanup.rs`: 3 tests covering SpatialHash cleanup on entity death, NearbyEnemies cleanup, and entity reverse registry cleanup
   - `microbenchmarks.rs`: 8 dedicated SpatialHash benchmarks (3 insert at varying scales, query sparse, query dense, buffer reuse, remove/reinsert, clear) plus 3 spatialty system benchmarks (100, 200, 500 movers)

7. **Proven performance.** The system handles the full benchmark workload (12 cities, 720+ units, 500+ ticks, mid-battle recruiting) with sub-millisecond spatialty times.

### 5. Alternative Crates Evaluated

| Crate | License | Fit |
|---|---|---|
| `spatial_hash_3d` (alexpyattaev) | GPL-3.0 | ❌ License blocker, 3D dense grid |
| `spatial_hash` (JulianKnodt) | MIT | ❌ Hexagonal grids, no `remove()`, different query semantics |
| `rstar` (georust) | Apache-2.0 | ❌ Wrong data structure. R-trees are for range/nearest-neighbor in arbitrary distributions. Overkill for combat-range adjacency on a 2D grid. Higher memory and CPU overhead than a simple hash grid. |
| `grid2d` | MIT | ❌ Dense 2D grid. No entity management (stores single value per cell, not Vec). No remove(). No auto-eviction. |

**Conclusion:** No available crate is better suited than the current purpose-built implementation. The closest match (`spatial_hash` by JulianKnodt) uses hexagonal grids and lacks the insert/remove/query pattern entirely.

## Cost/Benefit

| Metric | Current | Switch Cost | Net Benefit |
|---|---|---|---|
| **License risk** | None (MIT, zero deps) | Critical (GPL would force relicensing) | ❌ Hard blocker |
| **Lines of code** | ~85 (SpatialHash) + ~195 (SpatialtySystem) | +60–70 lines wrapper | ❌ More code |
| **Tests** | 23 existing tests | Must rewrite all | ❌ Loss of coverage |
| **Memory** | O(entities), ~13–36 KB typical | O(W×H), ~360 KB baseline | ❌ 10× worse |
| **Performance** | Proven sub-ms per tick | Unknown regression risk | ❌ Unverified |
| **Maintenance** | Self-contained, owned | External dependency risk | ❌ More to maintain |
| **API ergonomics** | Direct insert/remove/query | Wrapper indirection | ❌ Worse DX |

**Total switching cost:** Estimated 3–5 days of development (wrapper code, test rewrites, benchmark comparison, integration fixes) for **zero tangible benefit**. The investment would actively degrade the project in every measurable dimension.

## Recommended Improvements

Instead of switching crates, invest effort in targeted improvements to the existing system:

### High Value

1. **`remove(entity)` variant** — Currently `remove(entity, x, y)` requires the caller to know the entity's old position. A `remove(entity)` variant that scans cells would be more ergonomic for edge cases (death_cleanup already reads positions separately). Benchmark to confirm the scan cost is acceptable for the rare single-entity removal path.

2. **Cell capacity hinting** — Add `reserve()` on per-cell `Vec`s in `insert()` to reduce reallocations when multiple entities cluster in the same cell. The `Vec` currently starts at capacity 0 and grows via `push()`. A hint of 2–4 would amortize the cost of common multi-entity cells.

### Medium Value

3. **`len()` / `is_empty()` / `cell_count()`** — Add convenience accessors: `len()` (total entities across all cells), `is_empty()` (no cells), `cell_count()` (number of occupied cells). These are useful for debug stats and early-exit optimization checks.

4. **`ahash::HashMap`** — Replace `std::collections::HashMap` with `ahash::HashMap` for ~10–15% faster lookups with no API change. The dependency adds ~3 KB to binary size but eliminates hash DoS concerns and improves throughput. Note: this would also benefit `death_cleanup.rs` which uses `std::collections::HashMap` for the `entity_reverse` registry.

5. **`#[inline]` on `world_to_cell`** — The `world_to_cell` method is called twice per `insert`, twice per `remove`, and once per `query_nearby_into`. Inlining eliminates the function call overhead in the hot path. Profile to confirm the compiler doesn't already inline it.

### Low Value

6. **Benchmark `retain()` path** — Add a microbenchmark for `remove()` (which uses `retain()`) to ensure the per-entity retain cost doesn't degrade with larger cells. Current cell sizes are small (1–5 entities), and the linear scan is negligible. Worth benchmarking as a sanity check for future-proofing.
