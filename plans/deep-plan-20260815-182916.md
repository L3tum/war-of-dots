## Goals & Non-Goals

### Goals
1. Make microbenchmark results sensitive to small changes (more samples, min/percentile stats, min as the sub-µs headline).
2. Make the HTML report honest and comparable: no dead metrics, metric cards grouped by category with fixed order, per-tick charts showing the *averaged* run (length `config.ticks`) instead of three stitched battles.
3. Make `--bench-prev` cover Total Wall Time, Min/Max Tick, battle-activity counters, and — per column — every numeric column of the System Timing and Microbench tables; list the compared report in Configuration.
4. Lengthen warmup; single-source the warmup constant.
5. Keep the `<pre>` Raw JSON block as the stable, backward-compatible `--bench-prev` data source.

### Non-Goals
- No switch to Criterion; keep the custom harness.
- No change to the battle simulation, tick ordering, or the debug-stats recording in `game.rs`/`debug_stats.rs` (we only read them).
- No `--bench-players` wiring (documented dead flag; fixing it changes the workload).
- No per-column deltas in the Detailed Sub-Part Timing table (opt-in, low traffic).
- No new `--bench-warmup` / `--bench-runs` CLI flags.
- No change to the `run-benchmark.sh` interface.

## 1. Microbenchmark noise (sub-1 ms, huge run-to-run variation)

**File:** `src/microbenchmarks.rs`

### 1.1 Add min/p90/p99 statistics
- Replace the 3-tuple return of `compute_stats` (l.75–95) with a struct:
  ```rust
  struct BenchStats { mean: f64, std_dev: f64, median: f64, min: f64, p90: f64, p99: f64 }
  ```
  `min = sorted[0]`; `p90`/`p99` use the same index math as `benchmark::percentile` for consistency with the battle-benchmark latency percentiles. Keep population std.
- Add `min_ns, p90_ns, p99_ns: f64` to `MicrobenchmarkResult` (l.29–45) and to any empty-result constructor.
- Populate in `run_bench` (l.97) and `run_bench_with_setup` (l.134).
- In `run_bench_cumulative` (l.173) and `run_bench_with_setup_cumulative` (l.199), divide **all** stats — including `min_ns, p90_ns, p99_ns` — by `repeats`, exactly like the existing mean/std/median division.

### 1.2 Substantially increase iteration counts
- `BenchConfig::Default` (l.56–61): `warmup: 5, timed: 25` → **`warmup: 25, timed: 100`** (4×).
- `BenchConfig::fast()` (l.66–71): `warmup: 10, timed: 50` → **`warmup: 50, timed: 200`** (4×). Update the doc comment.
- Rationale: 100–200 samples let mean/median converge and make p90/p99 (10–20 extreme samples) meaningful; min is stable with even fewer samples, which is why it is the sub-µs headline (1.4).
- **Runtime budget (assumption):** microbench phase may grow ~3–4×; target total ≤ ~60 s. After implementing, run `bash run-benchmark.sh probe` once and time the "Running microbenchmarks..." block. If any single benchmark exceeds ~5 s wall (the heavy `run_bench_with_setup_cumulative` ones rebuild 5k–10k-unit worlds per iteration: `ecs/query_positions_5000`, `ecs/query_positions_10000`, `systems/movement_empty`), drop that benchmark's `timed` back down (e.g. to 100) and note the reduced `n` (already reported per row).
- **Not doing (assumption):** multiple independent passes / median-of-passes. 4× + min/percentiles gets the sensitivity with a much simpler change; revisit only if a specific benchmark stays noisy.

### 1.3 Fix the `run_bench` warmup no-op
- The warmup loop (l.103–105) only calls `setup()`, which callers pass as `|| {}` — so the timed op is never warmed. Change it to also run the bench body:
  ```rust
  let mut f = bench_fn;
  for _ in 0..config.warmup { setup(); f(); }
  ```
  (hoist `let mut f = bench_fn;` above the loop). Affects the plain `run_bench`/`run_bench_cumulative` benchmarks in `bench_systems`/`bench_map_settings`. `run_bench_with_setup` already warms correctly (l.145) — leave it.

### 1.4 Report the new stats (CLI + JSON; HTML in item 7.2)
- `print_result` (l.1412): print min, median, and mean. Headline rule (**assumption**): if `mean_ns < 1000.0` (sub-µs) lead with **min**, else lead with **mean**:
  ```
  ecs/spawn_single                    min   412.3ns  (med 420.1, mean 435.9)  (200 iters)
  systems/movement_200                 mean   84.2µs (min 80.1, med 83.9) ± 6.3µs  (100 iters)
  ```
- `results_to_json` (l.1432–1444): add `min_ns`, `p90_ns`, `p99_ns` to each benchmark object; keep existing keys unchanged so old consumers keep working. (Median is already serialized; just not printed.)
- HTML microbench table gets the new columns + per-column deltas in item 7.2.
- **Feature gating:** all inside `#[cfg(feature = "microbenchmarks")]`; without it the `microbenchmarks` summary key stays `null` and the table renders "No microbenchmark data" (colspan updated 6→7 in 7.2).

## 5. Run stitching vs. averaging (three runs currently concatenated; charts show 4500 points)

**File:** `src/benchmark.rs`, `run_benchmark` (l.172) + summary/chart construction.

### 5.1 Recommended combination (**assumption**)
- **Per-tick series** (all three charts + the `summary` per-tick arrays) use **per-tick-index averages across the 3 runs**, length `config.ticks` (e.g. 1500): `avg[i].field = mean over runs r of run_r[i].field`. Valid because every run is seeded identically, so tick `i` is the same simulation phase — a true replicate average, not a mismatched merge. This turns the 4500-point stitched chart into a smooth 1500-point average trajectory, renders faster, and lines up the "recruit every 100 ticks" spikes at the same x across reports.
- **Summary latency statistics** (`latency.avg/min/max/p50/p90/p95/p99`) and **overhead stats** stay computed over the **raw pool of all 3×N ticks**, exactly as today. Percentiles over the raw pool are an honest latency distribution and a stability indicator; min/max are the fastest/slowest *single observed tick* (averaging has no meaning for extremes).
- A note under the Per-Tick Timing chart documents this: *"Per-tick series are averaged across the 3 measured runs. Summary latency/overhead stats use all 3×N individual ticks."*

> **Corrected alignment rationale (review):** the change is safe because **both** chart series (`tick_durations` and `overhead_durations`) are recomputed locally from `results.tick_data` at the same index (benchmark.rs l.817, l.822–825, script l.1197) — at *any* length. It is **not** because `summary["overhead_durations_ms"]` feeds the chart; that summary key is write-only (Raw JSON only).

### 5.2 Exact code changes in `run_benchmark`
- l.399: stop stitching-only. Keep the stitched vec (rename `raw_tick_data`) **and** collect per-run arrays into `runs_tick_data: Vec<Vec<TickData>>`.
- **Ordering matters (review):** all existing stats (overhead durations l.447, latency percentiles l.566–580, movers/combats averages, combat diag l.501–520) must keep running over `raw_tick_data`. `let tick_data = all_tick_data;` (l.441) stays the raw vec for stats. Only **after** stats are computed do we build `avg_tick_data` (length `config.ticks`, element-wise mean over `runs_tick_data` — `total_ms`/`system_sum_ms` as f64 then round; `entity_count`/`unit_count`/`movers`/`combats` rounded u32).
- `BenchmarkResults` (l.64–68): keep the field name `tick_data` but **store the averaged array** (length `config.ticks`). Update the struct doc: *"Per-tick series averaged across measured runs; length == config.ticks. Summary latency/overhead stats are over the raw 3×N pool."* Because `generate_html_report` builds both chart arrays from `results.tick_data` (l.817–825), **the chart code needs no change** — it simply gets 1500 points instead of 4500.
- CLI prints: `Ticks completed` → `Ticks completed: {raw_count} ({MEASURED_RUNS} runs × {config.ticks})`. The "Avg tick (wall)" line (wall ÷ all measured ticks) is unchanged.
- No other consumer of `BenchmarkResults.tick_data` exists, and nothing calls `.len()` on it, so no hidden length assumption breaks (review-verified).

### 5.3 `summary` JSON changes (explicit)
- **Also average** `tick_durations_ms`, `movers_per_tick`, `combats_per_tick` to length N (review decision: keep them consistent with the chart rather than leaving a 3×N vs N divergence in the Raw JSON). These arrays are write-only (Raw JSON block) and are **never** read by any chart or by `parse_previous_report` (review-verified), so this is safe.

## 8. Design Decisions & Assumptions

| # | Decision | Recommendation | Assumption? |
|---|---|---|---|
| D1 | How to combine the 3 runs | Per-tick-index **averaged** arrays (length `config.ticks`) for all 3 charts + `tick_durations_ms`/`movers_per_tick`/`combats_per_tick`; **raw 3×N pool** for latency percentiles, min/max, wall time, overhead stats & `overhead_durations_ms` | Yes — rejected "chart one representative run" (arbitrary, hides variance) and "average everything incl. percentiles" (masks spikes) |
| D2 | New warmup length | 200 ticks (4× current) | Yes — 100–500 defensible; 200 balances steady-state front vs ~13% extra cost |
| D3 | Warmup/runs constant plumbing | Module-level `pub const BENCH_WARMUP_TICKS` / `MEASURED_RUNS` used everywhere incl. `generate_html_report` l.692; recorded in `summary.config` | No (cleanup) |
| D4 | Microbench sample counts | `Default` 25→100 timed, `fast()` 50→200 timed (4×); no multi-pass | Yes — per-benchmark `timed` may be reduced if a single bench exceeds ~5 s |
| D5 | Sub-µs headline metric | `min` (best case) in CLI + first table column; `mean` headline for ≥1 µs; `min/p90/p99` added to struct + JSON | Yes |
| D6 | `run_bench` warmup no-op | Fix (warmup must execute the bench body) | No — clear bug |
| D7 | Summary card layout | Fixed logical order within 4 groups; no value-sorting | Yes |
| D8 | Delta helper | Generalize to (unit, threshold); ms 0.0005 unchanged; count 1.0 | Yes (count threshold) |
| D9 | `--bench-prev` robustness | Keep `<pre>` JSON as sole source; non-silent warnings; richer per-system/per-microbench parse; **field-presence** backward-compat (no version field) | No (old reports have all needed fields) |
| D10 | Configuration additions | Rows: Measured runs, Warmup ticks, Detailed systems, Compared against (path), Previous seed/ticks; mirrored into `summary.config` | Partially ("Previous seed/ticks" row) |
| D11 | Per-column deltas | System table: Total, Avg/Call, Calls, % of Ticks, P50, P90, P99 each get an inline delta; microbench: Min/Median/Mean inline; trailing Delta column removed from both | No |
| D12 | `--bench-players` | Not wired (would change workload); stays documented-dead | Yes — out of scope |
| D13 | Detailed Sub-Part table | No per-column deltas (opt-in, low traffic) | Yes — out of scope |
