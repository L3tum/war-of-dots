# TickContext Performance Optimizations — Deep Plan

## Context

The recent `b4efb39` commit added `owner_id_by_entity: HashMap<Entity, u8>` to `TickContext`, enabling O(1) u8 owner equality checks in `nearby_enemies` and `combat` systems (replacing per-pair `&UnitOwner` ECS borrows + String comparison). The incremental dirty-flag pattern (`TickContextDirty`) was introduced for efficient cross-tick persistence.

A focused code review identified 6 issues across High, Medium, and Low severity. This plan fixes all of them as a cohesive set of performance and correctness improvements — no behavioral changes.

## Approach

### Issue 1 (HIGH): Lazy `units_by_player` rebuild

**Problem**: `update_units_by_player()` runs unconditionally every tick, but `units_by_player` is only consumed by:
- `influence.rs` every `INFLUENCE_TICK_INTERVAL = 3` ticks (2/3 of ticks wasted)
- `encirclement.rs` every `CITY_CAPTURE_TICK_INTERVAL = 30` ticks (29/30 of ticks wasted)

Each rebuild is an O(n) ECS query over `(Entity, &UnitOwner, &UnitPosition)`, followed by `owner.player_id.clone()` for every entity (String allocations) and a full HashMap replacement.

**Fix**: Add `units_by_player_stale: bool` to `TickContextDirty`. Set it to `true` after movement runs (positions change). Only rebuild `units_by_player` just-in-time when `influence` or `encirclement` actually executes.

### Issue 2 (MEDIUM): Reduce ECS query count from 3 to 0-2 per tick

**Problem**: Three separate archetype queries touch `(Entity, UnitOwner, UnitPosition)`:
1. `update_owner_map` pass 1: `query::<&UnitOwner>()` — collect unique player IDs
2. `update_owner_map` pass 2: `query::<(Entity, &UnitOwner)>()` — map entities to indices
3. `update_units_by_player`: `query::<(Entity, &UnitOwner, &UnitPosition)>()` — group by player

**Fix**: 
- **Owner map**: replaced by incremental updates (see Issue 3) — no ECS query needed in the tick loop.
- `rebuild_units_by_player`: single query (unchanged, but now only runs on influence/encirclement ticks)
- `rebuild_both`: single query for benchmarks (`build_full`), populating all maps in one pass

Net effect:
- Non-influence tick: **0 queries** (owner map is incremental, units_by_player is cached)
- Influence tick: **1 query** (units_by_player only)
- vs current: **3 queries every tick**

**Key architectural note**: `owner_id_by_entity` is consumed by `nearby_enemies` and `combat` (which run early in the tick, before influence), while `units_by_player` is consumed by `influence` and `encirclement` (which run late in the tick, after combat). They are always needed at **different points** in the tick loop, so they cannot be combined into a single rebuild call in the tick path. A `rebuild_both` helper exists only for `build_full()` in benchmarks.

### Issue 3 (MEDIUM) + Issue 4 (LOW): Incremental owner map updates

**Problem**: 
- `update_owner_map` does `self.owner_id_by_entity.clear()` (O(capacity) zeroing of the hash probing table) then rebuilds from scratch.
- A fixed `with_capacity(512)` is wasteful for <512 entities and causes reallocations for >512.
- A swap pattern with dynamic capacity still has allocation costs.

**Fix**: Replace the rebuild-with-swap approach with **incremental updates**:
- Add `player_id_to_index: HashMap<String, u8>` and `next_player_idx: u8` to `TickContext` (persistent player→index mapping).
- **On recruit** (`recruit_unit`): look up or assign the player index, insert the new entity into `owner_id_by_entity`. O(1) per recruit.
- **On death**: do nothing. Stale entries are harmless — dead entities are despawned from the ECS, so they won't appear in queries, and the `filter_map` in nearby_enemies/combat only looks up entities that exist in the ECS. The map grows by at most the total number of entities ever spawned (negligible: ~200 bytes per entity).
- **Remove** the `entities_changed` dirty flag — it was only used to trigger the owner map rebuild.
- **Remove** `rebuild_owner_map` entirely.
- `build_initial` populates both `player_id_to_index` and `owner_id_by_entity` from the initial ECS state.
- `rebuild_both` (for benchmarks) also populates `player_id_to_index`.

This eliminates the owner map rebuild from the tick loop entirely. The map is always current, updated in O(1) at the exact points where entities change.

### Issue 5 (LOW): Debug assertions for silently dropped entities

**Problem**: Both `nearby_enemies.rs` and `combat.rs` use:
```rust
.filter_map(|(e, ...)| {
    let owner_id = ctx.owner_id_by_entity.get(&e).copied()?;
    Some((e, ..., owner_id, ...))
})
```
If an entity exists in the ECS but is missing from `owner_id_by_entity`, it's silently excluded — masking stale map bugs.

**Fix**: Add `debug_assert!(ctx.owner_id_by_entity.contains_key(&e), "...")` in the filter_map callbacks in both systems.

### Issue 6 (LOW): Flat-buffer GridIndex

**Problem**: `GridIndex::build` creates `vec![Vec::with_capacity(4); total]` — one `Vec` allocation per grid cell. For large maps, this means thousands of small heap allocations per tick.

**Fix**: Replace per-cell `Vec<CellEntry>` with a flat buffer: `entries: Vec<CellEntry>` + `cell_offsets: Vec<usize>` (prefix-sum) + `cell_sizes: Vec<usize>`. This allocates exactly 3 Vecs regardless of grid size. The struct also needs to store `height: usize` explicitly (currently derived from `cells.len() / width`).

- [ ] **Add to `TickContext` struct**:

  /// Next available player index (monotonically increasing, never reused).

- [ ] **Update `build_initial`** to populate `player_id_to_index` and `owner_id_by_entity` in a single ECS query:
  ```rust
  let mut player_id_to_index: HashMap<String, u8> = HashMap::with_capacity(16);
  let mut owner_id_by_entity: HashMap<Entity, u8> = HashMap::new();
  let mut next_player_idx: u8 = 0;
  for (entity, owner) in world.query::<(Entity, &UnitOwner)>().iter() {
      let idx = *match player_id_to_index.entry(owner.player_id.clone()) {
          Entry::Occupied(e) => e.get(),
          Entry::Vacant(e) => {
              let id = next_player_idx;
              next_player_idx += 1;
              e.insert(id);
              &id
          }
      };
      owner_id_by_entity.insert(entity, idx);
  }
  debug_assert!(next_player_idx < 255, "too many players");
  ```

### Step 4: Fix `GridIndex::build` to use flat buffers

- [ ] Replace `cells: Box<[Vec<CellEntry>]>` with two separate arrays:
  - `entries: Vec<CellEntry>` — flat storage for all cell entries
  - `cell_offsets: Vec<usize>` — prefix-sum array: `cell_offsets[i]` = start index in entries for cell i
  - `cell_sizes: Vec<usize>` — count of entries per cell
  - This is simpler than `Vec<(usize, usize)>` because slicing becomes `entries[offsets[i]..offsets[i]+sizes[i]]`
- [ ] Update `GridIndex::build` to use the flat buffer:
  - First pass: count entries per cell to build `cell_sizes`
  - Build `cell_offsets` as a prefix sum over `cell_sizes`
  - Second pass: use a cursor array (copy of cell_offsets) to fill entries in place
  - The total entries capacity is known after the first pass: `entries: Vec::with_capacity(total_entries)`
- [ ] Update `cell_idx` usage in the main loop to iterate `&grid.entries[grid.cell_offsets[idx]..grid.cell_offsets[idx] + grid.cell_sizes[idx]]`
- [ ] The `GridIndex` struct becomes:
  ```rust
  struct GridIndex {
      entries: Vec<CellEntry>,      // flat storage for all cell entries
      cell_offsets: Vec<usize>,     // prefix-sum: cell_offsets[i] = start index in entries
      cell_sizes: Vec<usize>,       // count of entries per cell
      min_x: i32,
      min_y: i32,
      width: usize,
      height: usize,                // explicit (was derived from cells.len() / width)
  }
  ```
- [ ] Update `cell_idx` to use explicit `height` field:
  ```rust
  fn cell_idx(&self, cx: i32, cy: i32) -> Option<usize> {
      let x = (cx - self.min_x) as isize;
      let y = (cy - self.min_y) as isize;
      if (0..self.width as isize).contains(&x)
          && (0..self.height as isize).contains(&y)
      {
          Some((y * self.width as isize + x) as usize)
      } else {
          None
      }
  }
  ```
