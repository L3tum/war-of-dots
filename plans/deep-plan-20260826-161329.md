# Deep Plan: Network-Layer Hot-Path Optimization

## Context & Goals

The network phase is the single largest allocator in the tick loop (2,723 allocs / 742 KB per tick — ~99.9 % of per-tick heap traffic) and carries the worst tail latency (P99 4.642 ms) driven by grid-republication ticks. The user wants to improve it further via reuse, SIMD, parallelism, and a shared-scratch/dirty-set approach — while keeping the robust snapshot diff as the correctness backbone.

**Baseline** (`reports/report_92.html`, 200×200 map, 12 cities, 4 players, ~240 units, 1500 ticks × 3 runs, seed 42):

| Metric | Value |
|---|---|
| Network avg / P50 / P90 / P99 | 0.819 / 0.464 / 2.154 / **4.642 ms** |
| Allocs / tick | **2,723** |
| Heap / tick | **742 KB** |
| Wire bytes (no grid change) | ~186 KB |
| Wire bytes (grid change, every 3rd tick) | ~590 KB |
| Runs on | 88 % of ticks |
| Total network time / 1500 ticks | 1,228 ms |

Grid-change ticks are the expensive ones: each player receives a 40 KB vision + 40 KB border grid (160 KB × 4 players = 640 KB raw; ~590 KB after CBOR).

## Architecture Summary (verified in code)

- `run_network_phase(&Game, &mut NetworkBaselines, &[String])` — `src/server/delta.rs:360` — iterates players, calls `build_delta_inner` per player, encodes via `encode_message_with_hint`.
- `build_delta_inner` — `src/server/delta.rs:88` — takes `prev_vision: Option<&Arc<Vec<bool>>>`, `prev_border: Option<&Arc<Vec<u8>>>`, `current_vision: &Option<Arc<Vec<bool>>>`, `current_border: &Option<Arc<Vec<u8>>>`, plus shared `prev_units`, `current_units`, `current_cities`.
- Grid compare is `Arc::ptr_eq` fast-path → `slice == slice` fallback → collect.
- Vision grids: `Arc<Vec<bool>>` (`src/game/components.rs:150`, `src/game/systems/influence.rs:83` double-buffer `[Arc<Vec<bool>>; 2]`).
- Border grids: `Arc<Vec<u8>>` (`src/game/components.rs:166`).
- Per-player loop passes the **same** `prev_border` / `current_border` / `prev_units` / `current_units` / `current_cities` to every `build_delta_inner` call; only `prev_vision` + `player_id` vary.
- `unit_states()` (`game.rs:1830`) and `unit_states_direct()` (`game.rs:1876`) both produce the same `Vec<UnitState>` via identical ECS queries.
- `tick_system!` macro (`game.rs:39-65`) wraps the network phase; `benchmark.rs:625` records it.
- `make check-vectorization` (`Makefile:56` → `scripts/check_vectorization.sh`) canaries `GridIndex::build`; `Game::union_vision_grids` is REPORT_ONLY (0 wide-register ops, due to `[bool]` element type).
- No `rayon` in `Cargo.toml`.

## Approach / Strategy

**Principle: keep the robust snapshot diff as the correctness backbone; win on cheap, local, verifiable improvements.**

### (1) Reuse — biggest, safest wins

- **Dedupe the double snapshot.** `game_server.rs:556` calls `game.unit_states()` for the active-player check; `run_network_phase` then calls `game.unit_states_direct()` again. Pass the snapshot in instead of re-querying the ECS.

- **Compute the border grid diff once, share the bytes.** The border diff input (`prev_border` vs `current_border`) is identical for every player. Hoist the compare + `to_vec()` out of the per-player loop.

- **Compute unit/city diffs once.** `units_added`, `units_removed`, `unit_updates`, `city_updates` are player-independent. Compute them once above the per-player loop. The per-player loop then only does: per-player vision diff + `PlayerState` + idle-skip + assemble message. This is the "parallel-adjacent" win — removes 3 of 4 redundant passes over 240 units without adding threads.

### (2) SIMD — vision `[bool]` → `[u8]` (W5)

`[bool]` in Rust is 1-bit-in-MIR; LLVM **cannot** vectorize equality compare or the `*b as u8` conversion (confirmed: `check_vectorization.sh` shows 0 wide-register ops in `union_vision_grids`). Switching storage to `[u8]` (0/1) makes:

- The `prev.as_slice() == curr.as_slice()` compare a memcmp-class operation (LLVM emits `vpcmpb`/`vptest` or a scalar `memcmp` call).
- The diff conversion `curr.iter().map(|b| *b as u8).collect()` → `curr.as_slice().to_vec()` (a memcpy, no per-element work).
- `union_vision_grid_flat` (`game.rs:1702`) becomes a **branchless** byte-OR that auto-vectorizes (must be rewritten as `result[i] |= grid[i]`, not `if grid[i] != 0`).

The wire format is already `Vec<u8>` (delta.rs converts `bool → u8` before sending), so **no protocol or frontend change**.

The double-buffer invariant in `influence.rs:83-86` must be preserved: the slot being written is the one NOT published; `Arc::make_mut` is a strong-count-1 in-place fill at steady state. Changing the element type from `bool` to `u8` is type-level; the Arc-clone / ptr_eq / double-buffer logic is unchanged.

### (3) Parallel — do NOT add rayon for per-player deltas

Rayon was already trialed and removed (`delta.rs:14` module doc, `plans/W2_ENCIRCLEMENT.md` run 14):

- Per-player parallel flood: **10 % slower** in microbench (3.366 vs 3.048 ms), **+18 %** on real-game `p2_bfs` (4.822→5.710 ms), P99 unchanged at 10 ms, **allocs 21→89/call (+7×)**.
- Per-player network work is ~0.2 ms normal / ~0.5 ms grid-change. Rayon dispatch overhead (thread-pool acquire, task graph construction, join) is a large fraction of 0.2 ms → wash or regression.

**Decision: do not add rayon for the network phase.** The "parallel-adjacent" win is the dedup (compute shared work once) from (1) above, which is free and risk-free.

### (4) Shared scratch / dirty-set — assessed honestly

**Verdict: partially viable, a trap as a general mechanism. Implement the safe subset (movement-only fast path) as an optional Phase-2 item; defer the full dirty-set.**

| Mutation site | Tracked? | Notes |
|---|---|---|
| position / path | ✅ `MovementScratch.movers` (movement.rs:40) | clean |
| men / organisation / attacking | ✅ `CombatScratch.fought` (combat.rs:43, insert 546-547) | but… |
| attacking clear (defender exits) | ⚠️ NOT in `fought` (combat.rs:170, 854) | silent desync risk |
| men attrition / org recovery / equipment wear+delivery | ❌ **no dirty set** (supply.rs:195-355, runs over ALL units) | dominant mutation source |
| on_water / embarking / disembarking / boat | ✅ `WaterScratch.changes` (water.rs:29) | clean |
| encircled flag | ❌ **no dirty set** (encirclement.rs:301-302, over all units) | |
| unit removal | ✅ `DeathCleanupScratch.dead_set` (death_cleanup.rs:22+) | clean |
| healing / resupply toggle | ❌ **no hook** (game_server.rs:518-525) | command path, not a system |

A dirty-set is only correct if **every writer of every network-visible field** marks it. Missing even one site → silent client desync (baseline committed as "unchanged" while a field actually changed).

**Safe form (Phase 2, optional):** movement-only fast path. If a unit's entity is in `MovementScratch.movers`, skip the two `from_unit` digest builds and the digest `==` compare — go straight to the field-by-field slow path. This is a correctness-safe *optimization* on top of the snapshot diff: it only skips redundant comparison work, never omits a change, because every non-mover still goes through the full digest path.

**Entity→id bridging (important detail):** `movers` stores `hecs::Entity` handles, but the delta loop keys by `u.id` (String `"unit_{eid}"`). To check membership you must either:
- (a) build a `HashSet<u32>` from `movers.iter().map(|(e,_,_)| e.id())` and extract the numeric id from `u.id` (strip `unit_` prefix, parse), or
- (b) add a `#[serde(skip)] entity_id: u32` field to `UnitState` to avoid string parsing.

This is a small standalone task, not a one-liner.

## Concrete Changes

### Phase 1 — low-risk, high-win, no protocol change

**W-1: Dedupe the double unit snapshot**
- **What:** `game_server.rs:556` already builds `current_units = game.unit_states()`. Change `run_network_phase` to accept `current_units: &[UnitState]` (and `current_cities: &[CityState]`) as parameters instead of calling `unit_states_direct()` internally. Remove the second ECS query.
- **Reuse:** existing `unit_states()` (game.rs:1830). Keep `unit_states_direct()` (game.rs:1876) for callers that need it without a pre-built Vec.
- **Expected win:** eliminates one full pass over ~240 units — ~1,500–2,500 allocs/tick removed (≈ 50–70 % of the 2,723). Estimate; A/B is the arbiter.
- **Risk:** very low. Same data, same order.
- **A/B:** `./run-benchmark.sh <n> --bench-prev=./reports/report_<prev>.html`

**W-2: Compute border diff once; compute shared unit/city diffs once**
- **What:** In `run_network_phase` (delta.rs:360), before the per-player loop:
  1. Compute `border_grid_diff: Option<Vec<u8>>` once from `baselines.prev_border` vs `border_grid`.
  2. Compute `units_added`, `units_removed`, `unit_updates`, `city_updates` once from the shared `prev_units` / `current_units` / `current_cities`.
  3. In the per-player loop, only compute the per-player vision diff + `PlayerState` + idle-skip check, then assemble `GameDeltaMessage` by cloning the shared slices into the per-player message.
- **Idle-skip clarification:** The per-player idle-skip condition must **AND** both the shared-diff emptiness checks (`units_added.is_empty() && unit_updates.is_empty() && city_updates.is_empty() && border_grid_diff.is_none()`) **and** the per-player checks (`vision_grid_diff.is_none() && !funds_changed && prev_owned == player_state.units_owned`). Do not simplify to per-player fields only.
- **Reuse:** existing `build_delta_inner` logic, restructured. `estimate_delta_size` + `encode_message_with_hint` (protocol.rs:369-390) unchanged.
- **Expected win:** removes 3 of 4 iterations over 240 units (digest + field compare) and 3 of 4 border `to_vec()` / 40 KB compares. On grid-change ticks: ~120 KB of redundant alloc + ~120 KB of redundant compare eliminated.
- **Risk:** low. Shared parts are provably player-independent. Per-player assembly is a straightforward clone.
- **A/B:** yes — confirm P90/P99 drop on grid-change ticks and allocs drop on all ticks.

**W-3: Quantize `men` / `organisation` in `UnitStateDigest`**
- **What:** In `UnitStateDigest::from_unit` (delta.rs:55-72), change `men: u.men` → `men: (u.men / QUANT_MEN).round() * QUANT_MEN` and same for `organisation` with `QUANT_ORG = 1.0_f32`. **Use `round()` (round-to-nearest), not `floor()` or truncation.**
- **Rationale:** Per-tick men drain is `1/600 ≈ 0.0017` (supply.rs:332); even at 10× under-supply the drain is `10/600 ≈ 0.017` — both far below 1.0. A full, healthy unit's men value oscillates within one quantization bucket for ~60–600 ticks → digest stays equal → no `UnitUpdate` emitted.
- **Correctness guarantee:** A digest change still implies a real ≥ 0.5-soldier (or ≥ 0.5 org-point) change, which is visible. When an update IS emitted, the wire carries the exact `u.men` (the slow path reads `u.men`, not the quantized value). The stored `prev_units` also holds the exact value. No information lost; only the *frequency* of sub-threshold updates is reduced.
- **Caveat:** Units actively being replenished (men gaining up to 1.0/tick from the manpower pool) will still cross bucket boundaries every tick. The wire-reduction benefit is concentrated on idle/maxed units and may be smaller in combat-heavy scenarios than the headline number suggests.
- **Reuse:** existing digest struct + `from_unit`; no protocol change (wire field is still `f32 men`).
- **Risk:** very low. Quantization is in the digest only; wire values and stored snapshots are unchanged. A client displaying men at 0.1 precision sees at most a ≤ 0.5-unit lag — acceptable and consistent with 1-soldier granularity.
- **A/B:** yes — expect a large drop in `unit_updates` count (visible in per-tick wire bytes and allocs). Add unit tests (see Verification).

### Phase 2 — requires A/B or touches invariants

**W-4: Vision grid `[bool]` → `[u8]` (SIMD_ROADMAP §W5)**
- **What:** Change the element type from `bool` to `u8` (values 0/1) in:
  - `components.rs:150` — `VisionGrids.grids: Arc<HashMap<String, Arc<Vec<u8>>>>`
  - `influence.rs:83` — `InfluenceScratch.vision_pool: HashMap<String, [Arc<Vec<u8>>; 2]>`
  - `influence.rs` `stamp_circle` — `vision: &mut [u8]`, `vision[start..end].fill(1)` (instead of `fill(true)`)
  - `influence.rs` `compute_player` — `vision: &mut [u8]`
  - `game.rs:1570` `vision_grid_flat` — return `Option<Arc<Vec<u8>>>`
  - `game.rs:1702` `union_vision_grid_flat` — `Vec<u8>`, rewrite loop as **branchless** `result[i] |= grid[i]` (NOT `if grid[i] != 0 { result[i] = 1; }` — the conditional branch prevents LLVM auto-vectorization even on `[u8]`). This is required before adding to EXPECT_VECTOR.
  - `game.rs:1537` `vision_grid_2d` — `flat[y*w+x] != 0` for the 2-D bool conversion (LLM/spectator path). Note: `GameStateMessage.vision_grid` (protocol.rs:8) remains `Option<Vec<Vec<bool>>>` on the wire for the full-state message; `vision_grid_2d` handles the `u8 → bool` conversion per cell.
  - `delta.rs:334` `NetworkBaselines.prev_vision: HashMap<String, Arc<Vec<u8>>>`
  - `delta.rs` `build_delta_inner` — `prev_vision_grid: Option<&Arc<Vec<u8>>>`, `current_vision_grid: &Option<Arc<Vec<u8>>>`; diff is `curr.as_slice().to_vec()` (memcpy, no `*b as u8` map)
  - `game_server.rs` spectator path — `spec_vision: Option<Arc<Vec<u8>>>`
- **Wire:** `vision_grid_diff` in `GameDeltaMessage` is already `Option<Vec<u8>>` — no protocol change, no frontend change.
- **Double-buffer invariant:** unchanged. `Arc::make_mut` on `[u8]` works identically to `[bool]`. The `vision_gen` flip logic is untouched.
- **Expected win:** the `prev == curr` compare on a 40 KB grid becomes a vectorized/memcmp operation (µs-class) instead of a scalar 40 K-element bool compare. The `*b as u8` collect loop is eliminated. `union_vision_grid_flat` becomes vectorizable (after branchless rewrite). Modest absolute win (~20-50 µs on grid-change ticks) but removes a known non-vectorizable hot loop.
- **Risk:** medium. Touches the double-buffer type in 4+ files. Mitigated by: (a) mechanical type change (bool → u8, true/false → 1/0), (b) all existing vision/influence tests must pass, (c) `make check-vectorization` must stay green.
- **A/B:** yes. `make check-vectorization` is mandatory. `./run-benchmark.sh` for P99 on grid-change ticks.

**W-5 (Optional): Movement-only dirty fast path**
- **What:** Pass `&MovementScratch.movers` into `run_network_phase`. In the per-unit diff loop, if the unit's entity is in the mover set, skip the two `from_unit` digest builds and the digest `==` compare — go directly to the field-by-field comparison (which will find the position/path change). For non-movers, the existing digest fast-path is unchanged.
- **Entity→id bridging:** `movers` stores `hecs::Entity` handles; the delta loop keys by `u.id` (String `"unit_{eid}"`). To check membership:
  - (a) Build a `HashSet<u32>` from `movers.iter().map(|(e,_,_)| e.id())` and extract the numeric id from `u.id` (strip `unit_` prefix, parse), **or**
  - (b) Add a `#[serde(skip)] entity_id: u32` field to `UnitState` to avoid string parsing.
  - This is a small standalone task, not a one-liner.
- **Reuse:** `MovementScratch.movers` (movement.rs:40) — already populated, already owned by `Game`.
- **Correctness:** strictly safe. Only skips a redundant compare for units known to have changed. Every non-mover still goes through the full digest path. No change is ever omitted.
- **Expected win:** saves 2 × `from_unit` (each sums equipment Vec) + 1 struct compare per mover. ~50-100 movers × ~200 ns ≈ 10-20 µs. Modest.
- **Risk:** low, but adds a parameter and a `contains` check per unit.
- **A/B:** yes. **Recommendation: defer unless W-1/W-2/W-3 are insufficient.** Win is ~10-20 µs on a 819 µs avg — < 3 %. Coupling cost (threading `movers` into the network phase, keeping it in sync) not justified at this scale. Revisit if unit counts grow 10× or if the digest compare becomes a measured bottleneck after Phase 1.

**W-6 (DO-NOT-DO): Rayon per-player deltas**
- Do not implement. Document in `delta.rs` module doc (already present at line 14) and in this spec:
  - Rayon was trialed and removed. W2_ENCIRCLEMENT.md run 14: per-player parallel flood → 10 % slower microbench, +18 % real-game p2_bfs, P99 unchanged, allocs 21→89 (+7×).
  - Per-player network work is ~0.2 ms normal / ~0.5 ms grid-change. Below rayon's dispatch breakeven.
  - The "embarrassingly parallel" structure is real but the work is too small. The correct optimization is to *reduce* the work (W-1, W-2) rather than *spread* it.

**W-7 (DEFERRED): Full dirty-set pass-through replacing snapshot diff**
- Present as a tracked alternative. Completeness checklist (every writer must call `touch(id)`):
  1. `movement.rs` — `movers` ✅ (already exists)
  2. `combat.rs:546-547` — `fought.insert` ✅ (already exists)
  3. `combat.rs:170, 854` — `attacking` flag clear ❌ (not in `fought`)
  4. `supply.rs:195-355` — men/org/equipment over ALL units ❌ (no dirty set)
  5. `water.rs` apply pass 2 — `changes` ✅ (already exists)
  6. `encirclement.rs:301-302` — `encircled` flag over all units ❌ (no dirty set)
  7. `death_cleanup.rs:22+` — `dead_set` ✅ (already exists)
  8. `game_server.rs:518-525` — `toggle_healing` / `toggle_resupply` ❌ (no hook)

- Grids: whole-rebuilt each influence tick (influence.rs:357-435), no incremental dirty-region signal. A dirty-region grid scheme would re-do the 40 KB compare.
- **Recommendation: DO NOT implement unless Phase 1 (W-1/W-2/W-3) leaves the snapshot cost as the dominant alloc source (verify by A/B). Even then, implement incrementally (one system at a time) with a debug-assert that cross-checks the dirty set against the full snapshot diff in debug builds.**
