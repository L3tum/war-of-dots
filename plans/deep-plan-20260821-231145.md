## 4. Recommendations, ranked by effort/risk

### R1 — Free win, zero risk: branchless `|=` in `union_vision_grids`

- **Change:** `src/game/game.rs:1530` — replace
  ```rust
  if grid[i] {
      result_flat[i] = true;
  }
  ```
  with
  ```rust
  result_flat[i] |= grid[i];
  ```
- **Why safe:** `bool` OR is monotone and idempotent; the outer loop OR-accumulates each player's grid into an all-false `result_flat`, so per-cell final state is bit-identical (review-verified). Same shape as `supervisor_vision_grid` (game.rs:1458), which already auto-vectorizes to 256-bit.
- **Caveat:** this is a client-vision view path (only called from `server/game_server.rs` view handlers), not the per-tick hot loop — the absolute win is small; its value is (a) trivial + zero-risk, (b) a second auto-vectorized proof point, (c) an end-to-end test of the R2 asm workflow.
- **Verify:** emitted asm for `Game::union_vision_grids` shows `vpor`/`vorps` on `ymm`; `make test` green (vision/union semantics unchanged).

### R2 — Process fix: rewrite `scripts/check_vectorization.sh`

**Root cause of current breakage** `[OPEN]`: the script currently passes **vacuously** (it reports "not found" for the symbols it checks, so no FAIL ever fires). The RESEARCH phase hypothesised a **stripped** release binary (no symbol table → `objdump -d` emits no function labels → the awk boundary extractor matches nothing → every `FUNCS` entry is "not found").

**That stripping hypothesis is unconfirmed and is contradicted by the config** (review SHOULD-FIX-1): `Cargo.toml` has **no `[profile.release]` / `strip`**, and `.cargo/config.toml` sets only `rustflags = ["-C","target-cpu=x86-64-v3"]`; Cargo's default for `profile.release.strip` is *off*, so a plain `cargo build --release` normally **retains** its symbol table. The more probable cause is that the awk label matcher (`/<.*>:/` + the `FUNCS` regexes) does not match the actual **mangled** symbol names (the newer `_R…` scheme does not surface a bare `run` token), compounded by the deleted `nearby_enemies.*run` entry. **The actual cause must be confirmed empirically in S0/S1.1 first** (`nm -s target/release/war-of-dots | wc -l`, `file target/release/war-of-dots`, `objdump -t target/release/war-of-dots | head`).

The old plan's §2 defects (loose `ymm` substring regex matching struct copies; `FUNCS` missing the symbols that matter) remain as **independent** defects that would bite on any unstripped artifact.

Changes (all in `scripts/check_vectorization.sh`; Makefile target `check-vectorization:` at `Makefile:56` unchanged):

1. **Source of truth = rustc-emitted asm, not the built binary.** `cargo rustc --release --lib -- --emit asm` (the lib `war_of_dots` contains every hot game loop; avoids building the three bin targets — `war-of-dots`, `console_client`, `generate_schema`). The emitted `.s` **always** retains per-function labels regardless of binary stripping, so per-function boundary extraction is robust — this is why the fix stands even if the stripping diagnosis is wrong.
   - **Emit-asm mechanics `[OPEN]`:** confirm the toolchain's `--emit asm` output location (default: under `target/release/deps/*.s`) and the `.s` label format (mangled; possibly new `_R…` scheme). Adjust the label matcher empirically — **this is the main implementation risk of R2**. Confirm whether `--emit asm=<custom path>` is honoured through `cargo rustc` (else glob the newest `target/release/deps/*.s`).
   - `build.rs` runs `npm run build` unconditionally → the script **requires node/npm** (same pre-existing prerequisite as `build-release`). On any cargo failure the script must **fail loudly, never silently pass**.
2. **Fix `FUNCS`:** drop `nearby_enemies.*run` (file deleted `[SRC]`); keep `influence.*run`; **add** `for_each_within`, `movement.*run`, `GridIndex.*build`.
3. **Tighten `AVX_RE`** to require vector *arithmetic* on a wide register on the same line, e.g.:
   ```
   (vaddps|vsubps|vmulps|vdivps|vminps|vmaxps|vcmpltps|vroundps|vpadd|vpmax|vpmin|vpor|vorps).*(%ymm|%zmm)
   ```
   (must cover `GridIndex::build`'s actual op set — `vdivps`/`vroundps`/`vpminsd`/`vpmaxsd` — so the positive control passes; `vpmin`/`vpmax` substring-match `vpminsd`/`vpmaxsd`; excludes plain `vmovdqu` copies.)
4. **Two-list semantics** so "correctly scalar" loops don't turn the script red:
   - `EXPECT_VECTOR`: `GridIndex.*build` (passes today — positive control) and, after R1 lands, `union_vision_grids`.
   - `REPORT_ONLY`: `for_each_within`, `movement.*run`, `influence.*run` — print scalar/vector status as a diagnostic, don't fail.
   - Default: print per-function verdict table, exit 0. `--strict`: exit 1 if any `EXPECT_VECTOR` function lacks vector math or is missing from the asm.
   - Update the header comment: explain the vacuous-pass cause and the emit-asm workflow; keep the "positive = evidence, negative = meaningful" caveat.
- **Why safe:** no game-code change.
- **Verify:** run `make check-vectorization` → expect `GridIndex::build` ✓ vector math; `influence`/`movement`/`for_each_within` ✗ scalar (reported, not failing); exit 0. After R1: `union_vision_grids` ✓.

### R3 — Top payoff: `fold_influence_into` (gated on measurement)

`fold_influence_into` (`influence.rs:262–268`) runs the **full map grid per player on every dirty influence tick** (`INFLUENCE_TICK_INTERVAL = 3`, `constants.rs:10`) — the largest remaining scalar numeric loop in the game code.

**Step A — branchless-select rewrite (zero new dependencies).** Replace the branch with a select so LLVM *might* auto-vectorize on stable:

```rust
#[inline]
fn fold_influence_into(dominant: &mut [u8], max_inf: &mut [u16], grid: &[u16], idx: u8) {
    let idx_u32 = idx as u32;
    for i in 0..dominant.len() {
        // Branchless select; preserves the strict-`>` tie-break (lowest-sorted
        // player wins) — take == 0 keeps the current accumulators.
        let sel = 0u32.wrapping_sub(u32::from(grid[i] > max_inf[i])); // 0 or !0
        max_inf[i] = ((max_inf[i] as u32) & !sel | (grid[i] as u32) & sel) as u16;
        dominant[i] = ((dominant[i] as u32) & !sel | idx_u32 & sel) as u8;
    }
}
```
**Review-verified bit-identical** to the original `if grid[i] > max_inf[i] { max_inf[i] = grid[i]; dominant[i] = idx; }`: `0u32.wrapping_sub(u32::from(cond))` yields a clean `0`/`!0` mask; `x & !sel | y & sel` selects `y`(= `grid[i]`) iff `grid[i] > max_inf[i]`. Strict `>` **preserves the lowest-sorted-player-wins tie-break**; the **NONE = 255** sentinel is preserved (a cell is only written when `grid[i] > max_inf[i]`, which is never true at `0` vs `0`, so untouched cells stay NONE); `as u8` truncation is lossless (both operands `< 256`). It survives default `make clippy` (`cast_possible_truncation` is not default-on). Keep `#[inline]` so the vectorized code stays inside the `influence.*run` symbol the script inspects.
**[OPEN]:** whether LLVM actually vectorizes the mixed u16/u8 select on stable rustc 1.96 is unresolved until built. Re-check codegen either way.

**Step B — glam hand-SIMD (only if Step A stays scalar AND the benchmark justifies it).** Library decision carried from old §4.3: **`glam`** (stable, no feature gate; rejected: `std::simd`/`portable_simd` nightly, `wide` weaker maintenance, `cgmath` wrong tool). Add `glam` to `Cargo.toml`. Implementation notes: glam has **no native 16-lane u16 type** (it ships only f32/f64/u32/i32 V2/V3/V4) — pack two u16 per `UVec4` lane (8 u16/vector → two vectors per 256-bit step) with per-half compare/select via 16-bit masks; the u8 `dominant` select runs 32 lanes per 256 bits through a bitcast. Scalar fallback tail for non-multiple lengths. **~50–80 lines.** Add a randomized equivalence test against the scalar loop alongside the existing fold unit tests (`influence.rs:780–794`) and the `build_territory_grid` tests (`influence.rs:667` / `:713`).

**Why safe (both steps):** pure per-element function; determinism contract (strict `>` tie-break → lowest-sorted player wins; `NONE = 255` sentinel untouched) is preserved exactly.

**Verify:** `systems/influence_100` / `influence_500` / `influence_100_skip` microbenchmarks before/after; emitted asm for `influence.*run` shows vector select ops (`vpcmp`/`vand`/`vpor`/`vp*` on `ymm`); full `make test` (territory/encirclement tie-breaks are determinism-sensitive).

### R4 — Demoted: `for_each_within` two-phase (SIMD mask → gather → call `f`)

Carried from old §4.4, **demoted to "measure first, likely not worth it"**:

- Call sites are now exactly 2 production: movement occupancy gate (`movement.rs:161`, self-exclusion only) and combat target acquisition (`combat.rs:256`, running-min + id tiebreak). The old 4-monomorphization picture (incl. `nearby_enemies`) is gone.
- Cell occupancy is **O(1)** by the `MIN_UNIT_DISTANCE = 8` / `SPATIAL_CELL_SIZE = 10` rules (`constants.rs:21–32`): a 3×3 scan touches a small slice (≤ 9 entries per cell, typically far fewer), so SIMD setup cost may not pay back at realistic densities.
- The combat callback is *less* SIMD-favorable than the deleted `nearby_enemies` one: per-hit running-min + id tiebreak is a data-dependent scalar chain — even a masked filter only accelerates the *miss* distance tests, not the hits.
- `CellEntry` (`spatial.rs:23`) is interleaved `(x, y, …)`: 4-wide `f32` lanes need an **SoA split** (separate x/y arrays) or per-load `vpermilps` shuffles — a buffer-layout change touching `GridIndexScratch`, the builder (`movement::populate_grid_units`, movement.rs:249), and the benchmark fixtures (microbenchmarks.rs:576–581). Not "just add intrinsics".
- **Decision:** add a dedicated `spatial/for_each_within_*` microbenchmark id (none exists today; `systems/combat_50pairs` / `combat_200pairs` / `movement_500` / `movement_2000` only exercise it indirectly) and measure first. If it is a meaningful slice of movement/combat time at realistic densities, write a separate follow-up plan for the SoA restructure. Otherwise document and stop.

### R5 — Measure-first (per review feedback): supply — optimistic-vector + rare-scalar-rollback

The old verdict dismissed supply as order-dependent FCFS. Reconsidering: supply has **two** FCFS pool gates — equipment funds (`supply.rs:258–260`) and manpower men-refill (`supply.rs:280–282`) — and each is order-sensitive **only at the pool-exhaustion boundary**. When a player's pool comfortably covers its army's total demand, *every* unit is funded regardless of order → the batch is order-independent and safe to vectorize/parallelize. The exhaustion case (pool < total demand) is the rare path where FCFS order actually matters (a player's pool usually funds most of its army, so the boundary is uncommon).

**Approach (preserves determinism exactly):**
1. Compute each unit's demand (`plan_delivery_into` cost for funds; `recruitment_rate.min(max_men − men)` for men) — per-unit and independent of other units.
2. **Fast path (vector/parallel):** if `remaining_funds[oi] >= total_cost` **and** `remaining_mp[oi] >= total_men`, fund *all* of the player's units (order-independent, deterministic); SIMD/parallelize the apply.
3. **Rollback path (rare):** if the pool does *not* cover the batch, fall back to the exact existing scalar FCFS for that player — byte-identical boundary ordering.
4. **Heuristic:** pick fast vs rollback by comparing the pool to the batch total (the "roll back once it gets above `remaining_funds`" idea). The scalar path is the fallback that guarantees FCFS semantics.

**Caveats / measure first:**
- `plan_delivery_into` (`supply.rs:113`) has a variable-length per-slot loop (0–4 slots) with `f32` ceil + `SmallVec` writes — the *cost computation* is not trivially SIMD; the vectorizable surface is the men-refill + fund-apply/gating aggregate, not necessarily the per-slot cost loop.
- Per-unit work is spread across many independent units of one player — **rayon (data parallelism)** may be a more natural win than SIMD here, but the SIMD-with-rollback framing is valid for the aggregate. Decide SIMD vs rayon after measuring.
- No supply microbenchmark id exists today; the per-tick cost of supply vs combat/movement is unmeasured.
- Determinism is the hard constraint; the fast path must be provably order-independent (it is when the pool covers demand).

**Verify:** add a `systems/supply_*` microbenchmark id (dense army; add a constrained-pool case to exercise the rollback path); a randomized equivalence test fast-path vs scalar FCFS (must be bit-identical in **both** the covered and the exhausted cases); `make test` (economy/supply determinism).

### R6 — Measure-first (per review feedback): city_capture — SoA + vectorized distance + deterministic winner

Reconsidering: the inner loop (units × ~20 cities, `dist_sq = dx*dx + dy*dy < CAPTURE_RANGE_SQ`, non-owner) at `city_capture.rs:47–63` is a genuine per-(unit,city) numeric surface. The old plan dismissed it as "marginal f32 FMA," but the SoA restructure may make sense.

**Approach:**
- Split unit positions into SoA (separate x / y arrays) so the per-city distance test over units vectorizes (4-wide `f32` lanes: `dx²+dy² < CAPTURE_RANGE_SQ` mask).
- Winner selection: currently "last qualifying unit per city wins" via `BTreeMap` insertion order (`city_capture.rs:58`) — deterministic but order-dependent. A vectorized version must reproduce this exactly: reduce the qualifying mask to the *deterministic* winner (highest qualifying index/iteration), **not** `any-in-range`.
- Cities are few (~20) but units can be many, so a per-city vectorized scan over the unit array is the SIMD shape.

**Caveats / measure first:**
- The per-city scan is only as long as the unit count; if armies are small the win is small. Measure whether city_capture is a meaningful tick slice before the SoA restructure.
- The deterministic winner reduction is the tricky part — a naive SIMD `any-in-range` would change *which* player captures on ties.
- No city_capture microbenchmark id today.

**Verify:** add a `systems/city_capture_*` id (dense units on contested cities); a randomized equivalence test vs the scalar `BTreeMap` winner (must pick the same owner in all tie cases); `make test` (capture determinism / `player_stats.cities_captured`).

### R7 — Measure-first (per review feedback): encirclement — wave-parallel BFS / parallel flood-fill

The old verdict dismissed encirclement because "the BFS dominates." Reconsidering: the flood-fill (`encirclement.rs` `run` @50, BFS core @109–121) is a full-grid multi-player BFS over `safe: Vec<u8>` / `dominant: &[u8]`, and there are real vectorization angles.

**Frequency context (why influence is still #1):** the user's intuition that **encirclement + influence are the best structural opportunities is correct**. But note the asymmetry: **influence runs every 3 ticks** (R3, `INFLUENCE_TICK_INTERVAL`) while **encirclement runs every 30 ticks** — influence is ~10× more frequent, so it remains the top *absolute* target; encirclement is next.

**Approach options (concrete, not hand-wavy):**
1. **Wave-parallel BFS (parallel flood-fill)** — the standard technique (Cleve-Moler / Mark Harris "fast and efficient parallel BFS"): replace the sequential work-queue (`while qhead < queue_buf.len()`, encirclement.rs:109–121) with **synchronous waves**. Each wave, over the *entire grid array*, claim every unclaimed neighbor of the current frontier in lockstep using SIMD masks (`dominant[n] == pidx && safe[n] == NONE` → claim + add to next-wave frontier). Per-cell ops become vectorized grid-array masks; the frontier becomes a `Vec<u8>` "is-frontier" buffer (SIMD over it) rather than a scalar `usize` queue. Wave count is bounded by the map's cell-diameter (a few dozen), so the scalar-equivalent work is `O(waves × grid)`, but each wave is SIMD-parallel — a realistic win on a large map. This is an algorithm restructure, not "add intrinsics."
   - Trade-offs: waves can re-examine frontiered cells (needs a claimed/frontier mask to prevent double-claims); termination is a vectorized `any` over the frontier ("did this wave claim anything new").
2. **Cheaper wins (no restructure):**
   - **Seed scan** (encirclement.rs:103–106): a full-grid per-element predicate — vectorize the *count* (compare + popcount) to pre-size the queue even if the enqueue stays scalar.
   - **Per-unit encirclement flag** (encirclement.rs:127–138): `encircled = dominant[idx]==pidx && safe[idx]!=pidx` per unit — a per-unit u8 compare over the (small) unit array, vectorizable if units are SoA. Short/low-payoff but trivial.

**Caveats / measure first:** no encirclement microbenchmark id today; the flood-fill cost depends on map size + frontier shape. Measure the BFS slice of the every-30-tick strategic pass before committing to the wave-parallel restructure.

**Verify:** add a `systems/encirclement_*` id (large map, dense contested territory → long frontiers); a randomized equivalence test wave-BFS vs queue-BFS (identical `encircled` flags for all units); `make test`.

## 5. Explicitly NOT worth SIMD (reclassified after review)

Combat and death_cleanup stay out of SIMD scope (with corrected reasoning below); **supply and city_capture were reclassified as measure-first candidates (R5/R6)** after review pushback.

- **`combat`** — the per-pair damage math (base1/base2/eff/dmg/men, `combat.rs:445–503`) is **scalar per-pair f32, not auto-vectorized**, and *cannot* be auto-vectorized: each engagement is a branchy scalar chain (mutual vs one-way, equipment, terrain lookups) with per-pair `world.get` borrows and a sequential `men` dependency (iteration N reads iteration N−1's writes). There is no contiguous array of independent tuples to map. Vectorizing it would require the SoA + no-ECS-borrow restructure combat deliberately avoids (it is allocation-free + sequential by design). Re-confirmed on Site 1 (combat.rs:218–281) and resolution (combat.rs:319+).
- **`death_cleanup`** — **corrected reasoning (review):** the "order-preserved despawn" is **not** a real constraint — every unit that died within a tick has already gone through all processing, so the order in which dead entities are despawned is unobservable. That is, order-preservation is not what rules out parallelism here. death_cleanup is still **not an SIMD target for a different reason**: its cost is `hecs` despawn + `HashMap`/`HashSet` ops over entities (death_cleanup.rs:39–80), not a numeric array loop — there is no vectorizable math. A *parallel* despawn (rayon) was considered and rejected: hecs `World` despawn is the cost (not math), and the site-3 target-clear needs the complete `dead_set` built first anyway.
- **`encirclement`** — **reclassified → R7** (wave-parallel BFS / parallel flood-fill; the seed-scan and per-unit encirclement-flag sub-loops are also vectorizable). Measure-first; influence (R3) remains the higher-frequency top target.
- **`water`** — **corrected (review):** the embark/disembark countdown (the only numeric op — a per-unit `u32` decrement + `==0` completion check in `compute_water_change`) *is* vectorizable **in principle** if units were SoA — but it applies to a small, rare transition subset (few units embark/disembark per tick) and is gated behind ECS-scatter + the two-phase change buffer + per-entity `query_one_mut` apply. The bulk of units take the `TerrainCheck` branch (a scattered `terrain_at` lookup — a memory access, not vectorizable math). So: **low payoff today**, not "cannot"; revisit only if unit-transition density or the two-phase structure changes.
- **`surrender` / `delta`** — no dense numeric loop surface.
- ~~`supply`~~ — **reclassified → R5** (optimistic-vector + rare-scalar-rollback, measure-first).
