# Deep Plan: death_cleanup — drop the world-wide NearbyEnemies retain pass

*RESEARCH: plans/research-deep-plan-death-cleanup.md. REVIEW-PLAN: APPROVE-WITH-CHANGES (applied). Revision 1: combat lazy stale-deletion + nearby_enemies TODO (user feedback). **Revision 2 (this): core redesign per user feedback — death_cleanup performs a proper targeted reverse-lookup purge through the dead unit's own list, instead of tolerating stale entries; the percentile window fix and the stale game.rs comment fix are now in scope.***

## Context

### The problem (reports/stress_5.html, 1500 ticks, seed 42, 1000×1000 map)

- `death_cleanup`: **10 905.1 ms total, 6.415 ms avg/call, P99 34.498 ms** vs 15.9 ms average tick — by far the biggest system contributor during heavy combat.
- Root cause: on any tick with ≥1 death, `run()` (src/game/systems/death_cleanup.rs:43-45) does `nearby.entities.retain(|e| !dead_set.contains(e))` over **every** `NearbyEnemies` list in the world — ~588 146 entries (`health_avg_total_nearby_entries`), held by 577 units at ~1 019 entries each in dense melees (9 764 units; ~9 190 empty SmallVecs). That is O(all entries) per death-tick while the actual despawn work is µs-scale (microbench: 5.81 µs for 200 units / 50 deaths ≈ 0.1 µs per death, and that microbench never even had NearbyEnemies populated — see R6).
- No-death ticks hit the early return at death_cleanup.rs:27-29 (~0 ms); deaths occur on ~21% of ticks (10 905 ms / ~30 ms per death-tick / 1700 calls). P50/P99 (29.7 / 34.5 ms) describe the last-200-call window where a majority of ticks had deaths.
- Allocs are not a factor (16 allocs / 8 900 B over the whole run; scratch `clear()` preserves capacity).
- Secondary issues found along the way (now in scope per user feedback): (a) `record_system_timing` caps `durations_ms` at 200 entries, so report P50/P90/P99 are **last-200-calls only, not run-wide** (src/game/debug_stats.rs:206-209; same pattern at :88-90, :126-128, and src/game/world_ext.rs:153-155); (b) stale comment at src/game/game.rs:758 — "brute-force rebuild" describes the pre-grid architecture.

### Why the reverse lookup works (the key structural fact)

`nearby_enemies` (src/game/systems/nearby_enemies.rs:199-295) builds lists from a single grid snapshot per tick: a unit's list = every **enemy-owner** unit within `COMBAT_RANGE` (2.0), self excluded, `dist² < COMBAT_RANGE_SQ`. This relation is **symmetric** (same snapshot, symmetric distance predicate, cell size = range so the 3×3 query is exact): if U's list contains D, then D's list contains U. Lists are therefore **fresh and symmetric at death_cleanup time** (movement ran before the rebuild; no system moves units between the rebuild and cleanup — combat only deals damage and sets flags). Tick order: movement → (tickcontext) → **nearby_enemies → combat** → supply → city_capture → influence → encirclement → surrender → **death_cleanup** → track_unit_losses (src/game/game.rs:688-920).

Consequence: for a dead unit D, the set of units that reference D in their own lists is **exactly `list(D)`** — D's own `NearbyEnemies`. So cleaning up all references to D requires touching only the units in D's own list, not the whole world.

### Cost model (why this is never worse, usually far better)

- **Current (flat)**: any death tick pays O(Σ_all |list|) ≈ 588k retains ≈ ~30 ms.
- **New (targeted)**: C = union of the dead units' own lists (deduped); cost = O(Σ_{U∈C} |list(U)|) + O(|C_raw|) hash ops. Since C ⊆ {units with non-empty lists}, **the new cost is always ≤ the flat cost** (worst case: the dead units sit in the densest cluster and C covers every non-empty list — equal to today). Typical case (deaths in sparse terrain, where the 10k units average ~60 entries/unit): a dead unit touches a few dozen neighbors × a few dozen entries each — one to two orders of magnitude less than 588k.
- This is also the **right cleanup for the planned future** where `nearby_enemies` stops rebuilding everything every tick: the dead unit's own list is the natural, bounded reverse index.

### Expected payoff

- death_cleanup total drops from 10 905 ms to the targeted work (bounded above by the current cost; the actual reduction is visible in stress_6 — candidates are only units adjacent to the ~8.6 dead/tick, not all 577 combat units).
- Report P50/P90/P99 become run-wide (percentile fix) and death_cleanup's fall with the targeted work.
- Resulting list state after cleanup is **bit-identical** to today's under the current fresh-lists architecture (see determinism note in Approach 1), so `units_remaining` (8 775) and all gameplay rows must match stress_5 under seed 42.

## Approach

**Recommended design: targeted reverse-lookup purge in death_cleanup + run-wide percentile histograms + comment fixes.**

1. **Rewrite `death_cleanup::run` to purge via the dead units' own lists.** New body (signature unchanged — `scratch` stays, and its shape grows):
   ```rust
   pub fn run(
       world: &mut hecs::World,
       dead_lists: &[&[hecs::Entity]],
       entity_reverse: &mut HashMap<hecs::Entity, String>,
       scratch: &mut DeathCleanupScratch,
   ) -> usize {
       if dead_lists.iter().all(|l| l.is_empty()) { return 0; }
       let dead_count: usize = dead_lists.iter().map(|l| l.len()).sum(); // do NOT dedupe (keep comment)

       // 1) dead_set of everything dying this tick (multi-list safe)
       scratch.dead_set.clear();
       for list in dead_lists { for e in *list { scratch.dead_set.insert(*e); } }

       // 2) Reverse lookup: candidate units = union of the DEAD UNITS' OWN lists.
       //    Fresh symmetric lists guarantee: U references D  ⟹  D's list contains U.
       //    (lists must be read BEFORE despawn — components vanish with the entity)
       scratch.candidates.clear();
       scratch.seen.clear();
       for list in dead_lists {
           for dead in *list {
               if let Ok((nb,)) = world.query_one_mut::<(&NearbyEnemies,)>(*dead) {
                   for &u in nb.entities.iter() {
                       if scratch.seen.insert(u) { scratch.candidates.push(u); }
                   }
               }
           }
       }

       // 3) Targeted purge: one retain per candidate (skip dying units — they're despawned)
       for &u in scratch.candidates.iter() {
           if scratch.dead_set.contains(&u) { continue; }
           if let Ok((nb,)) = world.query_one_mut::<(&mut NearbyEnemies,)>(u) {
               nb.entities.retain(|e| !scratch.dead_set.contains(e));
           }
       }

       // 4) Despawn + entity registry (unchanged from today)
       for list in dead_lists {
           for dead in *list {
               entity_reverse.remove(dead);
               world.despawn(*dead).ok();
           }
       }
       dead_count
   }
   ```
   `DeathCleanupScratch` becomes `{ dead_set: HashSet<Entity>, candidates: Vec<Entity>, seen: HashSet<Entity> }` — all grow-only, `clear()`'d per run (capacity preserved, same pattern as today's `dead_set`).
   - **Prominent invariant comment** at the new step-2/3 code: (a) fresh symmetric lists ⇒ `list(D)` exactly covers the units referencing D (nearby_enemies builds all lists from one grid snapshot; symmetric distance predicate); (b) the reverse lookup depends on that freshness — if `nearby_enemies` ever becomes conditional (see its TODO), a dead unit's own list may miss a unit that one-sidedly references it; such a stale entry is then tolerated by combat (`world.get::<&UnitPosition>` → `Err` → `continue`, combat.rs:274-277) and removed by the next rebuild — but under the current unconditional rebuild, lists are always fresh, so the purge is exact and the after-state is bit-identical to the old flat retain; (c) hecs generations make any stale `Entity` unmatchable (despawn bumps generation; a reused index has a different generation; `world.get` on the old value → `Err`).
   - Determinism: for each unit U and each dead D: `D ∈ list(U)` ⟺ (fresh lists) `U ∈ list(D)` ⟺ `U ∈ C` ⟺ `D` is retained out of `list(U)`. The new code removes exactly the same (U, D) pairs as the old flat retain ⇒ identical world state after the system, same `dead_count`, same despawn order.
   - Module docs (lines 1-6): replace item 1 ("Clean NearbyEnemies references (single pass, O(total entries) amortized)") with: "Purge dead units from the NearbyEnemies lists of the units that reference them — via the dead units' own lists (reverse lookup), O(sum of dead units' neighborhood sizes), not O(all lists)."
   - The top-level `use crate::game::components::NearbyEnemies;` (:9) **stays** — it is used by the non-test `query_one_mut` calls in the new body.
2. **Fix the report percentile window to be run-wide** (src/game/components.rs:279 `SystemTimings`, src/game/debug_stats.rs, src/game/world_ext.rs). Replace the 200-entry `durations_ms` ring (and its O(n) `Vec::remove(0)`) with a bounded **run-wide log histogram**:
   - `SystemTimings`: remove `durations_ms: Vec<f64>`; add `hist: [u32; 24]` with `pub const HIST_BUCKETS: usize = 24` — 3 log₁₀-spaced buckets per decade covering 0.001 ms … 10 s: bucket `i` covers `[0.001·10^(i/3), 0.001·10^((i+1)/3))` ms; durations below the first edge clamp to bucket 0, `≥ 10 s` clamp to bucket 23. (96 bytes per system entry — bounded for arbitrarily long live sessions, unlike storing raw durations.)
   - Add `impl SystemTimings { pub fn record(&mut self, duration_ms: f64) }` — one place updating `total_ms`, `call_count`, `last_ms`, `avg_ms` and the histogram bucket (index via `((duration_ms.log10() + 3.0) * 3.0).floor() as usize` clamped to 0..24). All four record sites collapse to `entry.record(duration_ms)`: `debug_stats.rs` `DebugStatsGuard::record_system` (~:72-95), `record_detailed` (~:102-131), free fn `record_system_timing` (~:183-212, used by `tick_system!`), and `world_ext.rs` `WorldExt::record_detailed` (~:144-159).
   - Add `pub fn hist_percentile(hist: &[u32; 24], p: f64) -> f64` (debug_stats.rs): rank = `p × Σhist`; walk buckets; return the **upper edge** of the first bucket where the cumulative count reaches the rank; 0.0 if empty. Document semantics: run-wide; value is a bucket edge, so it overestimates the true percentile by at most the bucket factor (10^(1/3) ≈ 1.21).
   - `get_debug_stats` (debug_stats.rs:240+): both percentile blocks (`system_timings` ~:258-276, `detailed_timings` ~:296-314) switch from clone+sort+index to `hist_percentile(&timing.hist, 0.5|0.9|0.99)`. JSON keys `p50_ms`/`p90_ms`/`p99_ms` **unchanged** — the benchmark delta code (benchmark.rs:1168-1249) reads the same keys.
   - Consumers of the raw ring verified: none — `durations_ms` is read only in `get_debug_stats` (grep of src/ and frontend: only the benchmark's own separate `overhead_durations_ms`/`tick_durations_ms` arrays exist, built from the benchmark's own tick pool, not this ring).
   - Note for interpreting stress_6: percentiles are now **run-wide bucket edges** vs stress_5's exact last-200 values — Total/Avg/Calls columns are unaffected and remain the primary comparison axes.
   - `DebugStats.tick_durations_ms` (100-entry cap, debug_stats.rs:63-66, raw JSON for the overlay) is a **separate** field the benchmark doesn't use for percentiles — left as-is (follow-up note).
3. **Add the nearby_enemies TODO + invariant doc** (per earlier user feedback; still needed). Verified finding: the unconditional full rebuild is a *conservative design choice, not a hard requirement* — lists only need to be fresh before combat reads them; a unit's list can only change if it moved, a unit in its 3×3 neighbourhood moved/spawned, or an enemy died. A moved-only/dirty-cell rebuild is feasible as a follow-up with real subtleties: (i) refresh when *any* neighbour changes (dirty-cell bookkeeping); (ii) units recruited between ticks lack `NearbyEnemies` — detect for first-time insert; (iii) under a conditional rebuild, a neighbour's death (no movement) can leave a stale one-sided entry — safe because death_cleanup's reverse lookup covers the fresh case and combat tolerates the stale case (`world.get` → `Err` → `continue`); (iv) the `attacking` flag is set for movers only (nearby_enemies.rs:~296-300) and is sticky for non-movers — a dirty rebuild must not change that. **Doc-only change in this plan** (behavior unchanged): module doc and/or a comment above `pub fn run` (:199) stating the invariant (full per-tick rebuild guarantees combat reads fresh lists; death_cleanup's reverse lookup depends on list freshness/symmetry — see death_cleanup.rs) plus a **TODO: moved-only/dirty-cell rebuild** (~4.3 ms/tick on the table; must preserve pre-combat freshness or lean on combat's stale tolerance).
4. **Fix the stale comment at src/game/game.rs:758** (per user feedback): "NearbyEnemies: brute-force rebuild of enemy adjacency lists." → "NearbyEnemies: spatial-grid rebuild of enemy adjacency lists (CELL_SIZE 2.0 = COMBAT_RANGE, 3×3 cell query, O(n × c))." Also refresh the death_cleanup call-site comment (~:894-897) to mention the targeted reverse-lookup purge.
5. **Microbench fixture fix** (R6): `DeathCleanupFixture::new` (microbenchmarks.rs:776-795) spawns via `world.spawn_unit`, which omits `NearbyEnemies`, and `setup_nearby_enemies` (microbenchmarks.rs:472) is never called — so `systems/death_cleanup_50` today never exercises the cleanup pass. New baseline expected (was 5.81 µs).

**Superseded (from revision 1, dropped):** combat lazy stale-entry deletion. With a *proper* (exact) cleanup in death_cleanup, stale entries do not exist under the current architecture, so a combat-side scavenger would be dead code that only ever runs in the future conditional-rebuild scenario — revisit it together with that rebuild redesign, not now. (It was added in revision 1 to serve the stale-1-tick-by-design approach, which revision 2 replaces.)

**Alternatives considered** (research §6 + revisions): flat world-wide retain (status quo — O(all entries) per death tick); reverse *index* maintained incrementally by nearby_enemies (≈588k map inserts/tick — likely *more* cost than the flat retain it would replace, plus sync-bug surface; the dead unit's own list is a free, always-fresh-per-tick reverse index instead); tombstoned units (moves the O(all entries) cost into a system running 100% of ticks; query over-counts).

## Risks & mitigations

- **R1 — reverse-lookup coverage assumes fresh symmetric lists (low under current architecture).** The coverage proof (U references D ⟹ D's list contains U) holds because nearby_enemies builds all lists from one snapshot with a symmetric predicate, and positions don't change between rebuild and cleanup. It would weaken if the rebuild becomes conditional — the TODO in nearby_enemies.rs names this dependency explicitly, and the stale one-sided entry is safe anyway (combat's `world.get` Err → continue; hecs generations prevent aliasing). Mitigation: the `stale_one_sided_reference_survives_is_safe` test documents and pins both the limitation and the safety property.
- **R2 — worst case equals today's cost (no regression).** C ⊆ units with non-empty lists ⇒ targeted work ≤ flat work. Mitigation: stress_6 `death_cleanup` Total must be ≤ 10 905 ms; flag any increase as a bug.
- **R3 — determinism (low).** The new purge removes exactly the same (U, D) pairs as the old flat retain under fresh lists ⇒ identical after-state ⇒ identical combat ⇒ identical `units_remaining` under seed 42. Mitigation: Verification row — any gameplay-row mismatch is a coverage bug.
- **R4 — percentile semantics change (report interpretation).** stress_6 P50/P90/P99 are run-wide bucket edges vs stress_5's exact last-200; deltas for percentile columns are apples-to-oranges across the two reports. Mitigation: Total/Avg/Calls remain the primary axes (noted in the report interpretation); `hist_percentile` tests pin the computation; ≤×1.21 overestimate documented on the struct and in get_debug_stats.
- **R5 — `durations_ms` removal (low, verified).** No consumer outside the four record sites + `get_debug_stats` (grep of src/ and frontend: the benchmark's `overhead_durations_ms`/`tick_durations_ms` are separate arrays). `SystemTimings` derives only Debug/Default/Clone — no serde/save-file impact. Mitigation: build + tests.
- **R6 — test breakage (certain, contained).** Only `cleanup_removes_dead_from_nearby_enemies` encodes the old mechanism; rewritten in Step 2 with a symmetric setup.
- **R7 — microbench baseline moves (verified).** The fixture never had lists, so the row was unrepresentative; now it exercises the real path. New baseline noted in Verification.
- **R8 — pre-existing, not worsened:** `owner_id_by_entity` / `entity_registry` unbounded growth (Scope 3-4); `tick_durations_ms` 100-cap (Scope 5).
- **R9 — hecs generation semantics (standard, not locally source-verified).** Relies on hecs 0.11 bumping generations on despawn. High confidence (standard hecs 0.11.1 behavior; crate source not in local registry cache). Mitigation: the generation non-aliasing assertions in Step 2's new test encode the property and would fail if it were different.
