# Deep Plan — War of Dots: Per-Tick Allocation Elimination & Skewed-Tick Time Reduction

> Produced by the deep-plan pipeline (RESEARCH → COMPOSE → REVIEW-PLAN).
> Review verdict: **APPROVE-WITH-CHANGES**; all 6 required changes and citation
> corrections from the adversarial review have been merged into this document.
> Baseline: `reports/stress_1.html` (hecs 0.11.1, seed 42, 1000×1000 map / 1M tiles,
> 12 cities, ~10k units, 1500 ticks, 3 runs).

## Context

The stress benchmark shows the sim is dominated by **heap churn and a few
time-skewed systems**, not raw compute:

- **~15,784 allocs/tick and ~19.21 MB/tick**, avg alloc 1.25 KB. Per the report's
  per-system allocation table, `nearby_enemies` (7.35 MB/tick, 38.3%) + `combat`
  (7.14 MB/tick, 37.2%) ≈ **75% of all bytes**, and together with `movement`
  (1.66 MB), `influence` (1.59 MB) and `water` (1.25 MB) they are the entire
  per-tick allocation picture.
- **death_cleanup is TIME #1** at 10,870 ms total but heavily skewed
  (P50 ≈ 30 µs, P99 ≈ 34 µs) — the mean is pulled up by mass-death "spike" ticks
  that rebuild a `HashSet` and run an O(total NearbyEnemies) `retain` and N
  per-entity `despawn`s. Its allocations are negligible (0.56/tick).
- The user **specifically called out `water`'s allocations** (13 allocs/tick,
  426 KB per call, 1.25 MB/tick) even though it is the cheapest system by time
  (766 ms total, P50 ≈ 0.45 µs) — i.e. pure allocator traffic.

Root cause across the tick: most systems re-allocate fresh `Vec`/`SmallVec`/`Arc`/
`String` temporaries every tick that are freed at the end of `tick_game()`
(game.rs:658-900). The codebase **already has the fix pattern** — a
"grow-only scratch buffer owned by `Game`" — it is simply not applied to the hot
systems yet.

Tick order (game.rs:658-900):
economy → water (:700-703) → movement (:706-717) → tickcontext rebuild (:727-741)
→ nearby_enemies (:746-752) → combat (:754-769) → supply (:772-781)
→ city_capture (:784-795) → influence every 3 (INFLUENCE_TICK_INTERVAL=3,
:800-832) → encirclement every 30 (:835-856) → surrender every 30 (:859-873)
→ death_cleanup (:878-889).

**Component facts** (game/components.rs): `UnitPath` :54 (
`SmallVec<[(f32,f32);8]>`); `NearbyEnemies` :62 (
`SmallVec<[Entity;8]>`); `UnitFlags` :98 (Copy); `UnitWaterTransition` :110
(two `Vec<Equipment>`); `VisionGrids.grids` :147-148. `spawn_unit`
(world_ext.rs:59-97) deliberately omits `NearbyEnemies` — its absence marks an
entity "uninitialized".

## The common reuse: "grow-only scratch buffer on Game"

A plain struct of `Vec`/`SmallVec`/`HashSet` fields, owned as a `Game` field,
passed `&mut` into `run()`, `.clear()` at the top of each run so capacity is
preserved and steady-state ticks do **zero** heap allocation; `.extend()` instead
of `.collect()`; `std::mem::take(&mut scratch.field)` for owned returns. Existing
instances to mirror: `SupplyScratch` (supply.rs:27-72, with the
`std::mem::take(&mut scratch.dead)` idiom at supply.rs:337), `MovementScratch`
(movement.rs:31-35), `CombatScratch` (combat.rs:24-38, `clear()` :55-67),
`GridIndexScratch` (nearby_enemies.rs:42-46, `new()` :49-55, `ensure()` :58-66),
`InfluenceScratch` (influence.rs:68-85, `ensure()` :88-105), `economy_earned`
Vec (game.rs:172-174). `Game` scratch fields are declared at game.rs:162-211 and
initialized at game.rs:504-518. Per-system alloc attribution comes from the
`tick_system!` expression wrapper (game.rs:37-66) + `debug_stats::record_system_alloc`
(debug_stats.rs:219-235) under the `bench-alloc` counting allocator (bench_alloc.rs),
aggregated in `benchmark.rs::run_benchmark`.

**Two cross-cutting compile rules from review (apply to every workstream):**
- **R1 — no private-type-in-public-interface.** New scratch fields whose element
  type is module-private (`WaterChange`, `MovementChange`) must be **private
  fields** (only `run()` touches them; `game.rs` only passes `&mut scratch`).
  Do **not** make them `pub`.
- **R2 — no field-name collisions.** `CombatScratch` already has
  `pub candidates: usize` (combat.rs:33, read at game.rs:648). Any new candidates
  **Vec** must be named differently (`candidate_units`).

## W1 — water: `WaterScratch` (user's key target)
File: `src/game/systems/water.rs` (116 lines).

`run(world, world_entity)` at :23 builds `let changes: Vec<(Entity, WaterChange)>
= …collect()` at :25-34. `compute_water_change` (:68-116) returns
`Some(WaterChange::TerrainCheck {..})` **unconditionally** for every unit not
mid-embark/disembark transition (:109-115), so the Vec has **one entry per unit
every tick**.

> **Corrected size (review):** the unconditional entry is `TerrainCheck`
> = (f32,f32)+bool+discriminant → `(Entity, WaterChange)` ≈ **24 B**, not 80 B.
> The 80 B figure applies only to the rare `Timer` entries that carry a full
> `UnitWaterTransition` clone. So the per-tick buffer is **~132 KB** (≈5.5k
> units × 24 B), not 426 KB; "~13–14 doubling reallocs from empty" (the reported
> "13 allocs/tick") is still correct. Do not calibrate verification on 426 KB.

**Steps**
1. Add to water.rs: `pub struct WaterScratch { changes: Vec<(hecs::Entity, WaterChange)> }`
   with `impl Default` (field **private** per R1 — `WaterChange` is module-private
   at water.rs:12 and only `run()` touches it).
2. Change signature: `pub fn run(world: &mut World, world_entity: hecs::Entity, scratch: &mut WaterScratch)`.
3. Replace :25-34 with `scratch.changes.clear(); scratch.changes.extend(world.query::<…>().iter().filter_map(compute_water_change));`
   and iterate `scratch.changes` in the apply phase (:36-66).
4. game.rs: add field `water_scratch: systems::water::WaterScratch` (next to
   `movement_scratch`, ~:180); init `systems::water::WaterScratch::default()`
   (~:510); pass `&mut self.water_scratch` at game.rs:702.
5. Update the `water::run` call at microbenchmarks.rs:1213 to pass a **reused**
   local `WaterScratch` across the bench loop so the steady-state path is exercised.
6. **Keep** the rare `(*wt).clone()` full clones at water.rs:77 and :93 — they run
   only for units mid-embark/disembark and must stay to preserve exact timer
   behavior.

*Optional/deeper (not in scope):* `TerrainCheck` is a pure read of
`(pos, flags.on_water)` + `terrain_at` (a `Ref`, no clone); a later change could
skip enqueueing `TerrainCheck` entries and fold the read+conditional-flag-write
inline in a second pass, collecting only `Timer` changes. Skip now — marginal
gain over the scratch fix, and it reshapes the two-phase order.

**Estimated reduction: water 13 allocs/tick → ~0–2; ~132 KB/call (reported
426 KB) → ~0; total bytes −1.25 MB/tick (−6.5%).**

larger than the "64 B" the earlier estimate said; conclusion unchanged) × ~9k
units-with-paths ≈ 566 KB/call. `MovementScratch` (movement.rs:31-35) holds only
`movers`.

**Steps**
1. Extend `MovementScratch` with `changes: Vec<(hecs::Entity, MovementChange)>`
   (field **private** per R1 — `MovementChange` is private at movement.rs:16).
2. In `run()`: replace :69-97 with `scratch.changes.clear();
   scratch.changes.extend(world.query::<…>().iter().filter_map(|…| compute_movement(…).map(|c| (entity, c))));`
   The mover-count (:101) and the apply loop (:109-140) iterate `&scratch.changes`.
3. **Path-clone fix:** add `pop_head: bool` to `MovementChange` (movement.rs:16-24;
   `false` in the moving-toward branch). In `compute_movement`'s reached-waypoint
   branch (movement.rs:191-194), replace `let mut new_path_copy = (*path).clone();
   new_path_copy.path.remove(0); …Some(new_path_copy)` with returning
   `new_path: None, pop_head: true` — no `SmallVec` copy (heap when >8 waypoints)
   and no O(path) `remove(0)` memmove in phase 1.
4. In the apply loop (movement.rs:109-140; the `&mut UnitPosition` query is :118,
   the `query_one_mut::<(&mut UnitPath,)>` is :123-127 — **corrected citations**),

   Guard + `debug_assert` are defensive: `compute_movement` only reaches this
   branch after `path.path.first()?` succeeded (:162), and no other system writes
   `UnitPath` mid-tick. The apply loop processes **every** change (not only
   movers), which preserves today's "unit sitting exactly on first waypoint pops
   the path without marking moved" edge case.
5. No call-site signature changes: game.rs:706-717 and microbenchmarks.rs:994/1016/1038
   already pass `&mut …MovementScratch`. `changes` entries for non-movers
   (org drain) are still produced, matching current behavior.

*Optional:* after `pop_head` lands, `new_path` is never `Some` again — consider
deleting the `Option<UnitPath>` field and the apply branch (movement.rs:123-127)
rather than keeping a dead `Option`.

**Estimated reduction: movement 12.77 allocs/tick → ~0; 566 KB/call → ~0; plus
per-waypoint-reacher SmallVec clones eliminated.**

## W3 — nearby_enemies: `units` scratch + SmallVec `append` (largest byte source)
File: `src/game/systems/nearby_enemies.rs` (496 lines).

`run()` collects a fresh `let units: Vec<(Entity, UnitPosition, u8, bool)> =
…collect()` each tick at :194-206 (~240 KB at ~10k units). Per-unit, the update
branch does `nb.entities = enemies.drain(..).collect()` at :254 — **collect into
`SmallVec<[Entity;8]>` allocates a fresh heap buffer every tick whenever the unit
sees >8 enemies, then drops the old one**: this is the **7.35 MB/tick (38.3%)**,
the single largest source (~859k allocs / 11.56 GB cumulative). `enemies:
Vec::with_capacity(16)` at :217 is the drain scratch and is already reused. The
insert branch :257-263 (`world.insert` for units spawned without `NearbyEnemies`
— spawn_unit, world_ext.rs:59-97) legitimately needs a fresh SmallVec.

**Steps**
1. Extend `GridIndexScratch` (struct :42-46, `new()` :49-55, `ensure()` :58-66) with
   `pub units: Vec<(Entity, UnitPosition, u8, bool)>` (all-pub element types — no
   R1 issue) and initialize in `new()`.
2. In `run()`: replace :194-206 with `grid_scratch.units.clear();
   grid_scratch.units.extend(world.query::<(Entity, &UnitPosition, &UnitFlags)>().iter().filter_map(|…| …));`
   then use `let units = &grid_scratch.units[..];` for `GridIndex::build`
   (**:214** — corrected) and the per-unit loop (:220).
3. Update branch (:253-255): replace `nb.entities = enemies.drain(..).collect();`
   with `nb.entities.clear(); nb.entities.append(&mut enemies);` — `append` moves
   entities in O(k) with **no allocation** once `nb.entities` capacity ≥ current
   enemy count (SmallVec keeps its heap allocation across `clear()`), and leaves
   `enemies` empty for the next unit. Keep `nb.initialized = true;`.
   (If the toolchain lacks `SmallVec::append`, the equivalent is
   `enemies.drain(..).for_each(|e| nb.entities.push(e))`; `Entity: Copy`,
   Cargo.toml smallvec 1.x.)
4. Insert branch (:257-263) unchanged — preserves "absence marks uninitialized".
5. No call-site changes: game.rs:746-752 and microbenchmarks.rs:1062/1078/1094
   already pass `&mut GridIndexScratch`.

*Optional/deeper (measure first):* per-unit `ctx.owner_id_by_entity.get(&e)` and
the `query_one_mut` at :253/:268 are the residual **time** cost (7,259 ms system);
a version-stamped `NearbyEnemies` (skip the ECS write when the computed list is
byte-identical) could cut write traffic, but set-comparison is O(k) ≈ the
rewrite. Out of scope for the allocation fix.

**Estimated reduction: nearby_enemies 572.85 allocs/tick → ~0 (only fresh-spawn
inserts); 7.35 MB/tick → ~0. Largest single byte win in the game.**

(concurrent immutable `EntityRef`s coexist; the block must still end before :411)
but is optional — the buffer reuse in `attrition_into` alone already removes the

**Estimated reduction: combat 1172.74 allocs/tick → ~200–400 (residual = name

## W5 — influence: double-buffered Arc publish (1.59 MB per dirty call)
File: `src/game/systems/influence.rs` (752 lines). Compute already reuses buffers
(`ensure()` :88-105, `fill()` resets); the 1.59 MB/call is the **publish path**:
- :352 `updated_vision.insert(player_id.clone(), scratch.vision.clone())` — a
  ~1 MB (grid_size @ 1000×1000) `Vec<bool>` clone **per player** + a `String` key clone;
- :360 `wb.territory.grid = Arc::new(scratch.territory.clone())` — another ~1 MB clone;
- :323-324 fresh `HashMap<String, Vec<bool>>`; :359 `Arc::new(HashMap)`; :315
  `sorted_players` collect.

**Design (steady-state zero large-alloc publish; a live published Arc never aliases
the buffer being rewritten):**
1. Change `VisionGrids.grids` (components.rs:147-148) from
   `Arc<HashMap<String, Vec<bool>>>` to `Arc<HashMap<String, Arc<Vec<bool>>>>`.
   Readers are source-compatible — game.rs:1358 (`vision_grid_2d`) and :1466 both
   `.get(pid)` then index/iterate through `Arc`'s `Deref`. Update the influence
   unit-test snapshot comparisons (influence.rs:513-570) to the new inner type.
2. In `InfluenceScratch` (:68-85): remove `vision: Vec<bool>` and
   `territory: Vec<u8>`; add `vision_pool: HashMap<String, [Arc<Vec<bool>>; 2]>`,
   `vision_gen: u8`, `territory_pool: [Arc<Vec<u8>>; 2]`, `territory_gen: u8`
   (keep `city_positions`, `player_influence`, `territory_max`).
3. `ensure()` (:88-105): lazily size `territory_pool[0..2]` to `grid_size` on
   first use/size change. **Vision slots are sized lazily per player on first
   sight** of that player id (`[Arc::new(Vec::new()), Arc::new(Vec::new())]`); the
   first `resize(grid_size)` is a one-time ~1 MB alloc per slot per player.
4. In `run()` (:287-361), per player (:326-352):
   ```rust
   let pair = scratch.vision_pool.entry(player_id.clone())
       .or_insert_with(|| [Arc::new(Vec::new()), Arc::new(Vec::new())]);
   let slot = Arc::make_mut(&mut pair[1 - scratch.vision_gen as usize]);
   if slot.len() != grid_size { slot.resize(grid_size, false); }
   compute_player(…, &mut slot[..]);
   updated_vision.insert(player_id.clone(), Arc::clone(slot));
   ```
   After the loop: `scratch.vision_gen ^= 1;`.
   **Why allocation-free & safe:** each dirty tick writes slot `1-gen`; that slot
   was published two dirty ticks ago and its Arc is no longer in `wb.vision.grids`.
   When no reader still holds that old Arc (steady state), `Arc::make_mut` is a
   strong-count-1 in-place fill → **zero allocs, ~1 MB buffer per player reused
   forever**. If a stale reader still holds the Arc, `make_mut` clones once
   (~1 MB) and correctness is preserved — the buffer being written can never be
   the allocation inside a live published Arc.
5. Territory: replace `scratch.territory.fill(NONE)` (:336) + the fold accumulator
   (`fold_influence_into(&mut scratch.territory, …)` :344-349) with
   ```rust
   let terr = Arc::make_mut(&mut scratch.territory_pool[1 - scratch.territory_gen as usize]);
   if terr.len() != grid_size { terr.resize(grid_size, NONE); }
   terr.fill(NONE);
   // fold into `terr`
   ```
   publish `wb.territory.grid = Arc::clone(&scratch.territory_pool[1 - scratch.territory_gen as usize]);`
   then `scratch.territory_gen ^= 1;` (:360). `territory_max` stays a plain scratch
   Vec (never published).
6. **Intentionally fresh (do not pool):** the `updated_vision` HashMap (:323-324),
   the `Arc::new(HashMap)` at :359, and the per-player `player_id.clone()` `String`
   keys at :352 remain per-dirty-call allocations — a few KB with ≤ a handful of
   players, bounded and acceptable. The <32 KB residual target holds.
7. `InfluenceScratch::new()`/`Default` updated to construct the pools;
   game.rs:211/:518 unchanged (type name unchanged).
8. Re-check `encirclement.rs` and all other `wb.territory.grid` /
   `wb.vision.grids` consumers compile against the changed `VisionGrids` (review
   found readers only at game.rs:1358/:1466 + the influence tests; encirclement
   clones the territory Arc per run).

**Risk (highest in the plan):** the double-buffer is allocation-free only while no
consumer retains an inner `Arc` across ≥2 dirty ticks. Verified true for all
current consumers (`vision_grid_2d`/`supervisor_vision_grid` convert to `Vec`
immediately; encirclement clones per run; `run_skip_keeps_grids_untouched`
influence.rs:513-570 holds a snapshot across a *skip* run only — safe). Any future
consumer retaining an Arc across ≥2 dirty ticks silently falls back to a full
~1 MB clone (correct, just slower). Comment this invariant. *Fallback if the
make_mut clone ever proves hot:* add a third recycle slot (triple-buffer) — do not
start there.

**Estimated reduction: influence 4.33 allocs/call → ~2–3; 1.59 MB/call → <32 KB;
the ~1 MB `max_alloc` per dirty tick disappears; −1–2 ms/call at (≈1/3 ticks).**

## W6 — death_cleanup: scratch dead-set, no `all_dead` concat
Files: `src/game/systems/death_cleanup.rs` (130 lines) + game.rs:878-889.
TIME #1 at 10,870 ms, **skewed** (P50 ≈ 30 µs, P99 ≈ 34 µs — the mean is pulled by
death-spike ticks); negligible allocs.

Per death-tick today: `dead_set: HashSet<Entity>` built fresh from `all_dead`
(:21, 1+ allocs/run); `all_dead` is a fresh `Vec` from
`combat_dead.chain(supply_dead).chain(surrender_dead).collect()` (game.rs:878-882);
single-pass `retain` over **every** unit's `NearbyEnemies` (:25); per-dead

## Risks & correctness notes

1. **Influence double-buffer Arc lifetime (W5, highest risk).** Invariant: *the
   buffer `compute_player` writes is never the allocation inside any
   currently-published Arc.* Verified for all current consumers; a retained Arc
   across ≥2 dirty ticks falls back to a correct ~1 MB clone. Flip
   `vision_gen`/`territory_gen` **after** all players publish.
2. **Movement `pop_head` guard (W2).** Apply-phase `path.remove(0)` guarded by
   `if !mpath.path.is_empty()` + `debug_assert!` (defensive; compute only sets
   `pop_head` after `path.path.first()?` at :162, no same-tick `UnitPath` writer).
3. **Water preserves embark/disembark timer behavior (W1).** Only the buffer
   changes, not the logic; `Timer` entries still carry the full cloned
   `UnitWaterTransition` (clones at :77/:93 kept) and the `ticks_left == 0`
   transitions (flag flip, `boat_supply.clear()`/`max_boat_supply.clear()` at
   :95-97) are untouched. Two-phase order preserved.
4. **Death-cleanup (W6).** Keep per-entity `entity_reverse.remove`+`world.despawn`
   exactly as-is (:30-31); `entity_reverse` is a `Game` HashMap used by
   LLM/lobby for entity→unit-id lookup and must stay consistent per entity.
   Preserve combat→supply→surrender order and sum-of-lens `dead_count`. Do not
   land skip-retain in the same change.
5. **Combat shared equipment borrow (W4).** The collapsed `eq1`/`eq2` borrow must
   end before the `query_one_mut` writes at :411/:427 (hecs panics on overlapping
   mutable access); both original sites `continue` on `Err` so merging cannot
   change which pairs resolve. Invariant: no same-tick component removal between
   the two original fetches.
6. **NearbyEnemies `append` (W3).** `nb.entities.clear(); nb.entities.append(&mut
   enemies);` is content-identical to the old `= drain(..).collect()`; SmallVec
   keeps capacity across `clear()`; the `initialized = true` write and the
   fresh-insert branch are unchanged.
7. **Determinism.** No change reorders arithmetic or RNG. Order-sensitive spots:
   W6 dead-entity processing (preserve combat→supply→surrender) and W4 candidate
   iteration (same query, same order — only the storage Vec moves). Seed-42 runs

8. **Compile rules R1/R2** (above) — private scratch fields for private element
