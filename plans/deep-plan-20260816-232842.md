# Deep Plan: Post-Influence-Rewrite Optimizations

## Context

The influence system was rewritten in the last two commits (`55be210` "Implement full influence system", `bdfe8dc` "Improve performance of influence a bit"). The rewrite introduced:
- Merged vision + border influence into a single `stamp_circle` pass
- Precomputed `CIRCLE_SPANS` via `OnceLock`
- `InfluenceScratch` with reused buffers (SupplyScratch pattern)
- Per-player influence folded directly into territory (no intermediate HashMap)
- Dirty-flag skip path (clean ticks skip all compute + allocs)

A third commit (`45b81e8` "Added allocator tracking for benchmarks") added:
- **dhat-based heap invariants** (`src/alloc_invariants.rs`): asserts warm ticks don't grow the heap (≤ 64 blocks / 4 KB per tick). Runs as a normal `cargo test`.
- **Counting allocator** (`src/bench_alloc.rs`, feature `bench-alloc`): per-tick alloc call/byte counters in the battle benchmark HTML report. Run via `make bench-alloc`.

These tools give us a direct measurement of whether each optimization step below actually eliminates allocations.

This plan identifies the remaining optimizations across the tick loop, including cross-system reuse opportunities. Research confirmed that `fastrand` is **not applicable** (no RNG in the tick loop — `rand`/`StdRng` only exists in `benchmark.rs` for the seeded BattleSimulator).

## Scope

**In:** Per-tick allocation elimination, terrain grid flattening, smallvec component changes, cross-system index sharing, scratch buffer reuse.

**Out:** fastrand (no RNG in tick loop), rayon (already measured sub-breakeven), ahash/hashbrown (type-rippling; revisit later), bitvec for vision (medium API churn; measure first), bytemuck/rkyv (no hot-loop role), merging ECS queries (hecs 0.11 limitations).

## Steps

### Step 1: `NearbyEnemies.entities` → `SmallVec<[Entity; 8]>`

**Files:** `src/game/components.rs:60-68`

**Why:** `nearby_enemies.rs:206-217` does `nb.entities = std::mem::take(&mut enemies); enemies = Vec::with_capacity(16);` — drops the old buffer and allocs a fresh 16-capacity `Vec` for **every unit every tick**. At 500 units that's 500 allocs/tick. `combat.rs` then does `nearby.clone()` per candidate — another 500 allocs. Typical enemy lists are 0-5 entities, so `SmallVec<[Entity; 8]>` keeps them stack-allocated in the common case. `smallvec` is already a dependency (used in `supply.rs`).

**Change:**
```rust
// components.rs:60-68
use smallvec::SmallVec;

#[derive(Debug, Clone, Default)]
pub struct NearbyEnemies {
    pub entities: SmallVec<[hecs::Entity; 8]>,
    pub initialized: bool,
}
```

**Downstream effects (must fix, ~8 test/fixture sites):**
- `nearby_enemies.rs:206-217` — `Vec::with_capacity(16)` → `SmallVec::new()` (just update the local type)
- `combat.rs` — `nearby.clone()` now clones a SmallVec (stack-only if ≤ 8)
- All `.entities.iter()` / `.entities.is_empty()` / `.entities.len()` calls work identically
- **Test/fixture sites that use `entities: vec![...]` literals** (won't compile against SmallVec):
  - `combat.rs` tests (lines ~558, 604)
  - `death_cleanup.rs` tests (lines ~52, 56, 96, 115)
  - `microbenchmarks.rs:874`
  - `combat.rs` `populate_nearby_enemies` helper: `ne.entities = nearby` (Vec → SmallVec)
  - Fix: replace `vec![...]` with `smallvec::smallvec![...]` or `[...].into_iter().collect()`
- **Note:** lists > 8 entities still heap-allocate (SmallVec's overflow buffer). Fine, just not the fast path.

**Impact:** Eliminates ~500 heap allocs/tick at benchmark scale (500 units). Removes the `nearby.clone()` alloc in combat.

### Step 2: `UnitPath.path` → `SmallVec<[(f32, f32); 8]>`

**Files:** `src/game/components.rs:53-55`

**Why:** `movement.rs:189-191` does `(*path).clone()` when a unit reaches a waypoint. For units with short paths (typical 2-5 waypoints after pathfinding), this is a heap alloc per waypoint-reach per tick. `SmallVec<[(f32, f32); 8]>` keeps typical paths stack-allocated.

**Change:**
```rust
// components.rs:53-55
use smallvec::SmallVec;

pub struct UnitPath {
    pub path: SmallVec<[(f32, f32); 8]>,
}
```

**Downstream effects (must fix, ~6 sites):**
- All `.path.iter()`, `.path.first()`, `.path.remove(0)`, `.path.push()` calls work identically
- Pathfinding code that builds paths uses `.collect()` — works with `FromIterator`
- **Production sites that assign `Vec<(f32, f32)>` into the field** (won't compile):
  - `Game::move_troops` (game.rs:913): `up.path = path;` where `path: Vec<(f32, f32)>` → change to `up.path = path.into_iter().collect();`
  - `UnitQueryData` population (game.rs:1167): `path: path.path.clone()` into a `Vec` field → `path.path.to_vec()` (UnitQueryData is a query-output struct, keep its field as `Vec`)
- **Test literals** `UnitPath { path: vec![...] }` in movement.rs tests (4 sites, lines ~389-522) and microbenchmarks.rs:415 → replace with `smallvec![...]` or `[...].into_iter().collect()`

**Impact:** Eliminates per-waypoint-reach allocs for the common short-path case.

### Step 3: `city_capture` — stop cloning `String` per unit per tick

**Files:** `src/game/systems/city_capture.rs:24-29`, `src/game/game.rs` (call site)

**Why:** `city_capture::run` runs **every tick** (ungated in the tick loop) and does:
```rust
let units: Vec<(String, UnitPosition)> = world
    .query::<(hecs::Entity, &UnitOwner, &UnitPosition)>()
    .iter()
    .map(|(_, owner, pos)| (owner.player_id.clone(), *pos))
    .collect();
```
That's a `String` clone per unit per tick (500+ allocs). Then it does `owner_id.clone()` again in the `BTreeMap` insert (line 33).

**Fix:** Pass `&TickContext` and use `ctx.owner_id_by_entity` (u8) + `ctx.player_id_to_index` to resolve the owner string **only when a capture actually happens** (rare). For the distance check, just use the u8 index for comparison against the city's owner index (linear scan over ≤ 12 cities is fine, same pattern as `encirclement.rs:41-47`).

**Change (outline):**
```rust
pub fn run(
    world: &mut World,
    world_entity: hecs::Entity,
    player_stats: &mut HashMap<String, PlayerGameStats>,
    ctx: &TickContext,
) -> Vec<String> {
    // ...
    // Build city owner index: linear scan (≤ 12 cities)
    // For each unit, get u8 owner from ctx.owner_id_by_entity
    // Compare u8 to city owner u8 — no String comparison
    // Only clone the String when a capture actually fires
}
```

**Impact:** Eliminates ~500 `String` allocs + ~500 `String` comparisons per tick. The system now only allocates when a city actually changes hands (rare).

### Step 4: GridIndex scratch + drop cursor clone

**Files:** `src/game/systems/nearby_enemies.rs:44-100`, `src/game/game.rs` (add `GridIndexScratch` to `Game`)

**Why:** `GridIndex::build` allocates every tick:
- `cell_sizes: Vec<usize>` (line 76)
- `cell_offsets: Vec<usize>` (line 85)
- `cursor = cell_offsets.clone()` (line 91) — full clone
- `entries.resize_with(...)` with a placeholder init (lines 93-97) — writes every entry before overwriting

At 200×200 with units spread, `total` ≈ 10,201 → two ~80 KB Vec allocs + one 80 KB clone + a ~12 KB entries write pass, every tick.

**Fix:** Create a `GridIndexScratch` (owned by `Game`, same pattern as `CombatScratch`/`SupplyScratch`):
```rust
pub struct GridIndexScratch {
    pub entries: Vec<CellEntry>,
    pub cell_offsets: Vec<usize>,
    pub cell_sizes: Vec<usize>,
}
```
- `ensure(total)` resizes only on growth (like `InfluenceScratch::ensure`); at steady state, `resize` is a no-op
- Use `cell_sizes` as the fill cursor: zero it (`fill(0)`), use it as the cursor during the fill pass, after which it holds the final per-cell counts — eliminates the `cell_offsets.clone()`
- Drop `resize_with` placeholder init: with the reused buffer, `entries` already has the right length from the previous tick; just overwrite in the fill pass (no pre-write of defaults)
- **Note:** `cell_sizes` zeroing (`fill(0)`) is an unavoidable 80 KB memset per tick (cheap, SIMD-optimized)

**Impact:** Eliminates 2 heap allocs (cell_offsets fresh + cursor clone) + the `resize_with` full entry-write pass per tick. The `entries` Vec and `cell_sizes`/`cell_offsets` are reused (no alloc at steady state).

### Step 5: Flatten `TerrainGrid` to `Arc<Vec<Terrain>>`

**Files:** `src/game/components.rs:122-135` (TerrainGrid), `src/game/systems/movement.rs:157,172-175`, `src/game/systems/influence.rs` (compute_player terrain lookup), `src/game/systems/combat.rs` (terrain lookup), `src/game/world_ext.rs` (spawn_world/terrain_at), `src/game/game.rs` (`terrain_grid_2d` ~line 1233, `Game::new` builder), `src/server/game_server.rs` (wire protocol consumer), `src/replay/replay.rs` (replay consumer)

**Why:** `TerrainGrid.grid` is `Arc<Vec<Vec<Terrain>>>`. Every terrain lookup is:
```rust
terrain.get(x).and_then(|r| r.get(y)).cloned().unwrap_or(Terrain::Plains)
```
That's: Arc deref → outer Vec bounds check → row pointer load → inner Vec bounds check → copy Terrain. Two heap indirections, two bounds checks, one cache miss on the row pointer.

`Terrain` is a 5-variant enum (1 byte, `Copy`), so flattening to `Arc<Vec<Terrain>>` is straightforward.

**⚠️ CRITICAL: Index order.** The existing 2D terrain is **x-major**: `Game::new` fills `terrain[x][y] = map.terrain(x, y)`. The vision/territory grids use **y-major** (`idx = y * width + x`). The flattened terrain must pick ONE convention and use it consistently. **Recommendation: use y-major (`idx = y * w + x`)** to match VisionGrids/TerritoryGrid convention. The builder must transpose:
```rust
// In Game::new / spawn_world:
let flat: Vec<Terrain> = {
    let mut v = vec![Terrain::Plains; (w * h) as usize];
    for x in 0..w {
        for y in 0..h {
            v[(y * w + x) as usize] = map.terrain(x, y);
        }
    }
    v
};
```
And `TerrainGrid::get(x, y)` must read `self.grid[(y as usize) * w + (x as usize)]`.

**MUST add a non-square (e.g. 120×80) terrain-roundtrip test** to catch a transposition bug. All existing tests use square maps and would pass with a silent x/y swap.

**Affects:**
- `movement.rs:172-175` — per unit per tick (500 lookups/tick)
- `influence.rs` compute_player — per unit per dirty tick
- `combat.rs` — per pair per tick (terrain modifier)
- `game.rs:terrain_grid_2d` (~line 1233) — feeds wire protocol + replay (indexes `grid[x][y]` directly — must update to read from flat: `grid[y*w+x]`)
- `world_ext.rs:terrain_at` helper
- `server/game_server.rs` + `replay/replay.rs` — consume `terrain_grid_2d` output (no change needed if `terrain_grid_2d` is updated to return the same 2D shape)

**Change:**
1. `TerrainGrid` struct: `grid: Arc<Vec<Terrain>>` (flat, y-major), keep `width`/`height`
2. `TerrainGrid::get(x, y)`: `self.grid.get((y as usize) * (self.width as usize) + (x as usize)).copied().unwrap_or(Plains)`
3. `Game::new` / `spawn_world`: build the flat `Vec<Terrain>` with transposition (see above)
4. `terrain_grid_2d` (game.rs ~1233): rebuild from flat: `grid[y*w+x]` → 2D `Vec<Vec<Terrain>>` for wire/replay (keep the 2D output shape so wire/replay consumers don't change)
5. `movement.rs`, `influence.rs`, `combat.rs`: use `TerrainGrid::get()` or direct `grid[y*w+x]` index
6. **Add non-square test:** e.g. 120×80 map, verify `get(3, 7)` matches expected terrain at a known position

**Impact:** Halves terrain lookup cost in 3 systems. Eliminates row-pointer cache miss. ~500 fewer double-indirections per tick in movement alone.

### Step 6: Influence vision buffer → `InfluenceScratch` (reuse, not alloc)

**Files:** `src/game/systems/influence.rs:69-99` (InfluenceScratch), `:100-102` (ensure), `:175` (vision alloc), `:318-351` (publish)

**Why:** `compute_player` allocates `let mut vision_grid = vec![false; grid_size];` (line 175) — a full `grid_size`-byte zero-init per player per dirty tick. At 12 players × 40,000 cells (200×200 map), that's 480 KB of alloc + zero-init per dirty tick.

**Fix:** Add `vision: Vec<bool>` to `InfluenceScratch`:
```rust
pub struct InfluenceScratch {
    pub city_positions: Vec<(f32, f32)>,
    pub player_influence: Vec<u16>,
    pub territory: Vec<u8>,
    pub territory_max: Vec<u16>,
    pub vision: Vec<bool>, // NEW
}
```
- `ensure()` resizes `vision` alongside the others
- `compute_player` takes `vision: &mut [bool]` (out-param) instead of returning `Vec<bool>`
- Before stamping: `vision.fill(false)` (memset, no alloc)
- At publish: `Arc::new(vision_buffer.clone())` — still one clone per player per dirty tick, but no fresh alloc + zero-init

**Advanced (optional, later):** Double-buffer the vision (two `Vec<bool>` in scratch, stamp into A, publish A, stamp into B next time). Eliminates even the clone. But the simple version already saves the alloc + zero-init.

**Impact:** Removes 12 × 40 KB alloc+zero-init per dirty tick (every 3rd tick when dirty).

### Step 7: Economy — scratch `Vec<(u8, u32)>` instead of fresh `HashMap<String, u32>`

**Files:** `src/game/systems/economy.rs:20-51`, `src/game/game.rs` (call site)

**Why:** `economy::run` returns a **fresh `HashMap<String, u32>` every tick** (line 25: `let mut earned: HashMap<String, u32> = HashMap::new();`). At ≤ 12 players this is small, but it's an unconditional per-tick alloc with string hashing.

**Fix:** Change the return type to `&mut Vec<(u8, u32)>` (caller-provided scratch, cleared + reused):
```rust
pub fn run(
    world: &mut World,
    world_entity: hecs::Entity,
    funds_per_city: f32,
    earned: &mut Vec<(u8, u32)>, // OUT param
    player_index: &HashMap<&str, u8>, // or use TickContext
) {
    earned.clear();
    // ... same logic, push (player_idx, gain_rounded) instead of entry
}
```
Or simpler: just use a `SupplyScratch`-style persistent buffer in `Game`. The caller (game.rs:595-604) iterates the returned map — adapt to iterate the Vec.

**Impact:** Removes 1 HashMap alloc + hash ops per tick. Small at 12 players but free.

### Step 9: Encirclement — scratch for `safe`/queue; queue as `Vec<usize>`

**Files:** `src/game/systems/encirclement.rs:53,62`, `src/game/game.rs` (add to a shared scratch or inline)

**Why:** Every 30 ticks, encirclement allocates:
- `safe: Vec<u8>` (line 53) — `grid_size` bytes
- `queue_buf: Vec<(i32, i32, u8)>` (line 62) — 16 bytes/entry, capacity `grid_size`

The queue tuple `(i32, i32, u8)` is 16 bytes due to alignment. Storing as `Vec<usize>` (cell index, 4 bytes) + deriving player from `safe[nidx]`/`dominant[nidx]` cuts memory 4× and improves cache locality in the BFS.

**Fix:**
- Add a dedicated `EncirclementScratch` with `safe: Vec<u8>` and `queue: Vec<usize>` (do NOT alias `InfluenceScratch.territory` — the two runs are coupled by dirty flags and aliasing the published-territory buffer with BFS scratch is fragile)
- Queue entry = `usize` cell index (8 bytes on 64-bit); BFS loop: `let pidx = safe[idx]; let x = (idx % w) as i32; let y = (idx / w) as i32;`
- `ensure(grid_size)` grows only on map resize

**Impact:** Small (runs every 30 ticks) but trivial. Reduces 2 allocs + 2× queue memory (16 B → 8 B per entry on 64-bit).

### Step 10: Benchmark hygiene — pull instrumentation out of timed block

**Files:** `src/benchmark.rs` (timed tick loop, ~lines 355-368)

**Why:** The benchmark's timed per-tick block includes `query_all_units()` (which builds fully String-materialized `UnitQueryData` for every unit — `format!` + 6 String/Vec clones per unit) purely to call `.len()`, plus `combat_health()` which scans all units. This inflates the "total_ms per tick" baseline with non-game cost.

**Fix:**
- Replace `query_all_units().len()` with an entity counter: `world.query::<(&UnitStats,)>().iter().count()` (no allocation) or maintain a running count
- Move `combat_health()` outside the timed region (or gate it behind `detailed_systems`)
- Keep the instrumentation available but don't count it in `total_ms`

**Impact:** Gives an accurate tick baseline so the other optimizations show their real numbers.

## NOT doing (and why)

| Idea | Reason |
|------|--------|
| Add `fastrand` | No RNG in the tick loop. `rand`/`StdRng` only in `benchmark.rs` (seeded BattleSimulator). Nothing to replace. |
| Add `rayon` | Already tried at multiple granularities and rejected — per-player influence work (~0.1 ms) is below dispatch breakeven. |
| Add `ahash` / `hashbrown` | Modest ns-per-lookup gain, but type change ripples through `TickContext` and every system signature. Revisit AFTER Steps 1-8 land. |
| `bitvec` for vision grid | Cuts 40 KB → 5 KB per player but per-cell bit set/get is slightly slower in `stamp_circle` and every consumer API changes (wire, LLM, replay). Do only if vision transport shows in profiles. |
| Merge ECS queries across systems | hecs 0.11 has no cheap multi-query cache; systems have divergent component tuples. Forcing a shared query would add complexity for ~0 gain. |
| SIMD in `fold_influence_into` | LLVM autovectorizes the max-compare pattern at `-O3`. Profile first. |
| `CIRCLE_SPANS` → const/build-script | One-time cost behind `OnceLock`. Cosmetic. |
| `bytemuck`/`rkyv`/`num-traits`/`num-integer` | No hot-loop use found. No unsafe transmute sites; serialization is outside the tick loop. |
| `UnitFlags` → `bitflags` | 7 bools → 1 byte saves ~6 bytes/entity in archetype rows. Low priority, type-rippling. |

## Verification

The project now has two allocation-tracking tools (added in commit `45b81e8`):
- **dhat invariants** (`src/alloc_invariants.rs`): test-time global allocator that asserts a warm tick grows the heap by ≤ 64 blocks / 4 KB, and 10 ticks by ≤ 128 blocks / 32 KB. Run with `cargo test alloc_invariants`. Will **fail** if any step above introduces a per-tick leak.
- **Counting allocator** (`src/bench_alloc.rs`, feature `bench-alloc`): counts alloc calls + bytes per tick in the battle benchmark. Run with `make bench-alloc` (or `cargo run --release --features microbenchmarks,bench-alloc -- --benchmark --bench-html benchmark-alloc.html`). The HTML report shows `allocs`, `bytes`, `max_alloc` per tick.

Use these as the primary verification signal for each allocation-eliminating step.

After each step (or group of related steps):

1. **Run allocation invariants (must stay green):**
   ```
   cargo test alloc_invariants
   ```
   This pins the "warm tick is allocation-free" invariant. If a step accidentally adds a per-tick alloc, this test catches it.

2. **Run microbenchmarks (wall-clock):**
   ```
   cargo run --release --features microbenchmarks -- --benchmark
   ```
   Watch: `systems/nearby_enemies_100`, `systems/nearby_enemies_500`, `systems/combat_50pairs`, `systems/influence_500`, `systems/full_tick_200`, `systems/full_tick_500`.

3. **Run the battle benchmark with allocation tracking:**
   ```
   make bench-alloc
   ```
   (or `cargo run --release --features microbenchmarks,bench-alloc -- --benchmark --bench-html benchmark-alloc.html`)
   Watch: `allocs` per tick (should decrease with each step), `bytes` per tick, `max_alloc` (should not grow). Also wall-clock `total_ms` per tick.

4. **Run the battle benchmark (wall-clock only, for `--bench-prev` comparisons):**
   ```
   cargo run --release -- --benchmark --bench-prev benchmark-alloc.html
   ```
   (optionally `--bench-seed <n>` for reproducibility)
   Watch: mean/median `total_ms` per tick, `system_sum_ms` vs `total_ms` gap (overhead).

5. **For Step 5 (terrain flatten):** the `map/terrain_lookup` microbenchmark measures `Map::terrain(x, y)` (the procedural generator), NOT `TerrainGrid::get`. Instead verify via:
   - The non-square (120×80) roundtrip test (must pass)
   - `systems/movement_500` comparison (movement is the per-tick terrain consumer)
   - Optionally add a new microbench around `TerrainGrid::get` on a 200×200 grid

6. **Regression check:** `cargo test --features microbenchmarks` (all unit + integration tests must pass; the `--features microbenchmarks` flag ensures test fixtures in microbenchmarks.rs also compile). Note: `cargo test` (without `bench-alloc`) runs the dhat invariants automatically.

7. **Determinism check (Step 3):** verify city capture outcomes are identical pre/post by running the same seed and comparing city ownership at each tick.
