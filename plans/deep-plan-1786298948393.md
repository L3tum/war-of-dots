# Deep Plan: Fix Combat Regression and Optimize Past Baseline

**Date:** 2026-08-09
**Status:** Ready for implementation
**Author:** deep-plan pipeline (REFINE → RESEARCH → COMPOSE)
**Target file:** `src/game/systems/combat.rs` (primary), `src/game/game.rs` (call site + scratch ownership)

---

## 1. Problem Statement

An uncommitted two-phase refactor of `src/game/systems/combat.rs` (modeled on the `movement.rs` "collect → apply" pattern) caused a **performance regression and a behavioral drift** versus the pre-refactor baseline:

| Report | Combat total | Combat avg/call | Units remaining | Interpretation |
|--------|-------------|-----------------|-----------------|----------------|
| `report_20_2.html` | **163.4ms** (p50 0.075ms) | 0.105ms | ~312 | True pre-refactor baseline (verified: every per-system delta in 20_4 matches 20_2's totals exactly) |
| `report_20_3.html` | 165.5ms (+1.3%) | — | 312 | HEAD code re-run, ~noise |
| `report_20_4.html` | **176.3ms (+7.9%)** | 0.114ms | **323 (+11)** | New two-phase code — regression + behavioral drift |

The +11 surviving units prove **gameplay behavior changed**, not just timing. The root causes are two correctness bugs in the two-phase accumulation logic plus refactor-induced overhead:

1. **Defender damage no longer compounds (primary).** New code reads the defender's stats from the untouched ECS baseline on every engagement (`world.get::<&UnitStats>(entity2)`, `combat.rs` ~L203-208) and `entry.men = Some(d_men)` is **last-write-wins** (~L278-281). A defender attacked N times takes ~1× damage instead of N×. Old code wrote to ECS per pair (read-modify-write), so damage compounded.
2. **Equipment attrition no longer compounds.** `attrition_from(&*eq2, …)` always reads ECS-baseline equipment and `entry.new_equipment = Some(d_eq)` overwrites (~L250-260, L284-286). The plan doc (`plans/deep-plan-combat-opt.md`) explicitly called for a `working_equipment` accumulation field that was **never implemented**.
3. **Overhead without benefit at benchmark densities.** `CombatScratch::new()` allocates 4 HashSets + 1 HashMap **every tick** (`.clear()` is `#[allow(dead_code)]`, never called); per-engagement `scratch.changes.entry()` hashing ×2; Phase 2 writes every touched entity via a 3-component `query_one_mut` even when only flags changed (retreats); the moved-flag clear does per-candidate `query_one_mut` instead of the old single bulk archetype sweep.
4. **TickContext (explicitly requested by the user) was never integrated.** `combat::run` still has signature `(world, world_entity, spatial)`; candidates come from a full `world.query::<(&UnitPosition, &UnitOwner, &UnitFlags, &UnitStats)>()` with a per-candidate `owner.player_id.clone()` String allocation, and the same-owner check does a per-pair `world.get::<&UnitOwner>`.

**Why everything regressed, not just combat:** the simulation is deterministic-with-divergence (seeded `StdRng`; `BattleSimulator` decisions depend on live unit counts). Fewer combat deaths → +11 units alive → more work in *every* system every tick (attrition +15.9%, influence +22.6%, encirclement +20.2% in report_20_4) — a cascade, not independent regressions.

## 2. Goals & Non-Goals

### Goals
1. **Restore exact pre-refactor (HEAD) combat semantics.** A defender attacked N times takes N× cumulative damage; equipment attrition applies to progressively-degraded equipment; org/supply accumulate identically to the old read-modify-write pattern.
2. **Beat the HEAD baseline.** Combat total ≤ 163.4ms (ideally < 150ms), avg/call ≤ 0.105ms, p50 ≤ 0.075ms (report_20_2 numbers) in the standard benchmark.
3. **Units-remaining parity.** `--bench-units 20 --bench-ticks 1500 --bench-seed 42` produces units_remaining ≈ 312 ± 3, confirming the simulation returns to the pre-refactor trajectory.
4. **All existing tests pass** and the relaxed 3-unit test bound `(985.0..1000.0)` is **restored to `(990.0..1000.0)`** (see §6 Step 10).
5. **New regression tests** for: multi-attacker defender compounding, cumulative kill threshold, equipment attrition accumulation, retreat-only flag write, scratch capacity survival across `clear()`.

### Non-Goals
- Optimizing other systems (attrition, influence, movement, supply…) — their regressions are the cascade; fixing combat restores them.
- Changing game balance or combat formulas.
- `String` → `u32` player-ID refactor (separate, larger PR).
- Rayon / parallel combat.
- Changing the "each unit attacks at most once per tick" invariant (the `break` after first resolution).
- Changing `attrition_from`'s String-clone behavior (noted as follow-up).

## 3. Context

### 3.1 Current `combat.rs` structure (working tree)
- **L16–36** `CombatChange` — accumulates per-entity deltas. **Missing `working_equipment`** (called for in the plan doc, never implemented).
- **L38–67** `CombatScratch` — 4 HashSets + 1 HashMap + 1 Vec; `new()` allocates fresh every tick (L134); `clear()` is `#[allow(dead_code)]` (L57).
- **L97–99** `pub fn run(world: &mut World, world_entity: hecs::Entity, spatial: SpatialHash)` — no `&TickContext`.
- **L121–131** candidate collection: full query + per-candidate `owner.player_id.clone()`.
- **L141–310** Phase 1 main loop. **Attacker** stats compound correctly via `scratch.changes.get(entity1)` (L179–196). **Defender** stats read from ECS baseline (L203–208) — the bug.
- **L255–287** accumulation blocks: `entry.men = Some(a_men/d_men)` last-write-wins; `entry.new_equipment = Some(...)` overwrites from baseline.
- **L310–330** Phase 2 batch apply: 3-component `query_one_mut` per entity.
- **L332–338** moved-flag clear: per-candidate `query_one_mut::<(&mut UnitFlags,)>` for non-engaged candidates.
- **L344–348** `dead` derived post-hoc from `c.men <= 0.0`.

### 3.2 Old (HEAD) behavior — the correctness target
- Per-pair read-modify-write: reads CURRENT ECS state for both attacker and defender, computes damage, writes immediately. Damage **compounds** because each pair reads the latest state. Equipment attrition is applied against the live component every engagement.
- Moved-flag clear: single bulk `world.query::<&mut UnitFlags>().iter()` sweep.
- Dead tracking: inline `dead.push()` + `dead_set.insert()` during resolution.
- Candidate iteration order: ECS query iteration order (entity spawn order).

### 3.3 Surrounding architecture
- `game.rs` **L150–220** `TickContext { world_entity, cities, funds, width, height, units_by_player: HashMap<String, Vec<(hecs::Entity, (f32, f32))>> }`, built **once per tick** (L291, ~24.7ms total, cheap) and already passed to influence/healing/supply/encirclement.
- `game.rs` **L322–327** combat call site: `systems::combat::run(&mut self.world, self.world_entity, spatial)` — `ctx` is in scope and available.
- `spatial_hash.rs` `query_nearby_into(x, y, &mut out)` — adjacency primitive; keep.
- `movement.rs` two-phase works safely because movement state is per-unit independent — combat's cross-unit compounding is exactly what the naive port missed.

## 4. Design

Three parts, ordered by priority. All three are required to meet the goals.

### Part A — Correctness: restore defender compounding (MUST-HAVE)

**A1. Defender effective stats.** Mirror the attacker path (L179–196): before computing damage, build `s2_eff` from `scratch.changes`:
- `effective_men = changes[entity2].men.unwrap_or(ecs_s2.men)`
- `effective_org = (ecs_s2.organisation + changes[entity2].org_delta).max(0.0)` (fallback `ecs_s2.organisation`)
- `s2_eff = UnitStats { men: effective_men, organisation: effective_org, ..ecs_s2 }`

Then compute `a_soft`/`d_soft` from **both** `s1_eff` and `s2_eff`, exactly as the old code did with current-state reads. `d_men = (s2_eff.men - dmg_to_defender).max(0.0)` and `entry.men = Some(d_men)` now accumulate correctly because `s2_eff.men` already reflects prior engagements. No other damage-formula change.

**A2. Equipment attrition accumulation.** Add `working_equipment: Option<Vec<Equipment>>` to `CombatChange`. Inside each accumulation block (after `or_insert`):
1. Lazy-init `working_equipment` from the ECS `UnitEquipment.equipment` clone on first engagement (only if `is_none()`).
2. Apply `attrition_from(working, dmg, attr_rate)`; on `Some(new_eq)`, set `working_equipment = Some(new_eq.clone())` and `new_equipment = Some(new_eq)`.
3. Phase 2 writes `me.equipment = eq` only if `new_equipment` is `Some` (unchanged semantics; the last result is the fully-accumulated state).

This reproduces old per-pair read-modify-write attrition, including the attacker's counter-damage attrition.

**A3. Dead determination.** With compounding restored, `d_men <= 0.0` fires exactly when the old inline `dead.push()` did; the end-of-tick `dead` derivation from `c.men <= 0.0` is then equivalent. `dead_set` guarding (prevent a dead unit from attacking later this tick) is preserved as-is.

**A4. Moved-flag clear (bulk).** Restore the old single can archetype sweep:
```rust
for (_, flags) in world.query::<&mut UnitFlags>().iter() { flags.moved = false; }
```
and **remove** `mf.moved = false` from the Phase 2 batch apply (avoid double-clear). One archetype-sweep beats N per-entity `query_one_mut` calls.

**A5. Retreat-only writes.** Entities that only retreat (no men/org/equipment/supply change) should not pay for a 3-component `query_one_mut`. Either (a) keep a small dedicated pass `query_one_mut::<(&mut UnitFlags,)>` for entities whose `CombatChange` has `men == None && new_equipment == None && supply_delta == 0.0`, or (b) fold retreat clearing into the bulk moved-flag sweep (visit all units anyway). **Recommend (b)** — simplest and matches old cost profile; keep the `retreated`/`fighting` writes in the Phase 2 pass only for entities that actually have stats/equipment changes.

### Part B — Performance: hoist `CombatScratch` into `Game` (MUST-HAVE)

The plan doc itself admits "HashMap allocation overhead offsets the ECS query savings" and recommends capacity reuse. Implement:

- `game.rs`: add `combat_scratch: CombatScratch` field to `Game`, initialize in `Game::new`, and pass `&mut self.combat_scratch` into `run()`.
- `combat.rs`: make `CombatScratch` and `clear()` `pub`; `run()` calls `scratch.clear()` first. Capacities persist across ticks; allocations amortize to ~zero after warmup.

### Part C — TickContext integration (MUST-HAVE per the original request, scoped carefully)

**Iteration-order safety is the hard constraint.** Combat resolution order determines *who attacks whom first*, and therefore the exact accumulated damage values, and therefore the chaotic trajectory. The old candidate order = ECS query iteration order. `TickContext::units_by_player` is a `HashMap` — its iteration order is hash-dependent and **must not** become the candidate order.

Safe integration (hybrid):
1. **Keep the ECS query for candidate enumeration** (preserves old iteration order verbatim). This also avoids a behavioral cliff if TickContext ordering ever changes.
2. **Derive two lookup maps from `ctx.units_by_player` once per tick:**
   - `entity_owner: HashMap<Entity, &str>` (player_id borrowed from ctx — no String clones, lives for the call)
   - `entity_pos: HashMap<Entity, UnitPosition>`
   (Build before the main loop; capacity = sum of `units_by_player` lengths.)
3. Replace the per-pair `world.get::<&UnitOwner>(entity2)` same-owner check and `world.get::<&UnitPosition>(entity2)` lookup with these maps (L168–177). Per-pair ECS lookups drop from ~7 to ~4 (stats×2, flags×2, equipment×2 stays; owner+position become map hits).
4. **Do not** re-derive candidates from `units_by_player` in this change; a future change may do so behind a golden-trace test that proves order invariance.

This delivers the user-requested TickContext avenue (removes per-candidate String clones + per-pair owner/position ECS queries) without risking the chaotic-order cliff.

Signature change (combat.rs):
```rust
pub fn run(
    world: &mut World,
    world_entity: hecs::Entity,
    spatial: SpatialHash,
    ctx: &TickContext,
    scratch: &mut CombatScratch,
) -> Vec<hecs::Entity>      // call `scratch.clear()` at the top
```

Call site (game.rs ~L322):
```rust
let dead_entities = if let Some(ref ctx) = ctx {
    tick_system!("combat", &mut self.world, self.world_entity,
        systems::combat::run(&mut self.world, self.world_entity, spatial, ctx, &mut self.combat_scratch))
} else {
    Vec::new()
};
```
(`ctx` is an owned `Option<TickContext>`, so no borrow of `self.world` conflicts with `&mut self.world`/`&mut self.combat_scratch`.)

## 6. Implementation Steps (ordered)

1. **`CombatChange` + `attrition_from` plumbing.** Add `working_equipment` field; change `attrition_from` to `&[Equipment]`; update construction sites. `cargo check`.
2. **Scratch API.** `pub struct CombatScratch`, `pub fn clear()`, remove dead-code attr. `cargo check`.
3. **Signature + TickContext maps.** New `run(..., ctx, scratch)`; `scratch.clear()`; build `entity_owner`/`entity_pos` from `ctx.units_by_player`; import `TickContext`. `cargo check`.
4. **Per-pair lookup swap (Part C).** Owner + position via maps, keep everything else identical. `cargo test combat` (tests updated in Step 9; until then compile-gated update of call sites in test helpers).
5. **Defender compounding (Part A1).** Replace defender read with effective-stats block; damage math unchanged. This alone restores the pre-refactor casualty behavior.
6. **Equipment compounding (Part A2).** Per-engagement `working_equipment` init + attrition inside both accumulation blocks.
7. **Moved-flag bulk sweep + retreat handling (Part A4/A5).** Remove `mf.moved=false` from batch apply; single `world.query::<&mut UnitFlags>()` sweep; retreats folded in.
8. **Game wiring (Part B).** `combat_scratch` field + call site in `game.rs`. `cargo check`.
9. **Update existing tests + add regression tests.** Helpers `make_context()` (via `TickContext::build(world, world_entity).unwrap()`) and a local `CombatScratch::new()`. New tests:
   - `defender_takes_compounding_damage`: 3 same-owner attackers vs 1 defender, all co-located → defender `men < 990` (proves >1 hit applied).
   - `cumulative_damage_can_kill`: 10 weak attackers vs a 50-men defender → defender in `dead`.
   - `equipment_attrition_compounds`: defender with 10 rifles attacked by 2+ enemies → rifles < old single-attrition result (and == old compounded result).
   - `retreat_clears_fighting_flag`: isolated fighting unit → `fighting == false`.
   - `scratch_capacity_survives_clear`: fill 100 entries, `clear()`, assert `capacity() >= 100`.
10. **Restore the 3-unit test bound to `(990.0..1000.0)`.** Rationale: with defenders compounding, each unit is attacked exactly once in the test (they're all co-located but one-attack-per-unit), so each ends ~995 as pre-refactor; run once to confirm the value before tightening.
11. **Full suite + clippy + fmt.** `cargo test`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo fmt --all -- --check`.
12. **Benchmark A/B verification** (§7).

## Implementation Outcome Addendum (2026-08-09)

Implemented by the EXECUTION agent. Final solution deviates from the design above as follows (all majored deviations measured, not assumed):

1. **Fallback clause invoked.** The two-phase HashMap approach, implemented twice (buggy then with defender compounding + equipment accumulation fixed), could not beat the baseline: corrected two-phase measured **188.8ms** vs 163.4ms target. The plan's own fallback (restore the old per-pair direct-write pattern) was executed.
2. **Final code = HEAD loop verbatim + one delta.** `combat.rs` is the committed pre-refactor direct read-modify-write loop (compounding inherent via immediate ECS writes) with the only addition being a Game-owned `CombatScratch` (resolved/fought/dead_set/had_enemy_nearby/nearby/dead) with `clear()` for cross-tick capacity reuse. Signature: `run(world, world_entity, spatial, scratch: &mut CombatScratch)`.
3. **TickContext maps measured net-negative (~+15ms)** at benchmark density (per-tick map build over all units exceeds the per-pair `world.get` lookups it replaces) — the requested TickContext avenue was evaluated and rejected on evidence; signature takes no `ctx`.
4. **Test bound kept at `(985.0..1000.0)`.** Empirically unit B lands at 989.53 (org-penalized counter damage); even HEAD's committed `(990.0..1000.0)` bound fails for it. The bound relaxation in the original diff was therefore correct, not a regression smell.
5. **Verification:** `cargo test` 167/167 green (incl. 5 new regression tests), clippy clean (one pre-existing `spatial_hash.rs` dead-code warning, untouched), fmt clean. Per user decision, the release benchmark was **skipped** — code is byte-for-byte HEAD behavior (plus scratch reuse), so performance is expected ≈163.4ms baseline; run the §7 commands later to confirm.
