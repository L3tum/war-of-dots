## Context

War of Dots is a Rust + TypeScript LAN RTS game with:
- **Server:** Axum (HTTP/WS) + raw TCP, single `game_server.rs` (2,379 lines)
- **Game Engine:** ECS via hecs 0.10, `Game` wraps `hecs::World`, 12+ systems per tick
- **Protocol:** CBOR-encoded delta-based state sync
- **Frontend:** TypeScript + Canvas renderer, 300+ line Connection class
- **Replay:** JSONL log, handles only 3 of 7+ action types
- **LLM Agents:** OpenAI/Anthropic/Ollama providers, configurable per slot

A comprehensive 7-theme review found **45 issues**: 11 critical, 12 high, 15 medium, 7 low/over-engineering. This plan provides file-level implementation details organized into 8 work packages.

## WP-A: Security & Authorization (P0)

### A-1. SetSlotLlmConfig requires lobby creator authorization

**File:** `src/server/game_server.rs` - `handle_client_message()`, `SetSlotLlmConfig` branch

**Change:** Before calling `lobby_manager.set_slot_llm_config()`, verify the requesting player is the lobby creator.

```rust
let (player_id, lobby_code) = server.player_map.lock().await.get(conn_id).cloned()...;
let is_creator = {
    let lobby_manager = server.lobby_manager.lock().await;
    lobby_manager.get_lobby(&lobby_code)
        .map(|l| l.creator == player_id)
        .unwrap_or(false)
};
if !is_creator {
    let resp = ServerMessage::Error { message: "Only the lobby creator can configure LLM slots".to_string() };
    let encoded = encode_message(&resp);
    let _ = player_sender.send(encoded).await;
    return;
}
```

**Same check for:** `SetSlotLlm`, `AddLlmPlayer` - these should also be creator-only.

**Test:** Create lobby as player A, join as B -> `SetSlotLlmConfig` from B rejected.

### A-2. Keep client-settable base_url (no change needed)

**File:** `src/server/protocol.rs` - `LobbyMessage::SetSlotLlmConfig` struct

**Decision:** Players can "bring their own LLM" - keep `base_url: Option<String>` as-is. The security concern (attacker redirecting LLM traffic) is mitigated by A-1 (only lobby creator can set LLM config) and the LAN-only nature of the game. No code change needed.

### A-3. Message size limits (1 MiB) on TCP and WebSocket

**File:** `src/server/game_server.rs` - `handle_tcp_client()` (~1231) and `handle_ws_game()` (~1279)

**Change:** Add `const MAX_MESSAGE_SIZE: usize = 1_048_576;` and check before `decode_client_message()`.

**Test:** Send 2 MiB message -> connection closed, no server crash.

### A-4. In-game commands verify unit/city ownership

**File:** `src/server/game_server.rs` - command dispatch in `handle_client_message()` / tick loop

**Change:** Verify ownership at the **server layer** before dispatching to the game. The server already knows `player_id` from `player_map.get(conn_id)`. Check that the unit/city belongs to that player before calling game methods. No new parameters needed on game methods.

```rust
// In the tick loop, when receiving MoveTroop { unit_id, path }:
let player_id = server.player_map.lock().await.get(conn_id).map(|(pid, _)| pid.clone());
if let Some(pid) = player_id {
    // Verify unit belongs to this player via Game::get_unit_owner()
    if game.get_unit_owner(&unit_id) == Some(pid) {
        game.move_troops(&unit_id, path);
    }
    // Otherwise silently drop - not their unit
}
```

Apply same pattern to: `RecruitUnit` (city ownership), `ToggleHealing`, `ToggleResupply`, `EmbarkUnit`, `DisembarkUnit`. Add a lightweight `Game::get_unit_owner(&str) -> Option<String>` helper using the entity_registry + ECS query.

**Test:** Player A tries to move Player B's unit -> command silently dropped.

### A-5. CORS configured via tower-http middleware

**File:** `src/server/game_server.rs` - `run()` method, router construction

**Change:** Add `CorsLayer::new().allow_origin(Any).allow_methods(Any).allow_headers(Any)` middleware.

**Test:** `curl -X OPTIONS http://localhost:PORT/` -> `Access-Control-Allow-Origin: *`.

### A-6. Deserialization errors return generic messages

**File:** `src/server/game_server.rs` - error handling in TCP and WS handlers

**Change:** Return `ServerMessage::Error { message: "Invalid message format" }` instead of full error details.

**Test:** Send invalid CBOR -> response is "Invalid message format".

## WP-B: Gameplay Correctness (P0)

### B-1. Combat damage: rename variables for clarity

**File:** `src/game/systems/combat.rs` - lines 93-108

**Analysis:** The damage model is **mathematically correct**: `dmg_def = a_eff * mod` is damage TO the defender (proportional to attacker strength). The naming is just confusing.

**Change:** Rename `dmg_def -> dmg_to_defender` and `dmg_att -> dmg_to_attacker` with clarifying comments. No logic change.

**Test:** Existing combat tests pass unchanged.

### B-2. Recruitment: check manpower before deducting funds

**File:** `src/game/game.rs` - `recruit_unit()` (~413-447)

**Change:** Validate all preconditions (funds, manpower, city ownership) BEFORE any mutations. Deduct resources only after all checks pass.

**Test:** Funds >= cost but manpower < required -> funds unchanged after failed recruitment.

### B-3. Surrender: remove encircled exemption

**File:** `src/game/systems/surrender.rs`

**Change:** Remove `&& !flags.encircled` from the surrender condition.

**Test:** Update test - encircled unit at 4% men -> surrenders.

### B-4. Units spawn with full organization

**Change:** `organisation: unit_type.max_organisation` (was `0.0`)

**Test:** Newly recruited unit has `organisation > 0`.

### B-5. City capture: deterministic under contention
