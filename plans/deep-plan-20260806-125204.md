# Deep Plan: War of Dots — 3-Issue Quality Pass

Pipeline: REFINE → RESEARCH → COMPOSE (sequential subagents, driver-verified). Status: ready for review.

## Problem Statement

Three independent bugs degrade the player experience:
1. **Pointer gestures bleed into the browser** — right-click+drag camera pan triggers context menus, navigation, or touch-scroll despite Pointer Events API usage.
2. **Orphaned games** — when the last human player disconnects, the game keeps running (LLM agents remain, spectators don't count as active presence).
3. **Double-start races** — `StartGame` can be triggered repeatedly, spawning a second `GameRoom` that silently overwrites the first under the same `lobby_code` key in the `games` map.

## Context

### Architecture overview
- **Server** (Rust): `game_server.rs` is the central message router and game spawner. `room.rs` defines `PlayerConnection` (Player/Spectator enum), `PlayerSender`, and `GameRoom`. `lobby.rs` manages lobbies via `LobbyManager`.
- **Frontend** (TypeScript): `controls.ts` handles pointer events; `lobby.ts` manages lobby UI; `spectator.ts` shows GameOver overlay; `connection.ts` dispatches server messages.
- **Protocol**: CBOR-encoded messages via `protocol.rs`. `ServerMessage::GameOver`, `ServerMessage::Error`, `ServerMessage::LobbyUpdate` already exist.
- **Game loop** lives inside `GameRoom::new()` (spawned in `game_server.rs:~1908` as `tokio::spawn`). The tick loop is ~line 400–650 of `game_server.rs`.
- **StartGame handler** is at `game_server.rs:1666`. It calls `lobby_manager.get_first_lobby()` (line 1680), builds `GameRoom::new()` (line 1908), and inserts into `games.insert(lobby_code, room)` (line 1921). **No check** for an already-running game.
- **PlayerConnection enum** (`room.rs:17`): `Player { id, tx }` | `Spectator { tx }`. Human players are `Player`, spectators are `Spectator`. LLM agents are NOT in the `players` vector — they are `JoinHandle` tasks in `spawned_handles` that receive state via broadcast channels.

### Existing game-end paths (in tick loop, `game_server.rs`)
| Path | Trigger | Line | Behavior |
|------|---------|------|----------|
| A | `active_count == 0` | ~523 | Draw GameOver, record, abort LLM, break |
| B | `total_players > 1 && active_count == 1` | ~550 | Winner GameOver, record, abort LLM, break |
| C | `players.is_empty()` | ~626 | GameOver, `games.remove(&room_id)`, abort LLM, break |

**Bug in Path C:** `players` contains both `Player` and `Spectator` variants. If the last human disconnects but LLM agents remain (in `spawned_handles`), the game continues. `players.is_empty()` only fires when ALL connections (including spectators) drop.

### Existing frontend state transitions

- `ClearSpectator` → `spectator.clearAll()` in `connection.ts:170`
- `GameOver` → `spectator.gameOver()` in `connection.ts:172`, which shows `#game-over-overlay`
- `Error` → already handled (shows status messages)
- `StartGame` button (`#start-game-btn`) has no disable logic (`lobby.ts:63–65`)

## Design

### Issue 1: Prevent pointer gesture bleed

**Approach:** Add `e.preventDefault()` to the `pointermove` handler when `isDragging` is true. The existing `pointerdown` already calls `preventDefault()` for button 2 (right-click) and calls `setPointerCapture(e.pointerId)`. The `contextmenu` event is suppressed, `touch-action: none` is in `index.html`. The single missing piece is that `pointermove` during a drag does NOT call `preventDefault()`, which means the browser can still interpret the movement as a gesture (scroll, navigate).

**Rationale:** `preventDefault()` on `pointermove` while dragging is the standard way to fully suppress browser gesture handling during pointer captures. Since `setPointerCapture` already ensures events keep coming even outside the canvas, adding `preventDefault()` at this point completes the suppression.

### Issue 2: End game when last human player leaves

**Approach:** After the existing `alive` filter (line ~621–625), add a new check that counts remaining human players (`PlayerConnection::Player` variants, excluding `Spectator`). If zero human players remain, trigger game end with an "abandoned" GameOver.

**Key design decisions:**
- **Grace period:** Default 0 ticks (immediate). Configurable via a `grace_period_ticks` constant at the top of the file.
- **"No player" definition:** No `PlayerConnection::Player` variants remain. Spectators do NOT keep the game alive. LLM agents do NOT count as human presence.
- **Edge case — all-LLM benchmark:** If there were never any human players (e.g., `human_players` was empty at spawn), the game should also end immediately since there's no one watching. Handled because `human_count == 0` is true in this case too.
- **Game cleanup:** Same as Path C — broadcast GameOver, record in storage, `games.remove(&room_id)`, abort LLM handles, break.
- **Winner message:** "Game abandoned — no human players remaining" with winner set to "Abandoned".

**Where to add:** After line ~625 (`players = alive`), before the existing `if players.is_empty()` block. A separate, more aggressive check that fires when human players are gone even if spectators remain.

### Issue 3: Block StartGame when a game is already running

**Approach:** Two-layer guard.

**Server-side (primary guard):** Before spawning `GameRoom`, check `server.games.contains_key(&lobby_code)`. If true, return an `Error` message. This is the source of truth because `games` is the authoritative map of running rooms (the same key used to insert the room).

Additionally, remove the lobby from `lobby_manager.lobbies` after successfully starting (via a new `LobbyManager::remove_lobby` method). This is preferred over a `game_started` flag because a flag can desync if the game room is aborted; a consumed lobby is a clean one-way transition matching the intent that a lobby exists to start a game.

**Frontend (UX guard):** Disable `#start-game-btn` immediately on click. Re-enable on `GameOver` or `Error` messages.

  ```rust
  let human_count = players.iter()
      .filter(|p| matches!(p, PlayerConnection::Player { .. }))
      .count();

  if human_count == 0 {
      let winner_id = determine_winner(&game);
      let player_ids: Vec<&str> = game.players().keys().map(|s| s.as_str()).collect();
      let end_time = std::time::SystemTime::now()
          .duration_since(std::time::UNIX_EPOCH)

      storage_clone.record_game_end(

          &[winner_id.as_deref().unwrap_or("")],
          &player_ids,
          game.player_stats(),
          game.settings().use_standard_ruleset,
      );
      let msg = ServerMessage::GameOver {
          winner: "Abandoned".to_string(),
          game_id: room_id.clone(),
          message: "Game abandoned — no human players remaining".to_string(),
      };
      let encoded = encode_message(&msg);
      for player in &players {
          let _ = player.tx().send(encoded.clone()).await;
      }
      {
          let server = server_state.lock().await;
          let mut games = server.games.lock().await;
          games.remove(&room_id);
      }
      for handle in spawned_handles {
          handle.abort();
      }
      break;
  }
  ```

### Issue 3: Block StartGame when a game is already running

#### Server-side guard

- [ ] **3.1** `src/server/game_server.rs` — In the `LobbyMessage::StartGame` handler (line ~1666), capture the lobby code and check `games` before spawning:

  ```rust
  let server = server_state.lock().await;
  let lobby_manager = server.lobby_manager.lock().await;
  let games_guard = server.games.lock().await;
  if let Some((code, lobby)) = lobby_manager.get_first_lobby() {
      // Guard: reject if a game is already running for this lobby
      if games_guard.contains_key(code) {
          let error_msg = ServerMessage::Error {
              message: "A game is already running for this lobby".to_string(),
          };
          let encoded = encode_message(&error_msg);
          for p in &lobby.players {
              let _ = p.connection.send(encoded.clone()).await;
          }
          drop(games_guard);
          drop(lobby_manager);
          drop(server);
          return;
      }
  ```
  (Lock ordering is safe: all three are sub-mutexes of the same `server` struct.)

## Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Issue 1: `preventDefault()` on `pointermove` interferes with legitimate browser behavior | Scoped to `isDragging` (right-click only); left-click selection path unaffected. |
| Issue 2: Race between `human_count == 0` and `players.is_empty()` fallback | New check placed before the fallback; fallback only fires when both humans AND spectators are gone. No conflict. |
| Issue 2: Abrupt LLM-agent teardown | `spawned_handles` aborted (same as existing paths); agent `recv()` on dropped sender fails as well. |
| Issue 3: Lock ordering / deadlock (lobby_manager + games) | Both are sub-mutexes of the same `server` struct, acquired in consistent order; no deadlock. |
| Issue 3: Lobby broadcast after removal | Restructured to capture player senders and broadcast BEFORE `remove_lobby`. |
| Issue 3: Error not reaching requester | Error broadcast to all `lobby.players` (requester is one of them). |
