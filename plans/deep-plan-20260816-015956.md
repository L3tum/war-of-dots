## Context

The influence system was designed so that **vision and influence share the same circle**, and
**influence interacts with enemy influence** to produce a territory border (the equilibrium line
where opposing forces balance). The encirclement system was supposed to consume this pre-computed
territory for its flood-fill, not re-compute the dominant-player grid itself.

**Current broken state:**
1. Vision is a Chebyshev **square** (r3), influence is a Euclidean **circle** (r5) — different shapes, different radii.
2. The "dominant player per cell" (territory) computation lives in `encirclement.rs::build_dominant_player_grid`, not in `influence.rs`.
3. The wire protocol sends raw per-player **influence sums** (values like 0, 1, 5, 6…) as `border_grid`, but the frontend interprets them as **player indices** for color lookup — producing garbled borders.
4. Encirclement re-computes the dominant grid from per-player influence every 30 ticks, duplicating work that belongs in the influence system.

**Intended outcome:**
- One circle per source (unit/city). Vision = influence support (same cells).
- Influence is compared across players to produce a **territory grid** (u8: player index or 255=NONE).
- The territory grid IS the border — sent to clients, used by encirclement, rendered correctly by the frontend.
- Encirclement reads the pre-computed territory, no re-computation.

## Design

### Core principle: one circle, one territory

For each source (unit or city), a **single** Euclidean circle pass writes both vision (bool) and
influence (u16 weight) into the same cells. The per-player influence grids are then compared in a
single sweep to produce the territory grid. This territory grid is the single source of truth for
encirclement and the wire protocol.

### Vision = Influence (same circle, same cells)

| Source | Circle radius | Vision | Influence weight |
|--------|--------------|--------|-----------------|
| Flat unit | r5 | true | +1 (default) |
| Hill unit | r10 (5×2.0) | true | +1 (default) |
| City (any terrain) | r7 (5×1.5) | true | +1 (default — **equal to units**) |

Vision only **increases** relative to current (r3 square ⊂ r5 circle — all previously-visible
cells remain visible; the circle extends further). No cells are lost.

Hills: the terrain modifier (×2.0) applies to the **circle radius** (5→10), which extends both
vision and influence simultaneously. There is no longer a separate "vision radius" vs "influence
radius" — they are the same circle.

### Influence knobs are configurable (for playtesting)

**Design decision (per review feedback):** units and cities use the **same** influence weight
by default (both `1`). A city's advantage over a lone unit comes purely from its larger radius
(r7 vs r5), and stacking multiple equal-weight units still scales dominance (5 units > 1 unit at
a cell). The previous city ×5 weight is removed. All influence parameters are exposed through a
single `InfluenceSettings` struct so they can be playtested without recompiling balance:

```rust
/// Tunable influence/vision parameters (game balance). Defaults = equal weights.
#[derive(Debug, Clone)]
pub struct InfluenceSettings {
    /// Influence added per cell by a unit (default 1).
    pub unit_weight: u16,
    /// Influence added per cell by a city (default 1 — equal to units).
    pub city_weight: u16,
    /// Base circle radius for a unit (default 5.0).
    pub unit_radius: f32,
    /// City radius = unit_radius × this multiplier (default 1.5 → r7).
    pub city_radius_multiplier: f32,
    /// Hill terrain radius multiplier applied to unit radius (default 2.0 → r10).
    pub hill_radius_multiplier: f32,
}
impl Default for InfluenceSettings {
    fn default() -> Self {
        Self {
            unit_weight: 1,
            city_weight: 1,
            unit_radius: 5.0,
            city_radius_multiplier: 1.5,
            hill_radius_multiplier: 2.0,
        }
    }
}
```

This struct is added to `GameSettings` (as `pub influence: InfluenceSettings`) and plumbed into
`influence::run` → `compute_player`. It is optionally overridable from `config.toml`
(`standard_ruleset.influence`) for playtesting; if absent, `Default` (equal weights) applies.

**Radius cap:** the precomputed `CIRCLE_SPANS` table is sized from `InfluenceSettings`'s worst
case radius. With defaults, the max radius is hill-unit `5 × 2.0 = 10`. We keep the static
`MAX_RADIUS` sized to cover the configured maximum — computed as
`ceil(max(unit_radius, unit_radius × city_radius_multiplier) × hill_radius_multiplier)` at
`CIRCLE_SPANS` init. If a playtest raises a multiplier beyond the precomputed span, the span
lookup must clamp (`.min(MAX_RADIUS)`) rather than panic. See Step 13.

### Territory grid

`Vec<u8>` of size W×H, where:
- `0..N-1` = player index (deterministic: sorted player IDs)
- `255` = NONE (no player has influence at this cell)

Computed at the end of `influence::run()`, stored on `WorldBundle.territory`. Read by:
- `encirclement::run()` — replaces `build_dominant_player_grid`
- `game.border_grid_2d()` — wire protocol (values are now player indices)
- `game.supervisor_border_grid()` — spectator/replay (same grid)

### Wire protocol: no type change

`border_grid: Option<Vec<Vec<u32>>>` stays. Values change from influence sums to player indices
(0..N, 255). The frontend already expects player indices — the rendering will now work correctly.

## Reuse

- **`circle_spans()` / `CIRCLE_SPANS`** (influence.rs) — precomputed Euclidean circle spans. Now
  the ONLY iteration primitive for both vision and influence. `MAX_RADIUS` stays a compile-time
  `const` sized to cover the default worst case (hill unit `5 × 2.0 = 10`). Because radii are
  now configurable, the span lookup clamps: `.get(radius.min(MAX_RADIUS) as usize)` — a playtest
  that pushes a radius past `MAX_RADIUS` degrades to the largest precomputed span instead of
  panicking. If a playtest needs a bigger max, bump `MAX_RADIUS` (table is ~3KB, trivial).
- **`build_dominant_player_grid`** (encirclement.rs l.113–141) — moved to influence.rs as
  `build_territory_grid()`. Logic identical: sorted players, strict `>`, zero→NONE.
- **`mark_safe_edges_multi`**, **`mark_safe_near_cities_multi`**, BFS loop (encirclement.rs) —
  unchanged. Only the input source changes (read territory instead of computing dominant).
- **`InfluenceScratch`**, **`add_influence()`** — unchanged.
- **`ctx.player_id_to_index`** — NOT used for territory (it's first-seen order, not sorted).
  Territory uses sorted-keys mapping for deterministic tie-breaking.

### Step 3 — Add `build_territory_grid` to influence.rs

Add after `compute_player`, before `run()`:

```rust
/// Sentinel for "no player has influence at this cell."
pub(crate) const NONE: u8 = 255;

/// Compute the territory grid: which player has the highest influence at each cell.
/// Players iterated in sorted order; strict `>` means lowest-sorted ID wins ties.
/// Returns `Vec<u8>` — player index or NONE (255) where no influence.
pub(crate) fn build_territory_grid(
    border_grids: &HashMap<String, Vec<u16>>,
    player_to_idx: &HashMap<&str, u8>,
    grid_size: usize,
) -> Vec<u8> {
    let mut dominant = vec![NONE; grid_size];
    let mut max_inf = vec![0u16; grid_size];

    let mut player_ids: Vec<&str> = player_to_idx.keys().copied().collect();
    player_ids.sort();
    for player_id in player_ids {
        let idx = *player_to_idx.get(player_id).unwrap();
        if let Some(grid) = border_grids.get(player_id) {
            for i in 0..grid_size {
                if grid[i] > max_inf[i] {
                    max_inf[i] = grid[i];
                    dominant[i] = idx;
                }
            }
        }
    }
    for i in 0..grid_size {
        if max_inf[i] == 0 {
            dominant[i] = NONE;
        }
    }
    dominant
}
```

```rust
/// Values are player indices (0..N) or 255 (NONE/unclaimed).
/// Note: `player_id` is accepted for API compatibility but ignored —

pub fn border_grid_2d(&self, _player_id: &str) -> Option<Vec<Vec<u32>>> {
```

```typescript
    this.borderCacheEdges.push({ gridX: x, gridY: y, dir: 'h', ownerA: p1, ownerB: p2 });
}
if (p1 !== p3 && p1 !== TERRITORY_NONE && p3 !== TERRITORY_NONE) {

```

This prevents borders from being drawn at the boundary between claimed and unclaimed territory.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| `WorldBundle::new()` missing `territory` field → compile error | Build fails | Step 1 explicitly adds initialization. |
| 4 game.rs tests assert influence sums (5, 6, 1) | Test failures | Step 8 lists exact fixes. |
| Frontend renders `PLAYER_COLORS[255 % N]` if guard missed | Wrong colors (no crash) | Step 9 adds guard; Step 10 tests it. |
| Hill r10 is a large balance change (4× area vs r5) | Gameplay | Intended by design. `InfluenceSettings.hill_radius_multiplier` (default 2.0) is tunable via config.toml without recompiling. |
| **`influence::run` signature change** (+`settings` arg) breaks direct callers | Build fails in microbenchmarks + game.rs | Step 13 lists every call site (game.rs tick, 5 microbenchmark fixture sites). Compiler catches any miss. |
| **`GameSettings` new field** breaks all struct literals | Build fails across ~7 sites | Step 13 lists them; Rust requires all fields in a literal so `cargo build` enumerates every missed one. |
| **City weight 5 → 1** changes city dominance | A lone city no longer out-influences 5 stacked units at one cell | Intended (equal weights per feedback). City still wins on radius (r7 > r5) and 5+ units still stack. Playtest via `city_weight`. |
| `CIRCLE_SPANS` with MAX_RADIUS=10: `OnceLock` re-init | One-time cost | Safe — `OnceLock` only initializes once. Spans for r0–r10 are ~3KB. |
| Territory grid empty on first tick (before influence runs) | Encirclement reads empty grid | `border_grid_2d` returns `None` when grid is empty. Encirclement at tick 30 always has a populated grid (influence ran at tick 3). Safe. |
| `border_grid_2d` ignoring `player_id` | Semantic confusion | Doc comment + `_player_id` naming. All callers already pass it; no API break. |
| LLM misinterprets territory values | Strategic errors | Step 12 adds prompt clarification. |
| Player set changes between influence and encirclement runs | Stale indices (≤3 ticks) | Acceptable. Next influence run (≤3 ticks) corrects. Encirclement dirty-flag ensures it only runs after a fresh influence. |

## Open Design Question (Non-Blocking)

**Hill multiplier (default ×2.0 → r10)**: On a 20×20 map, a hill unit at the center projects to
nearly the entire map. If this feels too powerful, set `hill_radius_multiplier = 1.5` (r7, same
as city) or `1.2` (r6) in `config.toml`. No code change needed — it's a single tunable on
`InfluenceSettings`.
