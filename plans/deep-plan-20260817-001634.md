# Deep Plan: Allocation Measurement + Autovectorization Verification

## Context

The user wants to make more informed choices about *how* performance optimizations help the game, and whether autovectorization (AVX2) is kicking in or if manual SIMD is needed. Two capabilities are needed:

1. **Allocation measurement** during benchmark runs (both stack and heap)
2. **Autovectorization verification** — a feature + unit test that checks whether the compiler already vectorized the hot loops

### Critical Discovery

**AVX2 is already enabled** for `x86_64-unknown-linux-gnu`, `x86_64-apple-darwin`, `x86_64-pc-windows-msvc` via `.cargo/config.toml` (`target-cpu=x86-64-v3`). The **`x86_64-unknown-linux-musl` target (used by `make build-release`) is missing this**, causing the shipped static binary to silently fall back to SSE2 only. This is a real, verifiable inconsistency.

The only prime autovectorization candidate in the codebase is `influence.rs::fold_influence_into` — a contiguous `Vec<u16>`/`Vec<u8>` branchy-select loop that LLVM almost certainly already vectorizes under the existing flag. All other hot loops (movement, combat, nearby_enemies) are branchy, data-dependent, or use non-contiguous access patterns that prevent vectorization.

**The question is therefore not "enable AVX2" (already done) but "prove it worked, and have the measurement to judge future changes."**

---

## Approach

### Architecture (reviewed & approved)

- **Custom counting allocator** (`src/bench_alloc.rs`, ~80 lines wrapping `std::alloc::System` with atomics) for per-tick and per-benchmark allocation tracking. Chosen over the `alloc_tracker` crate because we need **per-tick `snapshot()`/`diff()` granularity** to feed a per-tick chart — `alloc_tracker`'s span-based API is designed for batched criterion-style measurement and doesn't expose incremental counter reads.
- **Static size-of table** for stack usage proxy (addresses the "both stack and heap" ask)
- **dhat-rs** (dev-dep) for heap-assertion invariant tests
- **`cfg!(target_feature = "avx2")` guard test** — CI tripwire proving the build config is correct
- **`check_vectorization.sh`** — on-demand asm-grep diagnostic (evidence, not proof)
- **Musl fix** — 1-line config correction

### What we are NOT doing

- No manual AVX2/intrinsics rewrite (the asm script + guard exist to *answer* "did it already vectorize")
- No `criterion` migration — Criterion 0.8.2's `BenchmarkGroup::finish()` still returns `()` (no in-process results API). However, Criterion **does save results as JSON** to `target/criterion/<group>/<bench>/new/estimates.json` after each run, and `cargo-criterion --message-format=json` provides a machine-readable stream. So the *blocker* is not absolute — results are accessible post-run via file parsing — but for our use case (integrating timing + allocation stats + battle benchmark data into a single HTML report in one process, with custom iteration counts and setup patterns), the existing custom harness is still the better fit. The JSON file approach would require a post-processing step, a separate `benches/` directory, and re-implementing the setup/fixture pattern that the custom harness handles cleanly.
- No dynamic peak-stack measurement (heaptrack is the escape hatch; static size table is the pragmatic answer)

## Code Sketches

### 1. `src/bench_alloc.rs` — Counting Allocator with Snapshot API

~80 lines wrapping `std::alloc::System` with `AtomicUsize` counters. The `snapshot()`/`diff()` pattern enables per-tick granularity (snapshot before each tick, snapshot after, diff = that tick's allocations).

> **Why not `alloc_tracker`?** The `alloc_tracker` crate (v0.7.1, MIT) is a well-maintained allocation tracker, but its API (`Session` → `Operation` → `ProcessSpan.iterations(n)`) is designed for **batched** measurement (one span covers many iterations, result is a batch average). We need **incremental** per-tick counter reads to build a `Vec<f64>` series for the per-tick chart. A simple atomics wrapper around System gives us exactly that, with zero dependencies.

```rust
//! Counting global allocator for benchmark allocation profiling.
//! Active only under `--features bench-alloc`.
//! Wraps `std::alloc::System` (the default allocator) with Relaxed atomics.
//! Overhead: ~1 atomic add per allocation (~0.5 ns).
//!
//! NOT compatible with Miri (replaces the global allocator).
//! Mutually exclusive with dhat (both install a global allocator).

#![cfg(feature = "bench-alloc")]

use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering};

#[global_allocator]
static ALLOC: CountingAlloc = CountingAlloc;

struct CountingAlloc;

static ALLOCS: AtomicUsize = AtomicUsize::new(0);
static BYTES: AtomicUsize = AtomicUsize::new(0);

impl GlobalAlloc for CountingAlloc {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        let p = System.alloc(layout);
        if p.is_null() { return p; }
        ALLOCS.fetch_add(1, Ordering::Relaxed);
        BYTES.fetch_add(layout.size(), Ordering::Relaxed);
        p
    }
    unsafe fn dealloc(&self, _ptr: *mut u8, _layout: Layout) {
        // We don't decrement — we track total alloc calls and total bytes churned.
        // This is what the user wants: "how many allocations does this tick make?"
        System.dealloc(_ptr, _layout);
    }
    unsafe fn realloc(&self, ptr: *mut u8, layout: Layout, new_size: usize) -> *mut u8 {
        let p = System.realloc(ptr, layout, new_size);
        if p.is_null() { return p; }
        // Count the size delta as new allocation activity
        let delta = new_size.saturating_sub(layout.size());
        if delta > 0 {
            ALLOCS.fetch_add(1, Ordering::Relaxed);
            BYTES.fetch_add(delta, Ordering::Relaxed);
        }
        p
    }
}

/// Point-in-time read of the cumulative counters.
#[derive(Clone, Copy, Default)]
pub struct AllocSnapshot {
    pub allocs: u64,  // total alloc calls since process start
    pub bytes: u64,   // total bytes allocated since process start
}

pub fn snapshot() -> AllocSnapshot {
    AllocSnapshot {
        allocs: ALLOCS.load(Ordering::Relaxed) as u64,
        bytes: BYTES.load(Ordering::Relaxed) as u64,
    }
}

/// Difference between two snapshots (allocations in the region between them).
#[derive(Clone, Copy, Default)]
pub struct AllocDelta {
    pub allocs: u64,
    pub bytes: u64,
}

impl AllocSnapshot {
    pub fn diff(&self, base: AllocSnapshot) -> AllocDelta {
        AllocDelta {
            allocs: self.allocs.saturating_sub(base.allocs),
            bytes: self.bytes.saturating_sub(base.bytes),
        }
    }
}

/// Insurance: prevent accidental double-allocator install.
#[cfg(feature = "heap-profile")]
compile_error!("Cannot enable both bench-alloc and heap-profile — both install a global allocator");
```

### 4. Harness Integration (in `run_bench` and all 4 variants)

**Key fact:** In `run_bench`, `setup()` runs BEFORE `Instant::now()`, so setup is excluded from timing. The allocation snapshot goes at the same point, so setup allocations are excluded.

```rust
// In run_bench (same pattern applies to all 4 variants):

let mut durations = Vec::with_capacity(config.timed);

#[cfg(feature = "bench-alloc")]
let base = crate::bench_alloc::snapshot();

for _ in 0..config.timed {
    setup();  // NOT timed
    let start = Instant::now();
    f();
    let elapsed = start.elapsed();
    durations.push(elapsed);
}

// After the loop — attach to result:
#[cfg(feature = "bench-alloc")]
{
    let d = crate::bench_alloc::snapshot().diff(base);
    let n = durations.len() as f64;
    result.allocs_per_iter = Some(d.allocs as f64 / n);
    result.bytes_per_iter  = Some(d.bytes as f64 / n);
}
```

**Cumulative variants**: divide the two per-iteration fields by `repeats`, same as the time fields.

### 10. `scripts/check_vectorization.sh`

```bash
#!/usr/bin/env bash
# On-demand diagnostic: disassemble the release binary and check whether
# known vectorizable hot functions contain AVX/SIMD instructions.
#
# CAVEATS:
#   - Greps the OUTERMOST symbol (inner #[inline] helpers have no standalone
#     symbol). A positive ("vector ops found") is EVIDENCE but not per-loop
#     proof — other code in the same symbol could emit vector instructions.
#   - A negative (0 vector ops) IS meaningful: the loop almost certainly
#     did not vectorize.
#   - For a definitive per-loop answer, use: cargo rustc --release -- --emit asm
#     and inspect the specific loop region.
#
# Requires an existing target/release/war-of-dots binary (does NOT rebuild
# — build.rs requires node/npm for the frontend).
set -euo pipefail

BIN="${1:-target/release/war-of-dots}"
[[ -f "$BIN" ]] || { echo "error: $BIN not found — run 'cargo build --release' first"; exit 1; }
[[ "$(uname -m)" == "x86_64" ]] || { echo "skip: not x86_64"; exit 0; }

OBJDUMP=$(command -v rust-objdump 2>/dev/null || command -v llvm-objdump 2>/dev/null || command -v objdump 2>/dev/null || true)
if [[ -z "$OBJDUMP" ]]; then
    echo "error: need rust-objdump, llvm-objdump, or objdump (try: rustup component add llvm-tools)"
    exit 1
fi

# Symbols to inspect (outermost, stable in release).
# Note: GridIndex::build is private + small → likely inlined; nearby_enemies::run is the primary target.
FUNCS=("influence.*run" "nearby_enemies.*run")
# Regex for x86-64-v3 (AVX2) vector ops on ymm registers
AVX_RE='ymm|vcmpps?|vaddps?|vshufp?s?|vpermilpd?|vblendvps?|vpadd|vpcmp|vmaxps?|vminps?'

strict="${2:-}"
fail=0
echo "Checking vectorization in: $BIN"
echo "────────────────────────────────────────────────"

for re in "${FUNCS[@]}"; do
    # Extract disassembly for symbols matching the regex
    body=$("$OBJDUMP" -d "$BIN" 2>/dev/null | awk -v re="$re" '
        /<.*>:/ { if (match($0, re)) { f=1; next } else if (f) { exit } }
        f { print }' || true)
    if [[ -z "$body" ]]; then
        echo "  ⚠ not found: $re (likely inlined or not in this binary)"
        if [[ "$strict" == "--strict" ]]; then
            echo "  FAIL: expected symbol missing"
            fail=1
        fi
        continue
    fi
    n=$(echo "$body" | grep -cE "$AVX_RE" || true)
    if [[ "$n" -gt 0 ]]; then
        echo "  ✓ vector ops found: $re ($n SIMD instructions in symbol body)"
        echo "    NOTE: evidence, not per-loop proof. Check asm for loop-specific patterns for certainty."
    else
        echo "  ✗ NOT vectorized: $re (0 vector ops) — candidate for manual SIMD"
        fail=1
    fi
done

echo "────────────────────────────────────────────────"
[[ "$fail" -ne 0 ]] && { echo "RESULT: FAIL"; exit 1; }
echo "RESULT: PASS"
exit 0
```

**Compile combinations:**
- `make test` (no features): dhat tests run, no counting allocator → clean
- `make clippy` (`--all-features`): counting allocator active, dhat tests excluded → clean
- `make bench-alloc`: counting allocator + microbenchmarks → per-tick alloc chart in report
- `make miri`: only works WITHOUT `bench-alloc` (counting allocator is Miri-incompatible)

| System | Vectorization likely today? | Notes |
|---|---|---|
| **influence** | **YES** — prime candidate | Contiguous `Vec<u16>`/`Vec<u8>` loops with branchy select → `vmaxps`/`vcmpps`+`vblend`. The `.cargo/config.toml` comment already claims ~29% gain. Verify with the script. |

## Reuse (Existing Code Patterns)

- **`alloc_tracker` crate** (v0.7.1, MIT, 120KB): considered but NOT used — its batched span API doesn't support the per-tick `snapshot()`/`diff()` granularity we need for the per-tick chart. Documented here as the alternative if batched-only measurement were sufficient in the future.
- **HTML delta helpers** in `src/benchmark.rs` — `cell_delta()`, `delta_html()`, `micro_delta_ns()`, `fmt_ns()` are generic on `f64` and work for allocation values
- **Field-presence pattern** — `results.summary.get("...").and_then(|v| v.as_f64())` renders `null` as absent, so new `Option` fields are naturally backward-compatible
- **`run_bench_with_setup` pattern** — the `setup` closure runs before the timer, so the allocation span at the `Instant::now()` point naturally excludes setup
- **`compute_stats` + percentile** in `microbenchmarks.rs` — the new alloc fields are simple per-iteration averages, no stats computation needed
- **Existing `#[allow(dead_code)]` pattern** (on `make_dummy_entity`) — reuse for the new `Option` fields

## Risks & Caveats

1. **Musl fix = deployment behavior change:** shipped binary will SIGILL on pre-AVX2 hardware. The deployment target must guarantee x86-64-v3 (most modern hardware does; old Xeon/E5 VMs do not).
2. **check_vectorization.sh is evidence, not proof:** a positive can be a false positive (other code in the symbol emits vector instructions). A negative IS meaningful. For definitive per-loop verification, use `cargo rustc --release -- --emit asm`.
3. **Counting allocator changes global allocator identity** (System → wrapper around System). Behavioral risk is minimal (same underlying system allocator). Overhead is ~1 atomic add per allocation (~0.5 ns). NOT compatible with Miri. The per-tick snapshot pattern adds 2 atomic loads per tick — negligible vs. tick cost.
4. **`RUSTFLAGS` env conflict:** `.cargo/config.toml` `rustflags` and `RUSTFLAGS` env are mutually exclusive in cargo (it errors if both are set). The existing file header mentions this. The musl fix adds a config-level entry, which means `RUSTFLAGS=... cargo build` will conflict — this is the pre-existing situation for the other three targets.
5. **Counting allocator + dhat are mutually exclusive** (both install a global allocator). The cfg matrix prevents this, and a `compile_error!` provides extra insurance.
6. **Multi-thread noise:** tokio runtime is started for `--benchmark` (via `#[tokio::main]`), but worker threads don't allocate on the benchmark path. The atomics track all threads; if other threads allocated during the window, their allocs would be included. In practice this is a non-issue for the benchmark path.
7. **Criterion is not a blocker:** Criterion 0.8.2 saves results to `target/criterion/` as JSON files post-run. You *can* parse these programmatically. The custom harness is preferred here not because Criterion can't produce data, but because (a) we need in-process results to combine with alloc stats and battle data in a single HTML report, (b) our benchmarks use a custom setup/fixture pattern that doesn't fit Criterion's `iter_custom` model, and (c) the iteration counts are fixed (not auto-scaled as Criterion does).
