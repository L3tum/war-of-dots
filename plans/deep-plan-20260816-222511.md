# Deep Plan: Optimize the Influence System (compute only, behavior-preserving)

> Status: **Reviewed — APPROVE-WITH-CHANGES applied.** This is the final, corrected
> specification after a RESEARCH → COMPOSE → REVIEW-PLAN pipeline. The reviewer's
> blocking fixes (correct terrain flat-index formula, infeasible Arc ping-pong
> removed, production-dead `borders` unpublish) are folded in below.

## 1. Goal & non-goals

**Goal.** Restore the performance lost by the "full influence system" (commit `55be210`)
by making the per-dirty-tick work cheaper, **without changing any observable output**:
circle shapes, the hill radius r10, the `InfluenceSettings` weights, the sorted
player-order / strict-`>` / lowest-ID-wins tie-break, and the `dirty` early-skip path
are all preserved.

**Non-goals.** No behavior/semantics change. No parallelism (Rayon was already tried at
multiple granularities and rejected per the `influence.rs` module doc, lines 12–13 —
per-player work ~0.1 ms is below dispatch breakeven). The cadence change (A2) is a
**separate, sign-off-required** option, not part of the default scope.

## 2. Context / architecture (verified against code)

- `src/game/systems/influence.rs` is the whole system:
  - `compute_player()` (lines ~95–178) — pure per-player projection. One Euclidean
    circle pass per source writes **both** binary vision and weighted u16 influence into
    flat `[y*w + x]` grids. Unit radius = `unit_radius` (5); hill units × `hill_radius_multiplier`
    (2.0 → **r10**, the intentional new behavior); city radius = `unit_radius × city_radius_multiplier`
    (5×1.5 → r7). Radii clamp to `MAX_RADIUS = 10` (line 33) against the precomputed
    `CIRCLE_SPANS` table (line 40).
  - `build_territory_grid()` (lines 188–214) — dominant player per cell.
  - `run()` (lines 217–281) — dirty gate → per-player compute → build territory → publish
    `Arc::new` of `vision.grids` / `borders.grids` / `territory.grid` into `WorldBundle`.
  - `InfluenceScratch` (lines 63–81) — SupplyScratch-pattern buffer owned by `Game`
    (`game.rs:193`), currently holding only `city_positions`.
- Call site `game.rs` (`tick_game`): runs only when `tick % INFLUENCE_TICK_INTERVAL == 0`
  **and** `self.influence_dirty`. `constants.rs:12` → `INFLUENCE_TICK_INTERVAL = 3`;
  `CITY_CAPTURE_TICK_INTERVAL = 30`. `influence_dirty` is set by movement (`game.rs:640`),
  city capture (`:713`), deaths (`:803`), recruitment (`:881`), city steal (`:1209`).
  A clean tick early-returns (`influence.rs:225–228`) preserving all stored Arcs.
- Consumers of the published grids:
  - `wb.territory.grid` → `encirclement::run` (every 30 ticks) **and** the wire/LLM/replay
    protocol every tick via `border_grid_2d` (`game.rs:1274`).
  - `wb.vision.grids` → per-player/supervisor/union vision for wire/LLM/replay — **MUST stay published**.
  - `wb.borders.grids` (per-player u16) → **write-only in production** (only written at
    `influence.rs:278`; every read is inside `#[cfg(test)]`). Confirmed by the reviewer.

## 3. Root cause summary (verified)

1. **Territory-grid rebuild frequency** (the headline regression). `build_territory_grid`
   is O(players × grid_size) **plus** a second full pass
   `for i in 0..grid_size { if max_inf[i]==0 { dominant[i]=NONE } }` (lines 209–212,
   provably a no-op — see A1). It now runs on **every dirty tick** where `tick % 3 == 0`
   (`game.rs`), whereas the equivalent dominant-player scan previously lived in
   `encirclement.rs::build_dominant_player_grid` (deleted) on the 30-tick cadence →
   ~10× more frequent. It also allocates fresh `Vec<u8>` + `Vec<u16>` + HashMaps + a new
   `Arc` per dirty tick. **Note (reviewer):** the territory scan is a *frequency +
   allocation* win, not the biggest FLOP sink — the per-cell circle stamping (B) is.
2. **Hill units r5 → r10** (`influence.rs:124–132`): span-table cell count 81 → 317 (~3.9×)
   per hill unit. **Intentional; must be preserved.** It only amplifies per-cell costs.
3. **Fresh per-player grid alloc + zero every dirty tick** (`influence.rs:110–111`):
   `vec![false; grid_size]` + `vec![0u16; grid_size]` per player per dirty tick.
4. Pre-existing inner-loop costs, now amplified: per-cell `(0..w).contains(&x)` bounds
   check in the unit pass (line 140) and city pass (line 168); nested
   `terrain.get(x).and_then(|r| r.get(y))` hill lookup **once per unit** (lines 126–127,
   *not* per cell); `player_id.clone()` ×2 + a `player_to_idx` HashMap per dirty tick
   (lines 258–271).

## 4. Optimizations (priority order, per reviewer)

### A1. Fold territory into the per-player pass + delete the dead 2nd pass — **Medium, Low risk, output-identical**
- **What.** Delete the no-op pass at `influence.rs:209–212` (a cell with total influence
  0 never satisfies `grid[i] > max_inf[i]` because both start at 0 / `NONE`, and
  `max_inf` only ever increases, so `dominant[i]` is already `NONE`). Maintain
  `dominant: Vec<u8>` (init `NONE`) + `max_inf: Vec<u16>` (init 0) as a running fold:
  as each player's influence grid is computed, immediately fold it in
  (`if grid[i] > max_inf[i] { max_inf[i]=grid[i]; dominant[i]=idx }`).
- **Hard constraints (reviewer — behavior must not drift):**
  - Iterate **sorted `ctx.units_by_player` keys** and use the **enumeration index** as
    the territory value. `encirclement.rs` re-derives indices by sorting
    `ctx.units_by_player` keys and enumerating; a mismatch sets flags on the wrong player.
  - **Preserve the city-only-player skip** (players with cities but 0 units get no grid —
    existing behavior; do not "fix" it here).
  - **Do not leave two live copies** of the territory logic (drift risk). Either keep
    `build_territory_grid` as the single fold routine (same signature, no 2nd pass) called
    per player, or delete it and move its tests to the new fold helper. Keep the
    `build_territory_grid_*` unit tests green either way.
- **Impact.** Medium — removes 1× grid_size pass, one allocation, and the intermediate
  `updated_border` re-read. Still O(players × grid) (a running-max per player), so it is a
  locality/alloc win, not asymptotic.
- **Reuses.** `InfluenceScratch`; the sorted-keys idiom from `encirclement.rs`.

### C. Stop publishing `wb.borders.grids` (production-dead) — **Medium, Low risk, output-identical**
- **What.** `wb.borders.grids` has **no production consumer** (only `#[cfg(test)]` reads
  it). Keep **one** `Vec<u16>` in `InfluenceScratch`; per player per tick `fill(0)`
  (a cheap memset), compute into it, fold straight into the A1 running territory max, and
  **never move it into the world**. Deletes per dirty tick: 1 `Vec<u16>` alloc + 1
  `updated_border` HashMap entry + 1 `Arc::new` + the world-field write at `:278`.
- **Vision is different and MUST stay published** (`vision_grid_2d`/`supervisor_vision_grid`
  read it every tick). For vision, **keep the per-tick `Vec<bool>` allocation** — it is
  1 byte/cell and reusing it is blocked by the `Arc` publication anyway (see C2 below).
- **Reviewer fix:** the original spec's "two-buffer ping-pong with `std::mem::swap`" is
  **infeasible** behind `Arc<HashMap<_,Vec>>` — once a `Vec` is moved into the Arc the
  world owns it, so it cannot be swapped back (`Arc::try_unwrap` fails under shared refs).
  Do **not** ship that mechanism against current Arc storage.
- **Impact.** Medium (kills the border allocation/HashMap/Arc churn); the memset stays.

### B. Hoist the per-cell x-bounds check (clamp each row's dx range once per row) — **Medium, Low risk, output-identical**
- **What.** The per-cell `if (0..w).contains(&x)` (unit pass line 140, city pass line 168)
  is replaced by clamping the valid x-range **once per row**:
  ```rust
  let y = cy + dy;
  if y < 0 || y >= h { continue; }                 // per row (as today)
  let y_off = (y as usize) * w_usize;
  let lo = (cx + dx_start).max(0);
  let hi = (cx + dx_end).min(w - 1);
  if lo > hi { continue; }
  for x in lo..=hi {
      let idx = y_off + x as usize;
      vision[idx] = true;
      add_influence(inf, idx, weight);
  }
  ```
  Extract both the unit and city passes into one private `fn stamp_circle(vision, inf, cx, cy, r, weight, w, h)`
  backed by `circle_spans()[r]` so the clamping lives in one place.
- **Why identical (reviewer-confirmed):** the written set is
  `x ∈ [cx+dx_start, cx+dx_end] ∧ x ∈ [0, w-1]` = `x ∈ [max(lo), min(hi)]` — provably the same cells.
- **Impact.** Medium — this is the **actual per-cell hot loop** (Σ sources × cells; e.g.
  500 units × ~81 cells, up to ×~317 for hill units). Biggest FLOP target.
- **Reuses.** `circle_spans()`, `add_influence`.

### E. Delete `player_to_idx` HashMap + one `player_id.clone` — **Small, Very low risk, output-identical**
- **What.** The territory index **is** the enumeration counter over the sorted keys, so
  delete the `player_to_idx: HashMap<&str,u8>` in `run()` (and the duplicate in
  `encirclement.rs`) and use `enumerate()` directly. Clone `player_id` **once** per player
  (reuse for the vision insert) instead of twice.
- **Impact.** Small (a few hundred ns/run); also shrinks the debug-profile bar.

### C2. (Optional follow-up, NOT default) vision buffer reuse
- Only if profiling still shows vision allocation mattering: change
  `VisionGrids.grids` from `Arc<HashMap<_,Vec<bool>>>` to a plain
  `HashMap<_,Vec<bool>>` (only `&self` wire accessors read it — no hot system does), then
  compute into a scratch `Vec<bool>` and `std::mem::swap` it with
  `wb.vision.grids.get_mut(player)` (scratch keeps the old capacity → `fill(false)` next
  tick reallocates nothing). *This* is the legitimate ping-pong, and it only works because
  the `Arc` is dropped. Ship as a separate follow-up.

### A2. (DECISION — sign-off required, NOT default) Defer territory publication to the 30-tick cadence
- **What.** Fold + publish `wb.territory.grid` only on `tick % CITY_CAPTURE_TICK_INTERVAL == 0`
  (or when `encirclement_dirty` is pending); other dirty ticks keep the previous territory Arc.
- **Impact.** Big on paper (removes ~9 of 10 territory scans).
- **Tradeoff.** `border_grid_2d` is called **every server tick** for client state, LLM
  advisor, and replays; territory would lag up to 29 ticks behind vision/borders.
  Encirclement itself is unaffected (it reads territory only on its own 30-tick runs, which
  would always be preceded by a fresh fold). **This changes observable freshness, not just
  compute — it requires explicit sign-off.** Revisit only *after* A1/C/B/E if the scan
  still shows up in the profile.

### D. (DEFERRED — formula was wrong) Flatten `TerrainGrid`
- **Reviewer finding (blocking if pursued):** terrain is stored `grid[x][y]` (outer = x,
  inner = y, inner length H). Flattening **preserving layout gives index `x * height + y`**,
  NOT `x + y*width` as the original spec claimed (that is the row-major `[y][x]` formula
  used by vision/border/territory — internally contradictory with "keep outer=x/inner=y").
  Implementing the original formula would silently transpose every terrain read (wrong
  hill/forest/water multipliers in movement, combat, hill-vision) with no compile error.
- **If pursued later:** either keep layout (`x*height+y`) or transpose on flatten to the
  codebase convention (`flat[y*width+x] = old[x][y]`) and update **all** consumers:
  `components.rs` (`TerrainGrid` type/get/`WorldBundle::new`), `world_ext.rs` (`spawn_world`),
  `game.rs` (build + `terrain_grid_2d`), `influence.rs`, `movement.rs`, `combat.rs`, and their
  test fixtures.
- **ROI:** the nested lookup is **once per unit, not per cell** (line 126–127), so the gain
  is small vs. a 6-file blast radius. **Defer** until after A1/C/B/E are landed and
  re-measured; drop if microbenchmarks don't flag terrain lookups.

  layout) or transpose to `y*width+x` and add a `TerrainGrid::get` flat-vs-nested test.
