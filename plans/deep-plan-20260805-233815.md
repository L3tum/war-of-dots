# Deep Plan: Fix WebGPU Rendering & Frontend/Backend Audit — War of Dots

Pipeline: REFINE → RESEARCH → COMPOSE (driver-verified). Status: ready for review.

---

## Problem Statement

The frontend WebGPU rendering produces a blank/white canvas because terrain data sent from the server
as strings (`"Plains"`, `"Hills"`, etc.) is assigned directly into a `Terrain[][]`-typed field without
conversion, causing all terrain colors to fall back to white. Additionally, delta grid merges corrupt
fog-of-war and border state after the first server tick, and the replay path has multiple parity gaps
with the live game path.

The user's request: fix the WebGPU rendering, and audit the rest of the frontend plus the
rendering-relevant backend.

## Root-Cause Analysis (ranked by severity)

### 1. CRITICAL — Terrain string → Terrain instance mismatch
**Chain**: `applyFullState` assigns `state.terrain` (raw `string[][]`) into `gameState.terrain`
(`Terrain[][]`). `marchingSquares` reads `grid[y][x].type` → `undefined` (strings have no `.type`).
`Terrain.colorForType(undefined)` → `undefined`. `hexToRgb(undefined)` → regex fails → returns
`{r:255,g:255,b:255}` (WHITE). Every terrain quad renders white → blank/white canvas.

**Impact**: 100% rendering break. This is the primary "WebGPU rendering doesn't work" symptom.

### 2. HIGH — Delta grid merge corrupts fog and borders
`applyDelta` does `gameState.visionGrid = delta.vision_grid_diff` (change mask) and
`gameState.borderGrid = delta.border_grid_diff` (sparse values), replacing the full grids with diffs.
After the first tick, unchanged vision cells become `false` (hidden) and unchanged borders become `0`
(erased).

### 3. MEDIUM — `vision_grid_diff` is semantically lossy
The server sends a boolean "changed" mask, not the new value. A client cannot reconstruct full vision
state from the mask alone. Needs a protocol-level decision (below).

### 4. MEDIUM — `renderFrame` swallows WebGPU validation errors
Silent blank frame during development.

### 5. MEDIUM — Replay path lacks parity with live path
No terrain conversion, no camera centering, no fog/border dirty marks, raw unit data instead of
`new Unit(...)`, `alert()` for GameOver.

### 6. LOW — `alert()` for server Error messages (`connection.ts:198`)
Blocking, renders user-controlled strings.

### 7. LOW — `controls.ts:49` hardcodes `32` instead of `CELL_SIZE`.

### 8. OPTIONAL — Generated protocol types missing `terrain` field.

## Fix 1: Enum-backed Terrain type, remove `height` (CRITICAL)

The frontend `Terrain` class (`frontend/src/game/terrain.ts`) carries an unused `height` field and wraps the
terrain type in an object (`{ type, height }`), which is what causes the crash: the server sends raw strings
("Plains"/"Water"/...), the client stores them in a `Terrain[][]`-typed field, and `marchingSquares`
reads `cell.type` from a string → `undefined` → white quads.

**Approach**: replace the `Terrain` class with an **enum-backed** string type (mirroring the backend
`enum Terrain`), removing `height` entirely. Because the server already sends the enum's serialized string
values, no conversion is needed at the wire boundary — a string cell IS a valid value.

**`frontend/src/game/terrain.ts`** becomes:

```typescript
export type TerrainType = 'Plains' | 'Hills' | 'Forest' | 'Water' | 'Mountain';
// enum-backed alias so existing `Terrain[][]` references keep type-checking
// (and can be tightened to TerrainType[][] during this refactor)
export type Terrain = TerrainType;

export function colorForType(type: TerrainType): string {
  switch (type) {
    case 'Plains':   return '#7eb547';
    case 'Hills':    return '#a0a04a';
    case 'Forest':   return '#2d7a2d';
    case 'Water':    return '#3878c9';
    case 'Mountain': return '#555';
    default:         return '#7eb547'; // safe fallback (never white/blank)
  }
}
```

`marchingSquares(grid: TerrainType[][], ...)` reads the cell directly: `colorForType(grid[y][x])`
(instead of `cell.type`). The `default` branch guarantees a colored fallback instead of the old white
blank screen even if the server ever sends an unexpected value.

**`frontend/src/game/game_state.ts`**: `terrain: TerrainType[][]` (grid of enum strings).

**`frontend/src/net/connection.ts`**: no parsing needed — `state.terrain` (already `string[][]`)
assigns directly into the enum grid. Just remove the object-wrap assumption.

**`frontend/src/main.ts`** / **`frontend/src/replay/replay_player.ts`** (legacy JSONL replay, lines ~84-87):
stop constructing `new Terrain(type, height)`; store `t.type` in the enum grid (drop height).

### Decision: `height` removed entirely
`height` is unused by the 2D renderer and backend game logic. Removing it (per review) also removes the
object-wrap that caused the `cell.type` crash.

## Delta calculation once-over (why the current grid diff isn't useful)

The current `build_delta_inner` treats vision/border grids like a real "delta": it compares every cell
(`prev[y][x] != curr[y][x]` → O(W×H) per player per tick), then allocates a **full-size** diff grid and
ships it every tick. The client then iterates the whole grid again to merge it. Net result: no meaningful
bandwidth or CPU savings over just sending the grid — the full map is tiny (default map is 20×20 = 400
cells ≈ ~1 KB), so the "diff" is the same size as the grid itself, while costing the same O(W×H) scan.

What IS genuinely worth delta-ing are **units and cities**: they can number in the hundreds/thousands and
only a handful change per tick, so sparse added/removed/updated lists save real bandwidth. Grids are small
and fully recomputed by the systems every tick; there is nothing to gain from diffing them per-cell.

**Recommended redesign:** keep the sparse unit/city delta, and for the grids simply **send the full grid
only when it changed** (skip entirely when unchanged). This is simpler, correct (naturally handles
un-reveal), and strictly reduces work vs. the current always-scan/full-size diff. A future scaling step
to sparse per-cell coordinates is noted as out of scope (needs incremental grid systems).

## Fix 2: Grid delta — send-on-change full grids (HIGH)

**Server (`src/server/delta.rs` + `src/server/game_server.rs`):**
- Drop the per-cell `prev != curr` diff loops for `vision_grid_diff` / `border_grid_diff`.
- Emit the field as the **full current grid** (`Some(current)`), present only when the grid changed
  since the last snapshot; emit `None` when unchanged. Detect change with a cheap equality/hash check of
  the stored `prev_*_grid` vs the current grid (O(W×H) but only as a gate, and trivial at 20×20; a
  per-player dirty flag set by the vision/border systems is the scalable alternative).
- Protocol type stays `Option<Vec<Vec<bool>>>` / `Option<Vec<Vec<u32>>>`; semantics change from
  "per-cell diff mask" to "full new grid when present". No `Option<bool>` or schema type change needed.
- Replay (`handle_replay_ws`) must pass the replay game's real `vision_grid_2d`/`border_grid_2d` as the
  `current_*_grid` (instead of `None`) so fog/borders update during replay just like live.

**Client (`frontend/src/net/connection.ts` `applyDelta`):**
- When `vision_grid_diff` is present, **replace** the grid with it and `markFogDirty()`:
```typescript
if (delta.vision_grid_diff) {
  this.gameState.visionGrid = delta.vision_grid_diff;
  this.renderer.markFogDirty();
}
```
- Same for `border_grid_diff` → replace + `markBorderDirty()`.
- This is exactly the existing replace-on-present behavior (already correct once the server sends full
  grids instead of diff masks) — the earlier "merge" idea and the `Option<bool>` encoding are
  superseded and **removed**. Replacing also correctly applies un-reveal, since a changed grid contains
  the updated `false` cells.

This change simultaneously fixes the lossy-diff bug (un-reveal now transmitted correctly) and the
delta-usefulness concern (no pointless per-cell diff; grids only sent when they change).

## Fix 3: `renderFrame` error surfacing — gated by the existing `debug-overlay` mechanism

**`frontend/src/game/renderer.ts`**: in the `renderFrame()` catch, store the last error on the instance
(e.g. `this.lastRenderError = err instanceof Error ? err.message : String(err)`) and keep
`console.error`. Do **not** rethrow by hostname.

Surface the error visibly via the **existing debug-overlay feature** (not a new ad-hoc gate): the
frontend already enables a debug overlay only when the backend reports `debug-overlay`/debug build is
active (`startDebugOverlay` in `main.ts` becomes active when `GET /debug/stats` succeeds, and hides
itself otherwise). Reuse that signal:
- When the debug overlay is **active**, append `lastRenderError` to the `#debug-overlay` (e.g. a
  `render-error` line) so WebGPU validation failures are visible during development.
- When it is **inactive** (production/release), keep logging to `console.error` and do not crash.

This reuses the project's existing `debug-overlay` feature to select render-error surfacing, instead
of introducing a separate hostname/`#render-error-overlay` mechanism.

## Fix 4: Replay uses the SAME path as live — differ only in that the client is a spectator

Replay should reuse the normal `Connection` + renderer + GameState flow, exactly like the live game,
with the only difference being that the connected player is a **spectator** (read-only: no lobby,
no controls, no outbound control messages). This eliminates the bespoke `connectReplayGame` duplicate
code (its own full-state handler, `applyDelta`, missing camera centering / dirty flags / `new Unit`,
and `alert()` GameOver).

**Frontend (`frontend/src/main.ts`, `frontend/src/net/connection.ts`):**
1. Add a spectator/replay mode to `Connection` (e.g. a `mode: 'game' | 'replay'` constructor option
   or a `connectTo(url, spectator: true)` entry):
   - connects to `/ws/replay?game_id=<id>` instead of `/ws`,
   - skips `LobbyUI`/`Controls`/advisor setup and never calls `send(...)` for control messages.
2. Route `/replay?game_id=...` through this same `Connection`, so it automatically gets Fix 1
   (enum terrain), Fix 2 (delta merge), camera centering (`centerCameraOnTerrain`), `new Unit(...)`,
   `markFogDirty`/`markBorderDirty`, and `spectator.gameOver()` — no duplication.
3. Delete the separate `connectReplayGame` function and its inner `applyDelta`.

**Backend (`src/server/game_server.rs` `handle_replay_ws`):** make the replay stream match live:
- The replay FullState already uses `replay_player.full_state()`; keep it.
- The replay delta loop currently passes `None, None` for `current_vision_grid`/`current_border_grid`
  (lines ~1126-1131), so fog/borders never update during replay. Pass the replay game's real
  `vision_grid_2d` / `border_grid_2d` into `build_delta_inner` so the spectator's fog and borders
  update with the new Option<bool>/value-carrying diffs (Fix 2), exactly like live.

## Risks & Open Questions

- **`vision_grid_diff`/`border_grid_diff` semantic change** (mask → full-grid-when-present) touches
  delta.rs, live client, and replay: coordinate as one change. Old clients reading a full grid as a mask
  would render wrong fog — land together with the frontend fix.
- **Change detection cost**: gating on a full-grid equality check is still O(W×H), but only as a gate and
  trivial at current map sizes; a per-player dirty flag set by the vision/border systems is the scalable
  alternative and is listed as the path to truly skip unchanged ticks without a scan.
- **Replay `full_state()` includes vision/border?** Verify `replay_player.full_state()` actually emits
  vision/border grids; if not, either compute them for the spectator or accept fog-less replay (document
  the choice).
- **Enum terrain removes the object wrapper** — any code still calling `cell.type`/`.height` on a grid
  cell must be updated (search `frontend/src` for `new Terrain` and `.height`); the plan lists
  `terrain.test.ts`, `game_state.test.ts`, `replay_player.ts`.
- **border `0` sentinel collision**: safe because player IDs ≥ 1.
- **`colorForType` default**: choose a stable fallback (Plains green) rather than white so a bad wire
  value never blanks the screen.
- **Open**: exact schema-regeneration command — verify from `Cargo.toml` (`generate_schema` bin) and
  `package.json` (`generate-types`) before running.
