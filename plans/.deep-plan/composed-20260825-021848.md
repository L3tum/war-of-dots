# Deep Plan: War of Dots — Benchmark Network Phase, Territory Borders, and Frontend Rendering/Controls Fixes

## Context & Goals

Repo: `war-of-dots` — Rust game server (hecs ECS, axum + WebSocket, CBOR protocol) + TypeScript/WebGPU frontend. Nine reported issues, grouped:

- **W0 (prerequisite, server):** shared-prev-state delta bug — one set of `prev_*` snapshots serves the whole per-player loop, so only the *first* player gets correct unit/city deltas; every other player's client freezes, and vision/border grids re-send ~200 KB to every player every tick. This is the root cause of part of W8 ("no units visible") and must land before W1 so the benchmark measures the *fixed* pipeline.
- **W1 (server/benchmark):** integrate the server's network phase (snapshot extraction + per-player delta build + CBOR encode) into `run_benchmark`, measured as its own phase.
- **W2 + W3 (frontend/terrain):** black spots at 4-way cell corners; flat, non-blending per-cell terrain colors. Both live in `marchingSquares` (`frontend/src/game/terrain.ts`) — do them in one change.
- **W4 + W6 (frontend/cities):** city dots too small (world-constant size); level labels lag (250 ms DOM gate, `left/top` writes); own cities not obvious (3-color palette, subtle halo).
- **W5 (frontend/territory):** "borders connect cities" because territory is only small influence disks; fix by filling territory client-side (server untouched — see rationale).
- **W7 (server/map):** default map has 5 cities (not 4) but the 5th is easy to miss; make it obvious; stabilize `/maps` ordering.
- **W8 (server):** no visible starting units — root cause W0 + silent recruit failure; add logging and a 3-unit starting force.
- **W9 (frontend/controls):** pan "slowness" is really the right-click capture dying on `pointercancel`; fix listeners, re-arm pan, add zoom-to-cursor.

**Sequencing:** `W0 → W1` (strict); `W0 → W8` (root fix first). `W2+W3` together; `W4+W6` together; `W5` standalone; `W7`, `W9` independent. No protocol changes anywhere (verified: `border_grid`/`vision_grid` shapes untouched; `build_delta_inner` is `pub(crate)`).

**Corrections to research line numbers (verified against source):**

## W0 — Prerequisite: fix shared-prev-state delta bug (server)

**Problem.** `game_server.rs:438-441` creates one `prev_units/prev_cities/prev_funds/prev_vision_grid/prev_border_grid`; the player loop at `:632-668` calls `build_delta_inner(&mut prev_units, ...)` per player, and `delta.rs:315-319` overwrites `prev` with the current snapshot inside the call. Consequences: (a) after player 1's non-idle delta, `prev_units == current_units`, so players 2..N get **empty unit/city updates forever** (frozen clients); (b) `prev_vision_grid` alternates between players' *different* grids → every player receives a full vision+border grid resend every tick, and the idle-skip (`delta.rs:290-305`) is dead.

**Approach.** Make the tick's end-state the shared *read-only* baseline; per-player prev only for vision. Commit after the player loop.

1. `src/server/delta.rs` — change `build_delta_inner` (`:85`) signature to read-only prevs:
   ```rust
   pub(crate) fn build_delta_inner(
       prev_units: &HashMap<String, UnitState>,
       prev_cities: &HashMap<String, CityState>,
       prev_funds: &HashMap<String, u32>,
       prev_vision_grid: &Option<Vec<Vec<bool>>>,   // this player's baseline
       prev_border_grid: &Option<Vec<Vec<u32>>>,    // global (grid is global; player_id is ignored, see game.rs:1550)
       current_units: &[UnitState],
       current_cities: &[CityState],
       current_unit_map: &HashMap<String, UnitState>,   // built ONCE per tick by caller
       current_city_map: &HashMap<String, CityState>,
       all_player_funds: &HashMap<String, u32>,
       current_vision_grid: Option<Vec<Vec<bool>>>,
       current_border_grid: Option<Vec<Vec<u32>>>,
       player_id: &str,
   ) -> Option<ServerMessage>
   ```
   - Delete the commit block `:315-319` (`*prev_units = ...; *prev_cities = ...; *prev_border_grid = ...`).
   - Delete the per-call `current_unit_map`/`current_city_map` construction at `:98-107` (now passed in); use `current_unit_map.contains_key` for the added-units check at `:128-141`.
   - Keep idle-skip semantics at `:290-305` (return `None` when nothing this player cares about changed).
2. `src/server/game_server.rs` tick loop (`:522-668`):
   - Init (`:213-232`): keep `prev_units`/`prev_cities` as `HashMap`s (drop `mut`), `prev_funds`, single global `prev_border_grid: Option<Vec<Vec<u32>>>`, and new `prev_vision: HashMap<String, Option<Vec<Vec<bool>>>>` (40 KB/player — negligible).
   - Per tick: build `current_unit_map` / `current_city_map` once (move the map-building logic that was inside `build_delta_inner`); compute `border_grid` **once** via `game.border_grid_2d(&any_pid)` (it is global — `game.rs:1550` ignores the player id) instead of per player at `:636`; per player: `let prev_vision = prev_vision.get(&pid).cloned().unwrap_or_default();` and pass `&prev_vision`, `&prev_border_grid`.
   - After the loop: commit `prev_units = current_unit_map; prev_cities = current_city_map; prev_funds = all_funds; prev_border_grid = border_grid_opt;` (all *moves*, zero extra clones) and `prev_vision.insert(pid, vision_grid)` for each player.
3. Replay path `game_server.rs:1244-1260` (single receiver): adapt to the new signature; commit the local prevs from the current snapshots **only when `build_delta_inner` returns `Some`** (preserving old "no prev mutation on idle" semantics).
4. Spectator paths (`:506-507`, `:624-626`, `:764-765`, `:814-817`) are unaffected (they build full state, not deltas).

**Acceptance criteria.** With 3+ players, after a unit move every player's client receives the update (manual check); idle ticks produce zero delta messages for all players (wire capture or log); `cargo test server::delta` green.

**Tests.** Update existing (signature change): `identical_snapshots_return_none_and_leave_prev_untouched` (rename to `identical_snapshots_return_none`; drop the prev-mutation assert), `single_unit_position_change_yields_one_update`, `funds_only_change_is_sent_to_changed_player_only`, `city_owner_change_yields_city_update`, `grid_change_includes_grid_diff`, `first_tick_from_empty_prev_sends_added_units`, `units_owned_change_is_detected` (all in `delta.rs` `mod tests`, `:397+`, adjust the `run()` helper at `:447`). **New:** `two_players_share_read_only_baseline` (same baseline + changed unit → both calls return the update), `per_player_vision_baseline_independent` (A's grid change must not suppress/alter B's grid diff).

**Risks.** Behavior change is the *point*; replay single-receiver path must keep semantics (mitigated by explicit conditional commit). Grid `prev == curr` equality compares still cost O(W·H) per player per tick — acceptable (200×200), note as follow-up if needed.

## W1 — Integrate the network phase into the benchmark

**Problem.** `run_benchmark` (`benchmark.rs:252`) times `sim.tick` + `game.tick_game()` + read-backs (`:567-578`) but never runs the server's per-tick network work: `unit_states()` (dominant alloc source — `game.rs:1777`), `query_cities`/`all_player_funds`, per-player `vision_grid_2d`/`border_grid_2d`, `build_delta_inner`, `encode_message`.

**Approach.** Replicate `game_server.rs:526-668` verbatim as a timed network phase per benchmark tick. (Depends on **W0** — measure the fixed, per-player-correct pipeline.)

1. `TickData` (`benchmark.rs:39-56`) — add: `net_ms: f64`, `net_allocs: u64`, `net_bytes: u64`, `net_max_alloc: u64` (bench-alloc gated, 0 when off), `net_wire_bytes: u64` (sum of encoded CBOR lengths), `net_deltas: u32` (players that got a non-None delta). Do **not** fold `net_ms` into `total_ms` — keep existing report series comparable.
2. In `run_benchmark` measured loop (after `game.tick_game()` and the read-backs at `:572-578`), add:
   ```rust
   let net_start = Instant::now();
   #[cfg(feature = "bench-alloc")] let net_base = crate::bench_alloc::snapshot();
   let current_units = game.unit_states();
   let current_unit_map: HashMap<String, _> = current_units.iter().cloned().map(|u| (u.id.clone(), u)).collect();
   let current_cities: Vec<CityState> = game.query_cities().iter().map(|c| c.into()).collect();
   let current_city_map: HashMap<String, _> = current_cities.iter().cloned().map(|c| (c.id.clone(), c)).collect();
   let all_funds = game.all_player_funds();
   let border_grid = game.players().keys().next().and_then(|pid| game.border_grid_2d(pid)); // global
   for pid in game.players().keys() {                       // "player_0".. (game.rs:576)
       let vision = game.vision_grid_2d(pid);
       if let Some(delta) = build_delta_inner(&mut net_prev /* baseline struct */, &pid) {
           net_wire_bytes += encode_message(&delta).len() as u64;
           net_deltas += 1;
       }
   }
   // commit baseline (move) — identical to the server tick loop after W0
   ```
   - Hold the baseline state across the whole run; **also run the network phase during the `BENCH_WARMUP_TICKS` loop** (`:549-552`) so first-tick spikes (grid `None → Some`, first vision runs — `INFLUENCE_TICK_INTERVAL=3`, `constants.rs:10`) are excluded from measured ticks, and reset it before each measured run alongside `reset_system_allocs` (`:556-562`).
   - Imports: `crate::server::delta::build_delta_inner`, `crate::server::protocol::{encode_message, CityState}` (both `pub(crate)`; benchmark is in the lib crate).
   - If W0's commit logic is extracted into a small `DeltaBaseline` helper struct (recommended in W0 for testability), the benchmark reuses it directly.
3. `avg_tick_data` (`:774-837`): average the new fields across `MEASURED_RUNS`.
4. JSON (`:1194-1209`): add `"net_ms_per_tick"`, `"net_wire_bytes_per_tick"`, `"net_deltas_per_tick"` series (same averaging shape as `allocs_per_tick_series`), plus a `"network": { "avg_ms": …, "p99_ms": …, "avg_wire_bytes_per_tick": … }` summary block.
5. HTML (`generate_html_report` `:1294`): add a "Network phase (snapshot + delta + CBOR)" summary panel and a per-tick wire-bytes/net-ms line chart next to "Per-Tick Timing" (`:2427`; series extraction helper `:2213-2225`).
6. CLI: wire the currently-dead `--bench-players` (`main.rs:48-50`) into a new `BenchmarkConfig.players: u32` (default `BENCH_PLAYERS`) and use it at `Game::new(map, settings, config.players as usize)` (`:425`) and in the network phase loop.

**Acceptance criteria.** `cargo run --profile release --features debug-overlay,microbenchmarks,bench-alloc -- --benchmark --bench-seed 42 --bench-ticks 300 --bench-html /tmp/net.html` produces a report with a populated network section: `net_ms > 0`, `net_wire_bytes > 0` from tick ~4 onward, `net_deltas ≤ players`; sim `total_ms` series unchanged vs. a pre-change run at the same seed (sanity: network measured separately).

**Tests.** New in `benchmark.rs`: `network_phase_reports_wire_bytes_and_deltas` — tiny game (2 players, few units), run 5 warmup + 5 ticks with the extracted network-phase function, assert `net_wire_bytes > 0` and at least one `net_deltas > 0` tick.

**Risks.** (a) `unit_states()` per tick is a large, real allocation — that's the point, but `total_ms` invariance must be asserted in review (kept out of `total_ms`). (b) `--bench-prev` comparison against old reports: new keys simply absent in the old report — guard the prev-diff code with `unwrap_or` (matches existing pattern at `:1194+`). (c) Representativeness nits (benchmark `funds_per_city: 20.0` vs config.toml `1.0`; `initial_manpower: 100_000` vs `2000`; `make_unit_types()` vs the 3 config.toml types) are pre-existing — **leave as-is**, note in report metadata only.

## W2 — Terrain black spots at 4-way cell corners

**Problem.** Rasterization coverage gaps at independently-rasterized flat quads' shared 4-way vertices expose the dark clear color (`renderer.ts:835`), clustering as corner-shaped 1–2 px dark spots (worse at large world coords where f32 ulp in the NDC transform grows).

**Approach — chosen: (a) half-pixel quad overlap in `marchingSquares`.** Rationale: smallest change that fully fixes the symptom; no shader, protocol, cache-design, or test-structure changes. Alternatives noted, not taken: (b) camera-relative vertex positions (also shrinks f32 magnitude but rewrites all position math and tests); (c) W×H terrain texture + stretch (also fixes W3, but deletes the mesh cache and breaks `terrain.test.ts` vertex assertions).

1. `frontend/src/game/terrain.ts`, `marchingSquares` (`:52`): compute overlap in world units — `const hpX = 0.5 / zoom; const hpY = 0.5 / zoom;` (derived: 1 physical px = `1/zoom` world; see correction note above).
2. Expand **both** quad emitters — mountain branch (`:118-123`) and flat branch (`:131-134`): push corners at `(wx - hpX, wy - hpY)`, `(wx + cellSize + hpX, wy - hpY)`, `(wx + cellSize + hpX, wy + cellSize + hpY)`, `(wx - hpX, wy + cellSize + hpY)`. Overlap of equal/different flat colors is invisible.
3. `frontend/src/game/renderer.ts:990` — include zoom in the mesh cache key: `` `${tStartCol},${tEndCol},${tStartRow},${tEndRow},${this.canvas.width}x${this.canvas.height}|${this.camera.zoom.toFixed(3)}` `` (overlap magnitude is zoom-dependent; without this a stale mesh survives zoom changes).

**Acceptance criteria.** Manual: pan across 4-way intersections at zoom 0.3, 1.0, 3.0 — no dark pixels. Programmatic: in a 2×2 uniform grid, adjacent quads' edges intersect by `2·(0.5/zoom)`.

**Tests.** `frontend/src/game/terrain.test.ts`: update `scales positions with cellSize` (`:66`) and `sends world-space positions (zoom applied by shader)` (`:73`) for the expanded corners; add `overlaps adjacent cells by half a pixel so 4-way corners are covered` (assert cell (0,0)'s right edge == cell (1,0)'s left edge).

**Risks.** At `ZOOM_MIN=0.3`, `hp = 1.67` world units ≈ 5% of a 32-unit cell — invisible; overlap only slightly inflates the triangle count's effective area (same vertex count). None material.

## W3 — Terrain colors: blend between cells and types

**Problem.** Every cell is flat-colored (`terrain.ts:94-99`, all 4 vertices identical at `:131-134`), so type boundaries are hard lines and per-cell `cellShade` confetti dominates; colors "don't blend".

**Approach — chosen: per-vertex corner-blend in `marchingSquares`** (single refactor alongside W2). Rationale: the pipeline already interpolates per-vertex colors (mountain top/bottom shading at `:113-124` is the in-pipe precedent), so no shader change; directly produces gradient blending. Alternative not taken: elevation-ramp shading requires a protocol change (client only receives `terrain: string[][]`) — out of scope.

1. `terrain.ts` `marchingSquares` — two-pass:
   - Pass 1: compute each visible cell's final RGB (existing `:94-109` logic: base palette × `cellShade` variance, coastal-water brightening `:104-109`, mountain base) into a `cellColor: [r,g,b][][]` over the visible range **expanded by one cell on each side** (for corner lookups; OOB → clamp/repeat edge cell).
   - Pass 2: build a `(cols+1)×(rows+1)` vertex-color lattice; each corner = average of the up-to-4 owning cells (2 at map edges, 1 at the corner). Emit each quad with its 4 corner colors (TL, TR, BR, BL) instead of 4 copies of one color.
   - Mountain shading: apply the existing top ×0.68 / bottom ×1.18 factors to the *corner* colors (top row of corners vs. bottom row) so shading and blending compose.
   - Optional, cheap: 2×2-average `cellShade` (`:38-42`) to calm confetti further.
2. Keep the function signature and return shape (`{positions, colors}`) unchanged.

**Acceptance criteria.** Manual: no hard color line between Plains/Hills/Forest/Water; visible smooth gradient at type boundaries and coastline; variance speckle reduced.

**Tests.** `terrain.test.ts`: rewrite `uses correct base color for terrain type` (`:139`) to recompute the corner-average expectation; `keeps colors within the palette variance range` (`:87`) still holds (averages stay in-range — keep); add `blends colors where two terrain types meet` (2×2 Plains/Hills grid → shared corner color strictly between the two base colors, per channel) and `coastal water still brightened at blended corners`.

**Risks.** Slightly more CPU per terrain rebuild (one extra grid of the same size); rebuild is already cached on camera/terrain state (`renderer.ts:990-1011`), so steady-state cost is zero. Corner-averaging a brightened coastal-water cell into a land corner shifts the coastline tint ~1 cell — acceptable/organic; adjust test thresholds accordingly.

## W4 — City dots too small + level labels lag

**Problem.** (1) `CITY_DOT_SIZE=6` (`config.ts:33`) with `halfSize = 6*zoom; halfSizeWorld = halfSize/zoom` (`renderer.ts:1396-1397`) — the zoom cancels: cities are 6 *world* units ≈ 2–3 screen px at fit-zoom. (2) `updateCityLabels` (`frontend/src/main.ts:206-262`) runs only every 250 ms (`CITY_LABEL_UPDATE_INTERVAL`, `config.ts:63`; gate at `main.ts:167-169`), uses per-city `document.getElementById` (O(n²)), and writes layout-triggering `style.left/top` → labels visibly trail the camera.

**Approach.**
1. **Dots → screen-space constant.** `renderer.ts:1396-1397`: `const halfSizeWorld = (CITY_DOT_SIZE / 2) / this.camera.zoom;` and `config.ts:33`: `CITY_DOT_SIZE = 12` (screen-px diameter — matches the existing own-halo pattern `pushOutline` `(dotSize + OUTLINE_EXPAND)/zoom`, `renderer.ts:1434-1435`). Do the same for unit dots at `renderer.ts:1064-1065` (`UNIT_DOT_SIZE = 8` → screen-px, `halfSizeWorld = (UNIT_DOT_SIZE/2)/zoom`) so dots don't shrink to nothing at fit-zoom.
2. **Labels: per-frame, cached, compositor-only.** `main.ts`:
   - Keep a module-level `Map<string, HTMLDivElement>` (and last `(x, y)` per city); replace `document.getElementById('city-label-'+id)` (`:224`) with the cache.
   - Remove the 250 ms gate (`:167-169`) — call `updateCityLabels` every rendered frame.
   - Position via `el.style.transform = translate3d(x, y, 0)` (drop `left/top`; keep the existing `translate(-50%,-50%)` by folding it into the same transform or a CSS class), and **skip the write when the delta is < 0.5 px** — makes stationary-camera cost ~zero and panning cost one compositor-style write per city.
   - Keep the on-screen cull (`:247-251`) and the stale-label removal loop (`:265-271`, also switch it to iterate the Map).
   - Container stays `pointer-events: none`.

**Acceptance criteria.** City dot ≈ 12 screen px at every zoom (incl. fit-zoom); during a fast pan, level numbers track dots with no visible lag; DevTools Performance shows no layout (not just paint) events per frame from label updates.

**Tests.** `frontend/src/game/renderer.test.ts`: update `scales city dot size with zoom` (`:529`) — new expectation: world size = `(CITY_DOT_SIZE/2)/zoom`, i.e. *inverse* scaling (constant screen size); adjust `generates correct quad at world position for city at (5,5)` (`:515`) and the unit-dot tests (`:179-226`) for the new formula. Extract the label screen-position math into a pure helper (e.g. `cityLabelScreenPos(camera, canvasW, canvasH, city)`) and add unit tests: `label position tracks camera/zoom`, `sub-pixel movement is skipped`, `off-screen city is culled`.

**Risks.** Screen-constant dots change `CITY_HIT_RADIUS` interaction minimally (hit test is already screen-space, `controls.ts:88-93`); per-frame label loop with skip-write is O(cities) and trivial at ≤12 cities. If the reviewer prefers a 50 ms throttle instead of per-frame, the gate constant can be restored — but per-frame + skip-write is the fix.

## W5 — Borders form real territories, not city-connecting chains

**Problem.** Server territory is only the influence disks (`influence.rs:228,251` — `stamp_circle` radius 5.0 unit / 7 city, strict running-max fold `:283-300`), so the border grid is mostly `255` with small blobs; borders render only where blobs touch → visually "borders connect cities". Frontend defects on top: edge scan at `renderer.ts:1249-1250` uses `y < length-1 / x < row.length-1` (outermost row/col borders never render), and `BORDER_LINE_WIDTH = 3` *world* units (`config.ts:16`) is sub-pixel at overview zoom.

**Approach — chosen: client-side territory fill for display.** Rationale: the client already receives `borderGrid` + cities; a cached multi-source BFS fills the gaps with "nearest city/cluster" territory, producing real region borders, while leaving protocol, delta, replay, LLM state, and — critically — **encirclement** untouched. Verified why not to fill server-side: `encirclement.rs` flood fills *through* `dominant == pidx` cells (`:436-458`) seeded from map edges + city anchors (`:195-216`); if the server grid were fully filled, every region would connect to edges/cities → everything "safe" → **encirclement never triggers**. Alternative noted, not taken: server-side Voronoi fill with a *separate* influence-only grid for encirclement (new `WorldData` grid + `replay.rs:178` + `llm/agent.rs:133` surface).

1. New module `frontend/src/game/territory.ts`: pure `fillTerritory(borderGrid: number[][], terrain: TerrainType[][], cities: {x,y,ownerIdx}[]): number[][]` — copy `borderGrid` (values are player indices or `255`), seed a multi-source BFS with all non-255 cells **and** each city's cell (value = its owner index), expand 4-neighbor into `255` cells that are not `'Water'`; return the filled grid. O(W·H).
2. `renderer.ts` border section (`:1243-1330`): on `borderDirty` (`:1245`) compute `displayGrid = fillTerritory(borderGrid, gameState.terrain, cities-with-owner-indices via gameState.colorIndexForOwner)`; cache it (rebuild only on `borderDirty`); scan edges **on `displayGrid`** with corrected bounds: `for y < displayGrid.length` / `for x < row.length`, guarding `x+1 < row.length` and `y+1 < displayGrid.length` so outermost edges render.
3. Zoom-aware width: in the per-frame position rebuild (`:1280+`), `const lw = BORDER_LINE_WIDTH / this.camera.zoom;` and use `lw` in both quad emitters (screen-constant line). Edge *cache* stays camera-independent (logical only) — no change there.
4. (Optional, skip if out of budget: low-alpha territory tint from `displayGrid`, reusing the fog-texture pattern at `renderer.ts:1469+`.)

**Acceptance criteria.** At fit-zoom, borders appear as long straight/diagonal region boundaries enclosing city regions, not dotted chains; the line has ~constant 3 px on-screen width from zoom 0.3 to 3.0; a border touching the map's last row/column renders.

**Tests.** New `frontend/src/game/territory.test.ts`: `fills unclaimed land by nearest city` (2 cities, gap → gap cells get nearest owner), `water cells stay unclaimed (255)`, `existing influence cells win over fill`, `city anchor claims its own cell`. Update `frontend/src/game/renderer.test.ts` "Border edge detection" (`:6-99`) — it contains a **drifted reimplementation** of the scan: fix it to the new bounds/guarded-neighbor logic (and it should ideally import from `territory.ts` rather than re-deriving); add `border at map edge renders` and `border line width is screen-constant across zoom` (`:159`'s `scales border positions with zoom` inverted expectation).

**Risks.** Fill recomputation is O(40k cells) in JS but only on `borderDirty` (grid changes are gated server-side by `INFLUENCE_TICK_INTERVAL=3` + dirty checks — `game.rs:932-935`), so worst-case a few Hz. Player-index space: `borderGrid` uses sorted-enumeration indices and `colorIndexForOwner` uses the same lobby-slot index — verify they match for >1 player; if they diverge, map through `colorIndexForOwner` as the single source. Gameplay unchanged (server untouched) — the only semantic shift is visual.

## W6 — Make it obvious which cities are yours

**Problem.** 3-color palette (`config.ts:38-49`) → the 4th player recycles player 1's red (`renderer.ts:1410` `CITY_COLORS[colorIdx % 3]`); the only own-highlight is a 0.35-alpha white halo behind the dot (`OUTLINE_ALPHA`, `config.ts:107`; pass at `renderer.ts:1429-1468`) — nearly invisible, especially with the tiny W4 dot.

## W9 — Pan "slowness", zoom scaling, right-click capture

**Problem.** The pan math is already 1:1 and zoom-scaled (`controls.ts:108-109`: `camera.x -= (dx * scaleX) / this.camera.zoom`) — so "slow" is the *capture-loss symptom*: `pointercancel` (`:217-222`) calls `endPan()` + release unconditionally, and browsers/trackpads emit `pointercancel` during right-button drags → pan halts until the next `pointerdown` (exactly "right clicking/holding right click doesn't capture the mouse anymore"). Secondary: wheel zoom is applied about the camera center, so the point under the cursor drifts.

**Approach.**
1. `frontend/src/ui/controls.ts`, `setupEventListeners` (`:147+`): move the **button-2 pan tracking** — `pointermove` and `pointerup` — from `canvas` to `window` (still gated by `isDragging`), so tracking survives pointer leaving the canvas and is independent of capture state. Keep the button-0 selection/path logic on `canvas` (unchanged).
2. `pointercancel` (`:217-222`): release capture but do **not** `endPan()`. Re-arm on `window` `pointermove`: `if (!this.isDragging && (e.buttons & 2)) { this.isDragging = true; this.rightDragStart = this.lastPointer = { x: e.clientX, y: e.clientY }; this.startPanLoop(); }`.
3. Keep `setPointerCapture` in `pointerdown` (`:165-171`) as a gesture suppressor (back/forward nav), keep `contextmenu` preventDefault (`:224`), keep the re-capture attempt in `pointermove` (`:186-191`).
4. **Zoom-to-cursor** (wheel handler `:225-230`): add helper `screenToWorld(clientX, clientY)` (inverse of `mouseToGameCoords` without the floor, reusing its ndc math `:44-51`); on wheel: capture `world = screenToWorld(...)`, apply existing `×0.9/×1.1` + `[ZOOM_MIN, ZOOM_MAX]` clamp, then re-aim: `camera.x = world.x - ndcX * canvas.width / (2 * zoom)` and same for y (mirror of `:48`).
5. `config.ts`: add `PAN_SPEED_MULTIPLIER = 1.0` and apply it at `controls.ts:108-109` — a user-facing knob in case pan still feels slow after the capture fix (research found no regression diff possible: single amended commit).

**Acceptance criteria.** Right-drag pan continues through `pointercancel` (mouse + trackpad); panning with the pointer outside the canvas keeps working; releasing the button (or a true cancel with `buttons === 0`) stops pan; zooming keeps the cursor's world point stationary; at zoom 3.0 a 100 px drag moves the camera 3× further than at zoom 1.0.

**Tests.** New `frontend/src/ui/controls.test.ts` (vitest + happy-dom; construct `Controls` with stub `renderer` (`{camera:{x,y,zoom}, currentPath:[]}`), `gameState` (`{units:new Map(), cities:new Map()}`), `connection`/`unitInfo` stubs, and a real `<canvas>` from `document.createElement`): `pan delta scales inversely with zoom (1:1 at zoom 1)`, `zoom clamps to [0.3, 3.0]`, `zoom keeps the point under the cursor fixed`, `pan survives pointercancel while button held (re-arm on pointermove with buttons=2)`, `pointerup with buttons=0 ends pan`. Note: synthetic events need `Object.assign(new Event('pointerdown'), { button: 2, buttons: 2, pointerId: 1, clientX, clientY, preventDefault() {} })`.

**Risks.** Window-level listeners can double-fire with canvas listeners for button 0 — avoided by scope (only button-2 logic on window) and `isDragging` gating; `setPointerCapture` on `window`-received events is not needed. Trackpad "right click" (two-finger) emits different `pointerType`s — the `e.buttons & 2` re-arm covers any active right-button drag regardless of pointer type.
