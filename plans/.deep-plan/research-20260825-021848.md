## Issue 2 — Corner-shaped black spots in terrain

**No compute shader**: frontend is CPU-built triangle-strip quads uploaded to WebGPU buffers; WGSL inline in `renderer.ts` (`createMainPipeline`, `createLinePipeline`, `createOutlinePipeline`, `createFogPipeline`); vert does `screenX = (pos.x - cameraX) * zoom / canvasWidth * 2.0`.
Terrain = `marchingSquares()` in `frontend/src/game/terrain.ts` — despite name, per-cell opaque quad loop (4 verts, per-vertex color), viewport-culled with 1-cell margin; `renderer.render()` caches mesh keyed on visible cell range (~:970), uploads via writeBuffer.
Root cause: rasterization coverage gaps at 4-way shared corners of independently rasterized flat quads, exposed by dark clear color `renderer.ts:835` `clearValue {0.05,0.05,0.1,1}`. Each cell's quad pushed at `terrain.ts:131-134`; at 4-way vertices f32 edge-function sign can round a pixel outside for all four triangles → 1–2 px dark spots clustering at 4-way vertices (corner-shaped). Absolute world positions (up to ~6400 units) grow f32 ulp in the NDC transform. `terrain.test.ts` has no coverage/adjacency test.
Options: (a) overlap quads by half a pixel `hp = canvasWidth / (2*zoom)` world units in `marchingSquares` (zoom + canvasWidth already params; ensure `terrainKey` includes zoom) — minimal; (b) camera-relative vertex positions to shrink magnitude; (c) render terrain as W×H RGBA8 texture + stretched quad (magFilter nearest or linear — linear also fixes Issue 3); deletes mesh cache; breaks terrain.test.ts vertex-count assertions.

## Issue 3 — Terrain colours flat / don't blend

Color per-tile flat: `terrain.ts:94-99` `factor = 1 + (shade-0.5)*2*palette.variance` (hash `cellShade` `:38-42`), same color on all 4 vertices (`:131-134`). Palettes `terrain.ts:18-24` (e.g. Plains 7e/b5/47, variance 0.07). Mountain cells: 2 flat shades (top ×0.68, bottom ×1.18, `:113-124`) — precedent that pipeline interpolates per-vertex color. Coastal water brightening `:104-109`. No elevation on client (enum-string grid `Plains|Hills|Forest|Water|Mountain`; live protocol `terrain: string[][]`), so no height ramp without protocol change.
Fix: per-vertex **corner-blend** in `marchingSquares`: build (W+1)×(H+1) vertex-color lattice where each corner color = average (or type-weighted mix) of up to 4 owning cells (OOB → repeat edge), push quad with 4 corner colors. No shader change. Optionally 2×2-average the hash shade to reduce confetti. Breaks exact-color tests in terrain.test.ts (`'uses correct base color for terrain type'` recomputes hash) — rewrite for corner formula.

## Issue 5 — Borders "just connect cities"

Server DOES produce a real per-tile territory grid: `game.rs:1544-1568` `border_grid_2d` → dominant player per cell (0..N or 255 unclaimed), global. Frontend DOES draw grid-based segments (`renderer.ts:1243-1330`): adjacent cell pairs with different non-255 owners → two thin quads (3 world units, `BORDER_LINE_WIDTH=3` `config.ts:16`) along shared edge, colored per owner.
Root cause: **territory model** — territory only claimed inside small influence disks (`influence.rs:210-258` `stamp_circle`: unit radius 5.0, ×2 on hills, clamp 10; city radius 7 = 5×1.5), strict running max. Player territory = blobs around units/cities; blobs touch only between neighboring clusters → borders visually "connect cities". Rest is 255, undrawn.
Frontend defects on top: (1) loop bounds `for y < borderGrid.length - 1 / x < row.length - 1` skip outermost row/col edges (`renderer.ts` ~1243-1330; renderer.test.ts has a second drifted copy of edge detection); (2) 3 world-unit border lines are sub-pixel at overview zoom.
Fixes: Server (root, pick one): (i) Voronoi/flood-fill territory pass assigning land cells to nearest city (weight by level/manpower), keep influence for defense/encirclement; or (ii) raise radius defaults so blobs merge. Grid/protocol/delta/frontend rendering unchanged. Frontend: fix loop bounds with neighbor guards; zoom-aware border width (`BORDER_LINE_WIDTH / camera.zoom`); optional low-alpha territory tint texture from borderGrid (fog-texture pattern).
Risks: territory model change affects `encirclement.rs`, LLM agent state description (`llm/agent.rs:133`), replay consistency (`replay.rs:178` stores `supervisor_border_grid()`); O(W·H) per-tick pass comparable to existing influence/vision passes — must be incremental/dirty-gated.

## Issue 9 — Camera pan/zoom/capture

(a) Pan math is **already zoom-scaled and correct 1:1**: `controls.ts:108-109` `camera.x -= (dx * scaleX) / this.camera.zoom`, `scaleX = canvas.width/rect.width` (DPR). Keyboard pan likewise. So "slow, should scale with zoom" not reproducible from math — most likely the capture failure makes pan halt mid-drag (reads as slow).
(b) Capture: `pointerdown` button 2 → `preventDefault`, `isDragging=true`, `setPointerCapture` in try/catch, `startPanLoop()` (`controls.ts:162-177`); `pointercancel` → **unconditional `endPan()` + release** (`:217-222`) — browsers/trackpads emit pointercancel during right-button drags → held button no longer pans until next pointerdown (exactly the reported symptom); `pointermove` re-captures if `!hasPointerCapture` (`:181-196`); `pointerup` button 2 → endPan + release (`:198-234`); `contextmenu` → preventDefault. If setPointerCapture throws, fallback is canvas-only tracking (no capture). No git history (single amended commit) — can't diff the regression.
(c) Wheel zoom `e.deltaY>0 ? 0.9 : 1.1`, clamp 0.3-3.0, applied at camera center (point under cursor drifts — comfort issue).
Fixes: bind `pointermove`/`pointerup` on **window** (already gated by `isDragging`) → capture-independent; don't end pan on `pointercancel` if button still held (track `buttons & 2` in pointermove, re-arm `isDragging`); keep setPointerCapture as gesture suppressor; optional `PAN_SPEED_MULTIPLIER`; optional zoom-to-cursor using inverse transform already in `mouseToGameCoords`. No `ui/controls.test.ts` exists — add one (happy-dom): pan math vs zoom, clamps, drag state transitions incl. pointercancel.
