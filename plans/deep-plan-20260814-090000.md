# Deep Plan: Optimize `supply.rs` (attrition + supply system)

> Pipeline: **RESEARCH → COMPOSE → REVIEW-PLAN** (sequential, output threaded forward).
> All claims below verified against the working tree with file:line evidence.

## Context
`src/game/systems/supply.rs::run` (hecs **0.11**) is a per-tick system fusing **attrition**
(equipment wear 1 item/tick, water/boat/org drain, base manpower drain scaled when
under-supplied) and **supply** (refill men from the player manpower pool at
`recruitment_rate`; refill equipment toward the supply buffer from funds, FCFS-gated,
encircled units excluded), plus organisation recovery. It runs every tick after combat
(`src/game/game.rs:586`).

The current design is **two-phase read-then-write**:
1. An **immutable** `world.query::<(...)>` computes each unit's net change into a
   `Vec<Change>` (cloning every unit's equipment), accumulating per-player costs in two
   `HashMap<String, u32>`.
2. **Phase 3** writes each change back via **up to 3 separate `world.query_one_mut` calls
   per changed unit** (`UnitStats`, `UnitEquipment`, `UnitWaterTransition`).

Goal: cut the per-tick allocation + write-back overhead while keeping behaviour bit-for-bit.

## Evidence (hot spots, verified)
- **H1 — per-tick table rebuild.** `unit_types_by_name: HashMap<&str, &UnitType>` is
  rebuilt from static `settings.unit_types` **every tick** (supply.rs:80–84), even though
  the settings never change mid-game.
- **H2 — two-phase + `Vec<Change>` + per-entity `query_one_mut`.** Net changes are staged in
  `Vec<Change>` (supply.rs:~100) and applied in Phase 3 via up to 3 `query_one_mut`
  calls per changed unit (supply.rs:286–303). hecs `query_one_mut` is O(1) archetype
  resolution (not O(n)), but the per-call overhead × up to 3 × N units, plus the staging
  `Vec`, is pure overhead.
- **H3 — full equipment clone per unit, per tick.**
  `let mut eq_copy = (*equipment).clone();` (supply.rs:173) clones both `Vec<Equipment>`
  including every `Equipment.name: String`, for **every unit every tick**, even when the
  net result could be applied in place.
- **H4 — `(*wt).clone()`** for on-water units (supply.rs:~150) — same pattern.
- **H5 — `String`-keyed player pools + per-unit hashing/cloning.** `remaining_mp` /
  `remaining_funds` are `HashMap<String, u32>` snapshots; `mp_cost` / `fund_cost` are built
  fresh each tick with `remaining_funds.get(pid)` and `mp_cost.entry(pid.clone())` where
  `pid: &String` (supply.rs:89–93, 174, 188, 205–229). The codebase already maintains a
  `TickContext` with dense `u8` owner indices (`game.rs:181`
  `owner_id_by_entity: HashMap<Entity, u8>`, `game.rs:183` `player_id_to_index`) used by
  combat / encirclement / influence / nearby_enemies — **supply uses none of it**.
- **H6 — `plan_delivery` allocates `Vec<(usize,u32)>` per unit** (supply.rs:24, called at 174).
- **H7 — `equipment_ratio` walks the equipment vec twice** per unit (needs + carried) each tick (supply.rs:~50–60).
- **H8 — two `world_data` / `world_data_mut` lookups** by `world_entity` (supply.rs:89, ~265).

**hecs 0.11 facts (verified in-repo):** hecs permits multiple `&mut` references of *different*
component types in a single query (one per type). Proven in the repo at `combat.rs:409` /
`combat.rs:425`: `query_one_mut::<(&mut UnitStats, &mut UnitEquipment, &mut UnitFlags)>`.
⇒ the entire two-phase design can **collapse into one mutable query that mutates in place**;
the local pool snapshots (`&mut World` locals) do not conflict with the query borrow.

**Reuse existing patterns (verified):**
- `CombatScratch` — `combat.rs:25` (`.new()` :39, `Default` :77), owned on `Game` at
  `game.rs:102` / initialised `game.rs:399`. Model `SupplyScratch` on it.
- `TickContext` — `game.rs:166`, built `game.rs:385`; `owner_id_by_entity` (u8) and
  `player_id_to_index` (u8) available for zero-string owner lookups.
- `microbenchmarks.rs:998` / `:1013` call `supply::run` via `SupplyFixture` — a signature
  change ripples there (ids `systems/supply_200`, `systems/supply_500`).
- 12 unit tests in `supply.rs` exercise `run` directly.
- `plans/PERF_ANAL.md`: **Rayon was already tested and rejected (+175%)** — do not
  parallelize.

## Approach (phased; Phase 1 is self-contained, highest-impact / lowest-risk, no new required dep)

### Phase 1 — collapse to ONE mutable query + `SupplyScratch` (MUST)
- Add `SupplyScratch { mp_cost, fund_cost, dead, delivery }` with `Default`/`.clear()`,
  mirroring `CombatScratch`. Own it on `Game` (field near `game.rs:102`, init near
  `game.rs:399`), pass `&mut self.supply_scratch` at the call site `game.rs:586`.
- New signature:
  `run(world, world_entity, settings, scratch: &mut SupplyScratch) -> Vec<Entity>`.
- Snapshot the pools (immutable `world.world_data`) into locals **before** the query, then run a
  single
  `world.query::<(Entity, &UnitTypeId, &UnitOwner, &UnitFlags, &mut UnitStats,
  &mut UnitEquipment, &mut UnitWaterTransition)>()` and **mutate in place** — no `eq_copy`,
  no `wt` clone, no `Vec<Change>`.
- `plan_delivery` → `plan_delivery_into(&mut equipment, out: &mut smallvec-or-Vec) -> u32`
  reusing `scratch.delivery` (fixes H6).
- **Drop** `type Change`, the `Vec<Change>` staging, both clones (H3/H4), and the Phase-3
  `query_one_mut` loop (H2). Return `std::mem::take(&mut scratch.dead)`.

- ⚠ **Behavior-preservation trap (the subtle one):** the original computes
  `let ratio = equipment_ratio(equipment);` at **supply.rs:198 using the pre-wear, untouched
  `equipment`** (not the worn/delivered clone). `ratio` drives both the men-drain multiplier
  (`mult = 10.0 - 8.0*ratio`) and the org malus. In the single-mutable-query rewrite the only
  `UnitEquipment` binding is `&mut`, so **compute `ratio` *before* applying wear
  (`saturating_sub(1)`, supply.rs:170) and delivery**, or the drain/malus silently drift and
  the org + funds tests break.
- FCFS ordering is preserved (identical query visitation order; deduct local pools as we go).

### Phase 2 — dense `u8` player indexing via `TickContext` (RECOMMENDED)
- Add `ctx: &TickContext` param; re-key the pool snapshot + cost accumulators to
  `Vec<u32>` indexed by `ctx.owner_id_by_entity[entity]` (u8). This eliminates per-unit
  `String` hashing and `pid.clone()` (H5) — matching how combat/influence/nearby_enemies
  already avoid it.
- Keep the `funds.manpower`/`funds.funds` *deduction* step keyed by String (or map index→id
  via `player_id_to_index`) so the world bundle is still written correctly.
- Safe to skip: Phase 1 alone stays correct with String keys.

### Phase 3 — alloc micro-tweaks (OPTIONAL)
- `smallvec` (or a fixed `[..; N]`) for `scratch.delivery` / `scratch.dead`.
- Cache `unit_types_by_name` once per `Game` (built at `Game::new`, not per tick) — H1.

## Risks
- **Borrow friction** mixing `&`/`&mut` in one query — Medium. Types are distinct, and
  `combat.rs:409` proves the multi-`&mut` pattern compiles in this hecs version; if the
  compiler balks at the pool-snapshot borrow, narrow the mutation scope (compute all reads
  first per entity, then mutate).
- **Behavior drift** — Medium. Compute `ratio` from pre-wear equipment; keep `.ceil()` +
  clamps verbatim; the 12 tests are the safety net.
- **Signature ripple** — Low. Isolated to S3, gated by `cargo check` before touching the body.

## Out of scope
- ECS engine swap; parallelism (Rayon already rejected); changing supply/attrition math or
  FCFS semantics; fixing the analogous per-tick table rebuild in `combat.rs` (separate plan).
