## Context

The project (`war-of-dots`, a Rust LAN multiplayer RTS game with ECS over `hecs`, Axum HTTP/WebSocket server, SQLite storage, and a TypeScript/WebGPU frontend) underwent a project-wide review pipeline of 7 themed subagents (security, architecture, tests, bugs, performance, linting, ponytail). That review surfaced ~40 findings.

This pass **verifies** those findings against the actual source and **fixes** the confirmed issues in a single, sequenced pass. The REFINE phase restated requirements and grouped findings into work packages; the RESEARCH phase verified each finding against real code (file paths, line numbers, symbols) and confirmed every finding referenced in this plan is real and actionable.

## Work Packages (execution priority order)

### WP-2 — Game Logic Bugs

#### 2.1 TCP deserialization partial-data loss
- **File:** `src/server/game_server.rs`, `handle_tcp_client` (~lines 1240-1268)
- **Problem:** Loop does `reader.read(&mut buf)`, then `decode_client_message(&buf)`, then **unconditional `buf.clear()`**. A CBOR message spanning multiple TCP segments loses its partial bytes on the first incomplete read, permanently corrupting the stream.
- **Fix:** Only advance/clear the buffer by the number of bytes actually consumed on a successful decode. On decode failure, **accumulate** (preserve undecoded bytes) rather than clearing. Bound buffer growth with a cap (e.g. reject/drop the connection if the buffered size exceeds a max, mirroring the existing 1MB message cap) to avoid unbounded memory from a malicious client.
- **Reuse:** existing `decode_client_message` (`src/server/protocol.rs:230`). No framing layer exists; keep the change minimal (do not add length-prefixing, which would change the wire protocol — see Gotchas).
- **Gotchas:** WebSocket path (`handle_ws_game`) uses atomic WS frames and is unaffected. Adding a length prefix changes the wire protocol and would break the console client — avoid in this pass.
- **Done when:** A partial CBOR message split across two reads decodes correctly; no data is lost on decode failure; buffer growth is bounded.

#### 2.2 Dead units (0 men) continue fighting
- **File:** `src/game/systems/combat.rs` (~lines 30-36)
- **Verified behavior:** Combat candidates are filtered by `flags.moved || flags.fighting` with no `men > 0` guard. Attrition drains men toward 0 but does **not** despawn; units are only despawned by the surrender check (every 30 ticks, `game.rs:338`) or when combat pushes them to `dead` and despawns them that same tick. A unit can also reach 0 men **outside combat entirely**: when it has no supply, the manpower drain in `attrition::compute_attrition` (`game/systems/attrition.rs`) keeps subtracting until `men` clamps to 0, so a supplied-out unit that never engages an enemy can still starve to 0 men and persist until the next surrender sweep. So a 0-men unit whose `fighting` flag is set remains a valid candidate and can be engaged (dealing negligible men-scaled damage and consuming an enemy's supply) for at most one tick before combat despawns it.
- **Resolved:** Keep the guard as a cheap correctness safety net. (a) In `combat.rs`, change the candidate filter to also require `stats.men > 0.0` (component `UnitStats().men` is already in the query), so a starved 0-men unit is skipped entirely rather than transiently engaged. (b) In `attrition.rs`, add an early `men <= 0` skip (or clamp at the point where it would drop to 0 and flag the unit for removal) so attrition stops mutating dead units and such units are picked up cleanly by the surrender sweep instead of lingering.
- **Reuse:** Existing `UnitStats` component in the combat query; existing attrition filter mapping; existing surrender sweep (`game.rs:338`) as the despawn path for 0-men non-combat units.
- **Done when:** Units with `men <= 0` are excluded from the combat candidate list and from further attrition mutation; a supply-starved unit outside combat that reaches 0 men is removed via the surrender sweep without being treated as a live fighter.

#### 2.3 Combat resolves entity1 vs only one enemy per tick
- **File:** `src/game/systems/combat.rs` (~lines 40-46, 96-98)
- **Problem:** A single flat `resolved: HashSet<Entity>` is used to mean both "this attacker is done" and "this defender is done". The first enemy match does `resolved.insert(*entity1)` + `resolved.insert(entity2)`, so entity1 is barred from engaging any *other* adjacent enemy for the rest of the tick.
- **Fix (per D-2):** Make `resolved` a set of **pairs** — `HashSet<(Entity, Entity)>` — recorded in a normalized (ordered) form, so each (entity1, entity2) pairing is resolved exactly once while entity1 remains free to engage additional distinct enemies. Replace the `resolved.contains(entity1)` / `resolved.contains(&entity2)` membership tests with pair-membership checks; the retreat pass should treat an entity as engaged if it appears in any resolved pair.
- **Balance note:** Entity1 now receives damage from multiple enemies in one tick. This is the intended bug-fix behavior; flag for a quick playtest/balance check in verification.
- **Done when:** A unit adjacent to multiple enemies engages each distinct enemy once per tick; no single pairing is resolved twice; retreat logic still clears `fighting` correctly.

#### 2.4 Supply grants free manpower when pool is empty
- **File:** `src/game/systems/supply.rs` (~lines 112-125)
- **Problem:** Phase 2 deducts with `saturating_sub` (caps at 0, never negative); Phase 3 always applies full gain (`stats.men = (men+gain).min(max_men)`). With an empty pool a unit still receives full resupply for free.
- **Fix:** Gate resupply on available manpower. In the planning phase, only include a unit in `resupply_needed` if the player's remaining pool can cover its gain; track remaining pool across units (first-come-first-served), or scale gains proportionally when the pool is exhausted. Keep the existing two-phase query-then-apply pattern.
- **Reuse:** `wb.funds.manpower` HashMap already accessed in this system.
- **Done when:** No unit receives free manpower from an empty pool; pool cannot go negative.

#### 2.5 `build_full_state` sums all players' funds
- **File:** `src/server/game_server.rs`, `build_full_state` (~line 679, initially ~863)
- **Problem:** `let player_funds: u32 = self.all_player_funds().values().sum();` sums ALL players' funds (and `units_owned` = all units) instead of the viewing player's.
- **Fix:** Use per-player values: `player_id.map(|pid| self.player_funds(pid))` with a supervisor fallback to the aggregate sum when `player_id` is `None`. Match the delta system's per-player behavior.
- **Reuse:** `Game::player_funds(&str) -> u32` (`src/game/game.rs` ~710) and `all_player_funds()` already exist.
- **Done when:** Full state reports the viewing player's own funds/units; supervisor view still shows aggregate.

### WP-3 — Authorization

#### 3.1 Ownership validation consolidated into game-layer methods
- **File:** `src/server/game_server.rs` command dispatch (~lines 406-430); `src/game/game.rs` mutation methods
- **Problem:** Ownership validation is inconsistent across command paths: `MoveTroop` checks at dispatch (`game.get_unit_owner(&unit_id) == Some(owner_id)`), while `RecruitUnit`, `UpgradeCity`, `EmbarkUnit`, `DisembarkUnit` rely on internal game-layer checks (`recruit_unit` game.rs:398, `upgrade_city` game.rs:472, `embark_unit` game.rs:497, `disembark_unit` game.rs:570).
- **Resolved (per feedback):** Keep a **single** ownership check per operation by standardizing on the **game-layer methods**. Do not add a second dispatch-level check. Audit each game-layer mutation method so all of them validate ownership and fail closed (return `Err`/`None`) on mismatch; make `MoveTroop`'s dispatch-side check redundant with (or delegated to) the game layer so there is exactly one enforcement point per operation.
- **Reuse:** Existing internal ownership checks in the game methods; `game.get_unit_owner()` already used for `MoveTroop`.
- **Done when:** Every player command has exactly one ownership enforcement point in the game layer; all mutation methods fail closed on unauthorized access; behavior is unchanged for legitimate commands.

#### 3.2 Surrender system documentation
- **File:** `src/game/systems/surrender.rs` (~lines 10-20)
- **Problem:** Research confirmed the system is **already deterministic** (< 5% of max_men ⇒ surrender; `men <= 0` ⇒ surrender). No probabilistic `surrender_chance()` model exists in the system.
- **Fix (per D-3):** No code-behavior change. Add a doc comment explaining the deterministic rule. Verify existing tests cover it.
- **Reuse:** Existing tests in `surrender.rs` (`surrender_zero_men`, `surrender_below_5_percent_not_encircled`, `surrender_at_5_percent_stays`).
- **Done when:** Deterministic rule is documented in source; tests confirm the boundary behavior.

### WP-1 — Security Critical

#### 1.1 Move the entire LLM config onto the server (`SetSlotLlmConfig` carries only the model)
- **File:** `src/server/protocol.rs` (~lines 157-162); handler in `src/server/game_server.rs` (~line 1640); `src/config.rs:25` (provider config); frontend lobby UI
- **Problem:** `SetSlotLlmConfig { slot, provider, model, api_key: Option<String>, base_url }` transmits API keys (and provider/base_url) over plain ws:// with no TLS. The handler clones the client-supplied key into `LlmAgentConfig`.
- **Fix (per D-1):** Move the entire LLM configuration onto the server. Narrow the wire message to carry only the **model** (e.g. `SetSlotLlmConfig { slot, model }`). The server resolves the provider, `base_url`, and `api_key` solely from `Config::llm.providers` (`src/config.rs:25`) / environment variables. The lobby host's model choice is loaded via the configured provider's `/v1/models` endpoint on the server, so the server never accepts a provider/key/URL from the client. Ignore/drop any `api_key`/`provider`/`base_url` a client still sends.
- **Reuse:** `Config::llm.providers` from config/env; existing server-side provider lookup; server-side call to the provider `/v1/models` endpoint.
- **Gotchas:** CBOR ignores extra fields, so old clients sending `api_key` remain wire-compatible (fields are dropped). Update the frontend lobby UI to stop sending keys/provider/base_url and instead request models from the server; regenerate the generated protocol types (`frontend/src/generated/protocol.ts`); update `LlmAgentConfig` construction to source everything server-side.
- **Done when:** No API key, provider, or base URL crosses the wire; the only lobby-host-settable LLM value is the **model**, sourced from the server-side provider's `/v1/models` endpoint; `LlmAgentConfig` is fully server-resolved.

#### 1.2 XSS via `innerHTML` with untrusted data
- **Files:** `frontend/src/ui/spectator.ts` (~line 72), `frontend/src/ui/advisor.ts` (~line 14)
- **Problem:** Untrusted/LLM-generated strings interpolated into `innerHTML` unescaped:
  - spectator.ts: ``div.innerHTML = `<strong>${this.currentFilter}:</strong> ${entry.action}...` ``
  - advisor.ts: ``this.panel.innerHTML = `<h4>Advisor</h4><p>${text}</p>` ``
- **Fix:** Escape all user/LLM-controlled values before interpolation. Export the existing `escapeHtml()` helper from `frontend/src/ui/lobby.ts` (or move it to a shared `utils.ts`) and apply it to `currentFilter`, `entry.action`, `entry.reason`, and `text`. Alternatively use `textContent`/DOM APIs.
- **Reuse:** `escapeHtml()` in `ui/lobby.ts`.
- **Gotchas:** The advisor toggle-button innerHTML (~lines 20-26) is static HTML — leave as-is.
- **Done when:** No user-controlled/LLM string is interpolated into `innerHTML` without escaping.

### WP-4 — Hardening

#### 4.1 CORS — no change
- **File:** `src/server/game_server.rs` (~lines 96-99)
- **Resolved (per feedback):** Keep CORS as `allow_origin(Any).allow_methods(Any).allow_headers(Any)`. This is a LAN game intended for arbitrary host origins; restricting it adds risk of breaking legitimate LAN playback for marginal benefit. **No code change.** Document the LAN-only trust assumption.

#### 4.2 Timing-safe password comparison
- **File:** `src/server/lobby.rs` (~line 139)
- **Problem:** `password.as_ref() != Some(pass)` — short-circuiting comparison leaks prefix info via timing.
- **Fix (per feedback):** Use a constant-time comparison via the `subtle` crate (`subtle::ConstantTimeEq`) on the byte slices of the provided and stored password.
- **Done when:** Password comparison is constant-time, implemented with `subtle::ConstantTimeEq`.

#### 4.3 Lengthen lobby codes
- **File:** `src/server/lobby.rs` (~line 107)
- **Problem:** `Uuid::new_v4().to_string()[..8]` — 8 hex chars (~48 bits).
- **Fix:** Change `[..8]` to `[..12]` (UUID string is 36 chars, so safe; ~72 bits).
- **Done when:** Lobby codes are >= 12 chars.

### WP-5 — Performance

#### 5.1 Cache frontend terrain mesh
- **File:** `frontend/src/game/renderer.ts` (~lines 463-473)
- **Problem:** `marchingSquares(terrain, ...)` regenerates the terrain mesh every frame.
- **Research finding:** Output is already viewport-culled, so cost is O(visible cells) — relatively low. 
- **Fix (low priority, per research):** Introduce a dirty flag so the mesh is only recomputed when `gameState.terrain` changes (terrain is static during a match); keep camera/zoom transforms in the vertex shader.
- **Done when:** Terrain mesh recomputed only on terrain data change, not every frame.

#### 5.2 Pre-hash `unit_types` by name
- **Files:** `src/game/systems/movement.rs` (~96-99), `src/game/systems/attrition.rs` (~73)
- **Problem:** `settings.unit_types.iter().find(|ut| ut.name == ...)` linear search per unit per tick.
- **Fix (low priority, per research):** Build a `HashMap<String, ...UnitType>` once (unit types are static per game) and reuse for O(1) lookup. Note the Vec is tiny (<10 types), so impact is minimal.
- **Done when:** Unit-type lookup is O(1) via a prebuilt map.

#### 5.3 Share `reqwest::Client` across LLM provider instances
- **Files:** `src/llm/providers/openai.rs` (~89), `anthropic.rs` (~107), `ollama.rs` (~81)
- **Problem:** `reqwest::Client::new()` constructed per call — no connection pooling between calls.
- **Fix:** Store `http_client: reqwest::Client` as a field on each provider struct, initialized once in `new()`. `Client` is `Clone` and `Arc`-backed internally.
- **Done when:** A single `reqwest::Client` is reused across calls per provider instance.

#### 6.4 Implement timing in the `tick_system!` macro (instead of deleting)
- **File:** `src/game/game.rs` (~lines 1-12; call sites throughout `tick_game`)
- **Found:** Both `#[cfg(...)]` branches currently emit `$expr` only — a pure no-op wrapper; the `$name` label is unused. The file's header comment notes the timing was dropped because macro hygiene prevents the macro from accessing `guard`/`self` in the caller's scope.
- **Resolved (per feedback):** Implement real per-system timing in the debug-build branch using the existing `crate::game::debug_stats::DetailedTimer` mechanism (the same one already used in `combat.rs` / `attrition.rs`). Concretely, pass the handles the timer needs into the macro so hygiene is not an issue, e.g. `tick_system!("combat", &mut self.world, self.world_entity, expr)` and have the debug branch emit:
  ```rust
  {
      let _t = crate::game::debug_stats::DetailedTimer::new($name);
      let _r = $expr;
      _t.finish($world, $world_entity);
      _r
  }
  ```
  The release branch keeps the plain `$expr`. Update all ~12 call sites to pass the handles. This removes the no-op and gives per-system timing in debug builds.
- **Reuse:** `debug_stats::DetailedTimer::new` / `.finish` already used by combat.rs and attrition.rs.
- **Done when:** In debug builds each system invocation reports its own timing via `DetailedTimer`; release builds are unchanged (still inline `$expr`); all call sites updated.
