

# Deep Plan: Network Layer Performance (Final: I6, I8, I1, I4, I3, I7)

## Overview
The game server rebuilds a full snapshot of every unit — and its internal bookkeeping tables — every tick even when almost nothing changed, so the "network" phase of each tick takes ~13 ms and ~90k memory allocations on the 10k-unit benchmark: 88% of total system time. This plan removes that wasted rebuild (I1), tightens two cheap hotspots (I6, I8), then cuts two wire bloats — shipping whole 1 MB vision/territory grids when few cells change (I4), and fat per-unit updates (I3) — and finally keeps memory bounded when a client stalls (I7). Each item is a separate commit with its own A/B stress run; no gameplay changes.

## Problem Statement
Per-tick network phase at 10k units / 1000×1000 (`reports/stress_i5.html`, the baseline for this round): 13.43 ms/tick (88% of system time), 89,639 allocs + 17.27 MB/tick; movement·grid-dirty ticks spike to 27.5 ms / 9.86 MB wire due to whole-grid shipping. Already done (do not re-propose): W0–W9 (shared deltas, Arc grids, flat u8 grids, owner count maps, splice encoder), I2a (digest quantization), I2b (hot/cold split, `COLD_EVERY=10`), I5 (count-map winner/active check).

## Design

**Sequencing — cheap no-wire-change first, wire changes after.**
1. **I6 + I8** (S, zero wire change): quick alloc wins before I1 so I1's A/B baseline is clean.
2. **I1** (M–L): the largest single CPU/alloc win; server-internal only, no wire change.
3. **I4** (M, wire change): sparse grid diffs; separate commit from I3.
4. **I3** (M, wire change): compact unit updates.
5. **I7** (M, no wire change): egress hardening; verified by soak test, invisible to the headless benchmark.

**Approach per item (final):**

- **I6 — Zero-temp grid splice (per-player vision temp).** In the splice path, only the per-player `vision_grid_diff` goes through `encode_entry` (`protocol.rs:442`, called at `protocol.rs:531` inside `encode_delta_spliced`, `:508`) — a fresh ~1 MB `Vec` + copy per player per grid-dirty tick. `border_grid_diff` is already pre-encoded once per tick in `SpliceShared::build` (`protocol.rs:484`) and spliced by `extend_from_slice`. Replace the vision entry with a hand-written CBOR entry: text-string key prefix + byte-string length prefix + `extend_from_slice` of the grid `Arc`. The prefix writer must handle **all four definite-length forms** (≤23 → `0x4x`, ≤255 → `0x50+len8`, ≤65535 → `0x51+len16`, else → `0x52+len32`): the stress map is 1000×1000 = 1,000,000 bytes, i.e. the 4-byte form. Factor one shared `splice_bytes_entry(key, &[u8])` helper and also apply it to the once-per-tick border entry in `SpliceShared::build` (same one-line use). Gate: `splice_matches_encode_message_byte_for_byte` (`protocol.rs:750`), extended with a >65,535-byte grid fixture to pin the 4-byte form (current fixtures use 8-byte grids only).
- **I8 — Lazy spectator union grid.** `union_vision_grid_flat` (`game.rs:1712`: 1 MB `vec!` + P×1 MB OR) runs every tick while a spectator is connected (live call site `game_server.rs:730–737`, already behind the spectator guard). Cache `{last_union: Vec<u8>, last_source_arcs: Vec<Arc<Vec<u8>>>, last_pids: Vec<String>}` in the room tick state; recompute only when the pid list differs **or** any source player-grid `Arc` fails `Arc::ptr_eq`. The influence double-buffer publishes by refcount and flips *all* published `Arc`s on every dirty run (`components.rs:144–150`), so the cache hits exactly on grid-clean ticks — savings land in the grid-clean regime with a spectator connected; state that in A/B expectations. **Scope: live tick loop only** — the replay endpoint (`game_server.rs:1363`) keeps calling the function directly. No-spectator path must cost nothing (guard already exists).
- **I1 — Incremental baseline-keyed snapshot.** The current `run_network_phase` (`delta.rs:579`) already takes `&mut NetworkBaselines` and commits internally; its tail rebuilds `baselines.prev_units: HashMap<String, UnitState>` by cloning every unit's id String (`delta.rs:747–756`). The real change: stop materializing `current_units: Vec<UnitState>` from `Game::unit_states_direct` (`game.rs:1884`, ~10–15 allocs/unit/tick — `id: format!("unit_{eid}")` + per-tick String clones of `owner`/`unit_type`/`symbol` + equipment `Vec`s). Replace with a single in-place ECS pass that, for every live unit, diffs components against a baseline `UnitState`, emits only changed units into the shared-delta build, and mutates the baseline in place.
  - **Baseline store:** `Vec<Option<UnitState>>` indexed by dense hecs entity id + per-slot `u32` generation stamp + alive list, growing with the arena high-water index. Precedent for exactly this mechanism: `TickContext.owner_at`/`owner_gen` (`game.rs:318–323`) and test `owner_index_generation_guard_survives_id_reuse` (`game.rs:2567`). Slot reuse ⇒ same `unit_N` id, new incarnation ⇒ emit removed+added. Strings (id/owner/unit_type/symbol, equipment names) allocated once at recruit and kept in the baseline; the id is interned there so the common changed-unit emit (numeric fields) borrows instead of allocating.
  - **Ordering constraint:** the diff must be computed against the *pre-commit* baseline (so dead units are still visible as prev for `units_removed`), then the store is committed — i.e., the pass returns changed units + live-id set, and tombstones dead slots only after delta construction. `UnitStateDigest` diffing (`delta.rs:120`) is preserved — it still decides what goes on the wire; I1 only removes the full materialization.
  - **Consumer rewiring (all verified call sites):** `run_network_phase` drops its `current_units: Vec<UnitState>` param (`delta.rs:583`) and tail `HashMap` commit (`delta.rs:747–756`); tick loop `game_server.rs:562` (snapshot) and `:696` (call); the I5 active-check `count_units_by_owner(current_units.iter()…)` at `game_server.rs:588` moves onto the in-place pass (emit per-owner counts as a side effect of the same pass); `compute_shared_deltas` (`delta.rs:213`) takes the baseline store/view instead of `&HashMap<String, UnitState>` — the **replay endpoint** (`game_server.rs:1330+`, which builds its own `HashMap` prev-state and calls `compute_shared_deltas` per replayed tick) gets a thin adapter that keeps its existing HashMap path (no perf requirement there); the **benchmark mirror has two call sites** — `benchmark.rs:699/708` and `benchmark.rs:777/792` — both must stay call-site-identical to the live loop.
- **I4 — Sparse grid diffs (single changed-cell format).** Today a grid "diff" is the *absolute* grid (client replaces its copy: `connection.ts:405–407`), shipped whole whenever it changed: border diff built in `compute_shared_deltas` (`delta.rs:238–249`), per-player vision diff in `build_delta_inner` (`delta.rs:454–465`). Add an optional changed-cell list per grid to `GameDeltaMessage` (`protocol.rs:18`): if changed cells < ~5% of the grid, send the list; else the full grid (unchanged behavior). **One codec for both grids: each changed cell = packed `u32` `(new_value << bits) | cell_index`, `bits = ceil(log2(w*h))`** (1000×1000 → 20 bits, value fits 8; maps > 2²⁴ cells always use full-grid form). The value is mandatory for *both* grids — vision flips include 1→0 (cells becoming invisible), so a set-bit-only format is a correctness bug. No per-tick dirty-cell set exists in the sim (influence publishes whole-grid `Arc`s), so diff construction is an O(cells) memcmp: ~100 µs at 1 MB, acceptable. Splice coupling: new optional map entries change the count formula in `encode_delta_spliced` (`protocol.rs:512`, `debug_assert!((5..=8)…)` at `:521`) and the byte-for-byte test needs a sparse case. Frontend: extend the grid apply in `applyDelta` (`connection.ts:402`) and the replay reader (`replay_player.ts:~125`); regenerate `generated/protocol.ts`. Target: movement·grid-dirty wire 9.86 MB → well under (expect ~1–2 MB if changed cells < ~20%; the A/B is the arbiter and the 5% threshold is tuned once from those numbers).
- **I3 — Compact unit updates.** `UnitUpdate` (`protocol.rs:78`) is already a field-level diff with `#[serde(skip_serializing_if, default)]`. Remaining waste: (a) `equipment: Option<Vec<EquipmentState>>` repeats `name: String` + `cost_per_item` on every equipment change — unit types are **user-defined in the lobby with free-form names** (`lobby.ts`), so the client does *not* hold a template; it learns slot names/costs from `UnitState.equipment` (names kept) in `units_added`/`FullState`, which are sent once per unit lifetime and therefore stay unchanged. Change only `UnitUpdate.equipment → Option<Vec<u32>>` (per-slot counts, slot order = `UnitState.equipment` order). `UnitState` (incl. `max_equipment`, `protocol.rs:52–53`) is **not** touched. (b) `position: Option<(f32,f32)>` (8 B per movement update) → quantized packed `u32` (u16×2, ×65536 per cell) — secondary, ship client+server together, regen generated types. **(b) Numeric unit id: dropped from I3, deferred with a trigger.** The id is ~10 B on the wire while equipment names dominate, and a `String→u32` id is a breaking change in three verified places: the client→server protocol (5 `unit_id: String` variants in `ClientMessage`, `protocol.rs:149–180`), the frontend unit-store string keys + selection/hit-test, and outbound `unitId: unit.id` sends (`controls.ts:255`, `unit_info.ts:178/191`). Trigger to revisit: `unit_updates` wire bytes still a top contributor after I4/I3 per the A/B. No legacy-replay compatibility work: replay files are event-based JSON (`replay/replay.rs:19`, `params: serde_json::Value`), and the browser replay viewer decodes *live-generated* delta frames, so it is just updated with the frontend. No dual-type decoders.
- **I7 — Bounded keep-latest egress.** Both transports use `PlayerSender::Tcp(mpsc::UnboundedSender<Vec<u8>>)` (`room.rs:68`): WS bridge spawns a sender task over the unbounded channel (`game_server.rs:1515–1527`) and the TCP path does the same (`game_server.rs:1440–1462`); a stalled reader grows the channel without bound. Fix = typed payload + queue-depth semantics only: (1) change the channel payload to a tagged envelope (`Delta(Vec<u8>)` / `Reliable(Vec<u8>)`) at every send site — tick-loop deltas → `Delta`; everything else (`FullState`, `GameOver` at `game_server.rs:637/668/807`, `ClearSpectator`, `Error` replies in `handle_client_message` and both handlers, lobby messages) → `Reliable`; (2) bounded depth-2–4 **Delta** ring with keep-latest (a stale delta is worthless once a newer exists); `Reliable` messages are always queued, never dropped. **Out of scope** (opportunistic follow-ups, not gated by this change): relocating the WS sink into the sender task (drop the `Arc<tokio::sync::Mutex<WsSink>>` at `game_server.rs:1519`), and "draining multiple messages per wake" — the current `while let Some(data) = rx.recv().await` loops already do that.
- **Alternatives considered:** rayon per-player parallelism — rejected, A/B dispatch-overhead regression documented in `delta.rs` header. UDP/WebRTC — rejected (browser constraint; WS is right below ~15 Hz). I9 (unit AOI) and I10 (off-tick encode worker) — deferred with triggers below. I3 numeric id — deferred, trigger above.

## Dependencies
- None new (ciborium 0.2, tokio 1, axum 0.7, hecs 0.11 all in use; I4/I3 are wire-format changes, not new crates)

## Risks & Mitigations
- **I1 entity-id↔index invariant / tombstones** — hecs reuses freed ids with bumped generation (proven in-tree: `owner_index_generation_guard_survives_id_reuse`, `game.rs:2567`); mitigate with per-slot generation stamps (precedent `game.rs:318–323`), diff-against-pre-commit-baseline ordering (dead units still visible for `units_removed`), lifecycle tests, and the golden parity assertion before deleting the old path
- **I1 scope creep into consumers** — three consumers of the materialized snapshot besides the network phase (active check `game_server.rs:588`, replay endpoint `game_server.rs:1330+`, benchmark mirrors ×2); all listed in the rewiring step; replay adapter keeps the unoptimized path
- **I4 changed-cell density** — if movement ticks change > ~5% of cells (plausible at 10k units on 1000×1000), the sparse form is rarely chosen and the wire win is small; the 5% threshold is tuned once from I4's own A/B wire numbers, and the full-grid fallback guarantees no regression
- **Wire-format regressions from I4/I3** — additive `#[serde(default)]`/`skip_serializing_if` fields, pinned byte-for-byte splice test (extended with sparse + 4-byte-length cases), frontend/replay tests before merging either wire commit; replay files are event-based JSON and unaffected
- **ms numbers lying under load** — round-3 false regression (I5 +6.8% was machine load); workload metrics (allocs/wire/updates, bit-stable) are the primary A/B signal; `net_ms` P50/P90 compared only on a quiet machine (load ≤ 0.5)
- **I7 dropping messages under backpressure** — keep-latest applies to deltas only; `Reliable` envelope never dropped; two-path design + soak test
- **Benchmark/live skew** — `run-stresstest.sh` already passes `--bench-splice`; both `benchmark.rs` mirrors must stay call-site-identical to the `game_server.rs` tick loop through the I1 signature change (regression risk: harness drift)
- **Grid `Arc` lifetime invariant** — influence double-buffer publishes `Arc`s by refcount and never mutates during the encode window (`components.rs:144–150`); I6/I8 must borrow, never mutate, during encode; I8's `Arc::ptr_eq` cache is safe *because* of this (dirty run flips all Arcs ⇒ guaranteed miss)
